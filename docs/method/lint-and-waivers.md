# RTLの静的検査と警告の扱い

静的検査（lint）は、入力を動かす前に幅・符号・未接続・暗黙ネット・ラッチなどの問題候補を見つけるために使います。シミュレーションで通ったこととは別に、対象のソース・トップ・パラメーターを明示して確認します。本リポジトリでは[共通入口](../../tools/run_lint.py)と[負例を含む実習](../../examples/local-lint/README.md)を用意しています。

## 1. 対象を固定する

[構成台帳](../../tools/lint_targets.json)に、`examples`配下の`rtl`ディレクトリ内の全SystemVerilog／Verilogファイル、宣言された各DUTモジュール、依存ソース、パラメーターを登録します。取り込んだMXFP4の上流RTLも含みます。全例の`run.py`にも、自身のDUT、共有DUT、手順・モデル中心の例という適用範囲を対応付けます。新しいファイル・モジュール・例が台帳から漏れると失敗します。

各モジュールの既定構成と、台帳に列挙した通常のパラメーター構成を読み込みます。上位モジュール内の固定パラメーターは、その上位を読み込むときに展開されます。任意のパラメーター値・defineの全組合せを調べた結果ではありません。対象を増やすときは、動作試験の構成と台帳を一緒に見直します。

テストベンチ、SVA・フォーマルのハーネス、実行時の生成HDL、合成後ネットリストは、この共通DUT lintの範囲外です。それぞれの`run.py`によるビルド・実行で確認します。接続性の例だけは、正式なブラックボックス宣言を台帳へ明記します。内部回路を別例の同名モジュールで置き換えると、異なる回路を検査することになるためです。

## 2. 実行して指摘を読む

```sh
python3 tools/run_lint.py --out artifacts/dut-lint
python3 examples/local-lint/run.py --out artifacts/lint-exercise
```

Verilator 5.052の`--lint-only --Wall -Wno-fatal`を使います。`-Wno-fatal`は警告を出力したままツールの処理を続ける設定です。終了コードだけで合格にせず、全指摘を読み取り、後段で差分と根拠を判定します。

| 出力 | 確認すること |
| --- | --- |
| `manifest.json` | 予定トップ・構成、入力SHA-256、判定一覧 |
| `targets/<構成>/lint.log` | 実行したコマンドに対応するツールの生ログ |
| `targets/<構成>/result.json` | 診断、終了状態、新規・解消・版変更 |
| `diagnostics.json` | 全体の警告一覧と`clean`の判定 |
| `baseline-candidate.json` | レビュー前の候補。採用に必要な項目は未記入 |
| `summary.json`／`junit.xml` | 予定した検査をすべて完了したか |

この環境の5.052では、SARIF出力にJSON構文エラーを再現しました。この入口はテキスト診断を厳密に読み、規則名・位置がない警告や未知の診断書式を拒否します。壊れたSARIFを警告0件と解釈したり、自動修復して根拠に使ったりしません。

## 3. 修正・既知指摘・除外を分ける

新しい指摘は、最初に対象構成とソース位置を確認します。例えば、CRCやTop-Kの組合せ処理内の一時変数に代入漏れがあれば、初期値を与えて不要なラッチを除き、同じ構成の動作試験や証明をやり直します。単に警告を消すために必要な処理を削除しません。

[警告台帳](../../tools/lint_baseline.json)には、指摘の完全な位置・メッセージ・件数に加えて、次を記録します。

| 項目 | 記録する内容 |
| --- | --- |
| `known-debt` | 未解決の既知指摘。安全性や仕様適合を確認済みという意味にはしない |
| `waived` | 範囲と理由を限定して除外する指摘。例：接続性モデルの意図的な未駆動自由値 |
| `reason`／`impact` | なぜこの扱いにするか、どの限界・影響が残るか |
| `reviewer`／`method` | 誰が、どの方法でレビューしたか。AIの処理を人の承認と記録しない |
| `expires` | ソース・構成・ツール版の変更など、見直しが必要になる条件 |

現在の初期台帳には未解決の幅・未使用信号などを残しています。**リグレッションの成功は「新規指摘なし・記録した既知指摘から変化なし」を意味し、警告0件を意味しません。** 警告が残る場合は`clean=false`です。製品への採用時には、残った指摘を担当者が処置し、必要な承認を別に記録します。

## 4. 台帳を更新する

1. 失敗した実行のログと`new`／`resolved`を確認する。
2. RTL、構成、ツール変更によるものかを確認し、修正するものを先に直す。
3. 候補と元の台帳を比較し、残す指摘ごとに扱い・理由・影響・レビュー方法を記入する。
4. 関係する動作試験を実行し、指摘数だけを合わせていないことを確認する。
5. 台帳を更新して新しい出力先へ再実行し、差分と入力ハッシュを照合する。

候補の`REVIEW REQUIRED`が残る台帳は拒否します。警告が解消した場合も差分を報告し、古い除外を残したまま自動的に合格へ戻しません。ソースハッシュと対象構成のハッシュを記録するため、同じ行番号・同じ警告件数でも、対象を編集すれば再レビューが必要です。
