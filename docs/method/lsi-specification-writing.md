# 検証しやすいLSI仕様書の書き方

LSIの仕様書は、設計者・検証者・組込みソフトウェア担当・統合担当が、同じ条件から同じ期待結果を判断できるように書きます。機能名と正常時の説明に加え、設計意図、入力の受理、境界・同時動作、異常、初期化と復帰、観測点を残します。

これから仕様書を作る場合は本資料と[記入用テンプレート](../templates/lsi-specification.md)を使います。書かれた仕様から項目を作る段階は、[仕様から検証項目を作る実例](spec-to-test-items-walkthrough.md)と[検証手順](spec-to-verification-method.md)へ進みます。章立てと記録方法は本リポジトリの提案であり、すべての企業・製品に共通する必須様式ではありません。

## 1. 読む人と仕様の境界を決める

まず、製品全体の仕様、IPの外部仕様、内部の実装設計書、検証計画の役割を分けます。

| 文書・情報 | 主に決めること | 検証者が必要とするもの |
| --- | --- | --- |
| 製品・システム仕様 | 用途、外部からの要求、機能・性能・動作環境 | IPへ割り当てた要求と、上位で確認する条件 |
| IPの外部仕様 | インターフェース、観測可能な振る舞い、構成・制約 | 刺激と期待値を決められる契約 |
| 実装設計書 | パイプライン、内部状態、共有資源、採用方式と根拠 | 外部要求との対応、内部で検査すべき不変条件 |
| 検証計画 | どの要求を、どの方式・構成・条件で確認するか | 要求・チェッカー・到達目標・証跡・担当の対応 |

一つのファイルへまとめても、どの記述がどの役割かは表示します。外部のレイテンシや容量が要求なら規定し、単に現在のRTLがその構成だからという理由で、内部レジスタ名や状態符号まで外部契約にしません。安全機構・CDC方式・使用セルなど、実装方式そのものが制約になる場合は、その理由・適用条件・確認担当を明記します。

## 2. 設計意図・規定・前提を分けて書く

### 2.1 設計意図は検証の狙いを伝える

設計意図には、解決したい問題、想定ユースケース、守りたい性質、代替案とトレードオフを書きます。検証者は、そこから正常動作だけでなく、設計判断が効く境界・競合・誤使用を探せます。

例えば「イベントとクリアが同時ならセット優先」だけでなく、「ソフトウェアのクリア処理と新しいイベントが重なっても、新しい通知を消さないため」と書くと、同時受理と前後1サイクル、マスク中、リセットとの競合を検討しやすくなります。ただし、1ビットの保留状態は複数イベントの回数を保存しません。全イベントを数える要求があるなら、別の要求と方式の検討が必要です。

設計意図の記録には、少なくとも次を持たせます。

- 意図ID、対象の機能・構成、背景・利用者が困ること。
- 守りたい性質と、それを具体化した要求ID。
- 採用した判断、検討した代替案、容量・面積・遅延・電力等のトレードオフ。
- 成立に必要な前提、保証しない範囲、判断担当・根拠・改訂。

### 2.2 設計意図を隠れた要求にしない

| 記述の種類 | 書く内容 | 扱い |
| --- | --- | --- |
| 規定・要求 | 実装が満たす動作・値・時間・制約 | 要求IDと改訂を付け、合否を判定できる形にする |
| 設計意図・根拠 | なぜ必要か、なぜその判断をしたか | 関連要求へ結び付ける。説明だけを新たな合否基準にしない |
| 環境前提 | 外部が満たす入力・順序・周波数等 | 満たす側・確認する側・違反時の扱いを決める |
| 参考例・推奨 | 理解を助ける波形や典型的な使用法 | 規定か参考かを表示し、例にない動作も本文で定義する |
| 未確定事項 | 未決の数値・優先順位・構成 | 課題ID、影響、担当、期限を付ける。推測で承認済みにしない |

「高速に」「適切に」「通常は」といった意図を、そのまま判定条件にしません。必要な上限・条件・例外へ展開します。意図と要求・図表が矛盾した場合は、検証者が都合のよい方を選ばず、仕様課題として解決します。

要求の明確さ・検証可能性・根拠と前提の記録は、[NASAの要求記述ガイド Appendix C](https://www.nasa.gov/reference/system-engineering-handbook-appendix/)も参考になります。本資料のLSI向け章立てや以下の回路例は、本リポジトリ向けに整理したものです。

## 3. 検証項目へ展開しやすい章立て

RTLのmodule一覧だけを目次にせず、利用者が行う操作と、外部から見える機能・契約を軸にします。内部のブロック図は、機能と実装の対応を補うために使います。[記入用テンプレート](../templates/lsi-specification.md)は次の構成です。

| 章 | 主な内容 | 検証項目を作る入口 |
| --- | --- | --- |
| S00 文書管理・読み方 | 文書ID・版、用語、規定と参考、参照仕様と優先関係 | どの版・記述を根拠に判定するか |
| S01 目的・設計意図・使用シナリオ | 背景、上位要求、ブロック図、選択理由、保証の限界 | 必要な性質と、その判断が効く条件 |
| S02 適用範囲・構成・モード | パラメーター、合法範囲、オプション、対象外 | 構成ごとの計画と禁止構成 |
| S03 インターフェース・データ形式 | 端子、方向、幅、ドメイン、受理・完了、単位、符号・バイト順 | 入力・出力・観測時点 |
| S04 機能ごとの動作要求 | 正常、境界、保持、競合、異常、初期化、完了 | 要求IDごとの刺激と期待値 |
| S05 レジスタ・メモリマップ | アドレス、アクセス属性、リセット値、副作用、予約領域 | CSR操作、部分書込み、同時更新 |
| S06 状態・時間・性能・同時動作 | 状態遷移、優先順位、レイテンシ、帯域、仲裁 | 時間関係・クロス条件・進行性 |
| S07 クロック・リセット・電源 | CDC/RDC、停止・再開、リセット種別、保持・破棄 | 起動・中断・復帰・非同期境界 |
| S08 異常・保護・テストモード | エラー、故障反応、権限、DFT、デバッグ | 拒否・通知・封じ込め・機能復帰 |
| S09 演算・数値・容量の境界 | 精度、丸め、飽和、オーバーフロー、最大長 | 値の境界と独立した参照モデル |
| S10 観測点・検証との対応 | 状態・通知・カウンター、要求と判定の対応 | 観測漏れ、検査方法、到達性 |
| S11 実装・物理・品質条件 | 対象技術、クロック・PVT、電力等の基準、担当 | RTL以外で確認する範囲 |
| S12 変更・未確定・レビュー | 要求の改訂、影響、課題と解決、承認状態 | 古い期待値・証跡の失効と再確認 |

小さなIPでは章を統合できます。適用しない章にも理由を残し、未記入と対象外を区別します。S04の各機能は、「目的・関連意図 → 適用条件 → 受理 → 正常動作 → 境界 → 競合 → 異常 → リセット・復帰 → 結果と観測点」の同じ順で書くと比較しやすくなります。

同時動作をすべて巻末へ追いやらず、各機能から優先順位表や相手機能の要求へリンクします。例えばDMAは「設定」「開始の受理」「境界分割」「応答待ち」「中断」「完了通知」を別々に探せるようにします。

## 4. 一つの要求を、条件と結果へ落とし込む

基本形は、**対象・適用構成が、どの事前状態で、何をいつ受理したら、どこへ、どの値・状態・応答を、いつまでに示すか**です。独立に合否を判断する主張を分け、必要な条件を省略しないようにします。

| 要求に持たせる情報 | 記入すること |
| --- | --- |
| 識別と根拠 | 安定した要求ID・改訂、上位要求、設計意図、出典の節・図表 |
| 適用と前提 | 構成・モード・事前状態、外部が満たす条件と確認担当 |
| 受理と動作 | valid/ready等の受理条件、対象クロック・エッジ、状態更新・応答 |
| 値と時間 | 幅・単位・符号・許容範囲、開始点と終了点、含む／含まない境界 |
| 競合と例外 | 同時動作の優先順位、異常、リセット、保持・取消・復帰の関連要求 |
| 観測と状態 | 端子・CSR・トランザクション等の観測点、判定方法、未確定事項 |

要求IDを章番号だけにすると移動で対応が切れるため、意味を保つIDを使います。本文・図・表・CSR定義へ出典IDを付け、同じ規定は一か所を原本にして参照します。要求の分割・統合・廃止では、旧IDを再利用せず対応を残します。

## 5. 曖昧な記述を改善する

| 曖昧な書き方 | 明確にする方向 |
| --- | --- |
| 要求を受けたら速やかに完了する | 受理エッジ、応答の定義、最小・最大レイテンシ、待ち・停止時の条件を数値で定める |
| busy中は操作しない | 誰の制約か、どの操作を禁じるか、入力された場合に拒否・保持・エラー等の何を行うかを定める |
| 最大長まで転送できる | 単位、上限を含む範囲、0・最大・最大+1、アドレス加算の桁あふれを定める |
| 割り込みをクリアする | W1C等の方式、更新する時点、イベントとの同時受理、IRQへの反映を定める |
| リセットで初期化する | リセット種別、同期／非同期、値、保持・破棄、途中処理、解除後の最初の受理を定める |
| エラー時は状態不変 | 応答・エラーカウンター等の更新を含むか、どの状態・メモリ範囲を保護するかを分ける |
| データの下位ビットを返す | 入力と演算の符号・中間幅、丸め・切捨て・飽和、出力位置を定める |
| 予約ビットは使わない | 読出し値と書込みの扱い、予約アドレスとの違い、将来互換性の条件を定める |

環境前提違反に対する保証と、検出して応答すべき不正要求を区別します。「未規定」で任意の出力を要求どおりと判断したり、実行可能な異常入力をすべてassumeで消したりしません。保証しない条件も、範囲と理由を明記して統合担当へ引き継ぎます。

## 6. 意図から検証項目へつながる記入例

### 6.1 背景と適用範囲

**意図 INT-IRQ-001（参考・根拠）**：ソフトウェアが保留イベントをクリアする時点に新しいイベントが来ても、その通知を消さないようにする。マスクは通知だけを抑え、保留状態を捨てない。

題材は1ビットの割り込みコアです。入力`event`・`clear`は`clk`立上りで受理する同期信号、`rst_n`はLow有効の同期リセット、`irq_en`は同じクロック領域の通知許可です。この教材では、保留状態を出すPENDと通知出力IRQを観測点とします。CSRのバス受理生成、非同期パルスの捕捉、イベントの回数保存、X/Z、物理的なグリッチ保証は対象外です。

`clear`は、上位がW1C書込みを正常完了したときに生成する同期要求を想定します。待ち中・エラー応答で発生させない契約は上位の仕様で定めます。ここでのIDは記入例用で、既存の要求カタログを改訂するものではありません。

### 6.2 動作の規定

| 要求ID | 適用条件・受理 | 規定する結果 |
| --- | --- | --- |
| REQ-IRQ-RESET r1 | `clk`立上りで`rst_n=0` | event・clear・irq_enに関係なく、更新後PENDを0にする |
| REQ-IRQ-SET r1 | `rst_n=1`でevent=1、clear=0を受理。irq_en=0／1の両方に適用 | 更新後PENDを1にする |
| REQ-IRQ-CLEAR r1 | `rst_n=1`でevent=0、clear=1を受理 | 更新後PENDを0にする |
| REQ-IRQ-PRIORITY r1 | `rst_n=1`でevent=1、clear=1を同じ立上りで受理 | 更新後PENDを1にする。クリアよりセットを優先する |
| REQ-IRQ-HOLD r1 | `rst_n=1`でevent=0、clear=0を受理。irq_en=0／1とその変更を含む | PENDを保持する |
| REQ-IRQ-OUTPUT r1 | 組合せ出力が安定した有効期間 | IRQをPEND AND irq_enとする |

この規定から、状態更新はリセット、セット、クリア、保持の順となります。セット優先はこの例の仕様で、すべてのW1C回路に共通の規則ではありません。PEND=1の間に来た複数イベントは一つの保留状態へまとまります。

### 6.3 図表で時間関係を補う

以下の出力は各立上りによる状態更新と組合せ出力が安定した後の値です。irq_enの値も、その観測時点での値を示します。同期リセットはクロックを待たずにPENDを消す規定ではありません。

| 立上り | rst_n | event | clear | irq_en | 更新後PEND | 更新後IRQ | 狙い |
| --- | --- | --- | --- | --- | --- | --- | --- |
| k0 | 0 | 1 | 1 | 1 | 0 | 0 | リセット優先 |
| k1 | 1 | 1 | 0 | 0 | 1 | 0 | マスク中も保持 |
| k2 | 1 | 0 | 0 | 1 | 1 | 1 | 許可への変更で通知 |
| k3 | 1 | 1 | 1 | 1 | 1 | 1 | イベントとクリアの競合 |
| k4 | 1 | 0 | 1 | 1 | 0 | 0 | クリアだけを受理 |
| k5 | 1 | 0 | 0 | 1 | 0 | 0 | 状態保持 |

この表は説明用の一系列で、全組合せの網羅表ではありません。シミュレータのNBAや`#1`は検証実装の観測手段であり、物理的な出力遅延の仕様に置き換えません。SVAのサンプル時点との関係は[既存の検証項目作成例](spec-to-test-items-walkthrough.md#6-期待値と観測時点を具体化する)へ対応付けます。

### 6.4 検証者が作る項目の入口

| 要求・意図 | 作る条件 | 比較・観測すること |
| --- | --- | --- |
| PRIORITY・INT-IRQ-001 | PEND=0／1、irq_en=0／1で同時受理、さらに前後1サイクル | 同時はPEND=1、前後は各エッジの受理順どおり。途中の結果も比較 |
| SET・HOLD・OUTPUT | マスク中のevent、マスク解除、再マスク | PENDの保持と、通知だけの抑止・再開 |
| RESETと通常動作 | PEND=1でリセットと操作を重ね、解除直後に再度受理 | リセット優先、古い通知なし、最初の新しい受理が成立 |

設計意図から条件を広げても、期待値の根拠は規定した要求へ結び付けます。意図から推測しないと決まらない結果があれば、仕様を補ってから採用します。

## 7. LSIで抜けやすい具体事項

- **レジスタ**：アドレス・ビット位置・幅、RO/RW/W1C等の属性、リセット種別ごとの値、読出し副作用、byte strobe、ハード更新との競合、未実装アドレス、予約ビット、複数ワードの一貫性。
- **バス・メモリ**：要求の受理、応答と所有権、待ち中の保持、順序・ID、部分更新、境界分割、エラー時に更新済みとなる範囲、キャッシュ・DMAとの可視性。
- **数値・データ形式**：符号、エンディアン、固定小数点の小数位置、中間幅、丸め、飽和／wrap、特殊値、CRC等の多項式・初期値・ビット順。
- **状態・性能**：状態遷移の前提、同時事象の優先順位、レイテンシを数えるクロックと開始・終了、負荷とready条件、期限のない完了に必要な進行条件。
- **クロック・リセット・電源**：同期関係、CDC/RDC、解除順、停止中の要求、部分リセット、未完了の保持・取消、電源復帰後の初期化。[非同期検証の手順](asynchronous-verification.md)へつなぐ。
- **保護・DFT**：権限・ライフサイクル、異常応答と回復、テストモードへの入口、機能への影響、破壊する状態、終了と復帰。[DFTの手順](dft-verification.md)へつなぐ。
- **実装・物理条件**：ASIC／FPGA、合成対象RTLの制約、セル・メモリ、周波数・PVT・電力等の基準、実施段階・担当。詳細は[合成向けRTLのルール](synthesizable-rtl-guidelines.md)と[製品開発上の確認](spec-to-verification-method.md#14-実際の半導体設計で併せて必要な項目)へ分担する。

各項目は機能の該当節から参照し、用語だけを一覧にして完了にしません。単純な数値でも、最小・最大・一つ外・状態と重なる境界を検証者が選べるようにします。

## 8. 原本・図表・変更を管理する

レジスタはSystemRDL・Hjson等の機械可読な原本から表・RTL・ソフトウェア定義を生成すると、不整合を減らせます。ただし、同じ原本から作ったRTLとチェッカーが一致しても、原本の誤りを検出できるとは限りません。動作の根拠・独立レビュー・生成器の検査を残します。

図表にはID、凡例、クロックと観測時点、validの条件、規定／参考の別を付けます。波形の一例で、描かれていない競合や異常時の動作を暗黙に決めません。本文・表・図の矛盾は仕様課題へ戻します。

変更履歴には、変更した要求ID・旧新の意味・理由・適用版・影響する構成・互換性を残します。RTLだけ先に直して仕様を実績へ合わせず、参照モデル・SVA・カバレッジ・CSR生成物・ソフトウェア・既存証跡への影響を確認します。設計意図だけの変更でも、対応する要求が本当に変わらないかレビューします。[仕様変更の演習](../../examples/local-spec-change/README.md)も参照してください。

## 9. レビューで「項目を作れるか」を確かめる

1. 設計者以外が、主要な使用シナリオと設計意図を説明できる。
2. 各機能に、受理条件・期待結果・観測点・時間と適用構成がある。
3. 正常だけでなく、境界・異常・同時動作・リセット・停止復帰の結果が決まる。
4. 外部前提を満たす側と確認する側が分かり、未確定が合格基準へ紛れていない。
5. 主要な要求から検証項目を数件試作し、RTLを読まずに期待値を書ける。書けない箇所は仕様へ戻す。
6. 実装制約・物理評価・ソフトウェアで確認する範囲が、担当と文書へ割り当てられている。
7. ID・版・図表・生成原本・未解決課題と変更履歴を追える。

全員が同じ期待値に到達できるかを、レビューの判断材料にします。テスト本数や要求数の多さだけで、仕様の十分性を判断しません。OpenTitanの[開発段階](https://opentitan.org/book/doc/project_governance/development_stages.html)と[検証方法](https://opentitan.org/book/doc/contributing/dv/methodology/index.html)も、設計仕様と検証計画・レビューを対応付ける実プロジェクトの参照先です。
