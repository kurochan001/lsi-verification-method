# 試作と実機評価：FPGA・エミュレーション・実チップでの検証

シミュレーションで合格した回路を、FPGAの試作、エミュレーター、実チップで動かすと、シミュレーションでは起きなかった不具合が見つかることがあります。速く長く動かせる、実際の周辺回路とつながる、という利点の代わりに、回路の中が見えにくくなり、同じことを2度起こすのが難しくなります。この文書は、その違いと、観測の手段、見つけた不具合をシミュレーションの固定回帰へ持ち帰る流れを整理します。

このリポジトリでは、FPGA・エミュレーター・実チップでは何も実行していません。実行例は、試作で使う仕組み（合成できる自己判定テストベンチ、トレースバッファ）をシミュレーションで確かめるものです。

## 1. 環境ごとの違い

| 環境 | 速さの目安 | 回路の中の見え方 | 同じことを再び起こせるか | 主な用途 |
| --- | --- | --- | --- | --- |
| RTLシミュレーション | 遅い | すべての信号 | できる（seedと入力を固定すれば同じ） | 機能の検証、回帰 |
| エミュレーション | シミュレーションの数百倍以上 | 多くの信号を記録できるが、記録の深さと設定に限りがある | ほぼできる（環境の入力を記録すれば） | ソフトウェアを含む長い試行、性能 |
| FPGAの試作 | 実時間に近い | 埋め込んだ観測の回路が拾うものだけ | 難しい（非同期の入力、実際の周辺回路） | ソフトウェアの開発、実際の周辺との接続、長時間の試行 |
| 実チップ | 実時間 | ピン、デバッグの経路、試験回路だけ | 難しい（温度・電源・個体差も加わる） | 最終の確認、特性、量産の試験 |

速さの目安は環境と回路の大きさで大きく変わります。この表は傾向を示すもので、測った値ではありません。

## 2. シミュレーションとの違い

### 実機でだけ起きること

- **長い試行**：シミュレーションでは届かない回数・時間（カウンターの一周、何時間もの通信）に届きます。まれな並びの入力も、そこで初めて現れます。
- **非同期の入力と初期値**：クロックの乗換え、外部の入力の到着の時刻、電源投入時の値は、シミュレーションでは決まった値になりがちです。実機では毎回違い、取込みの時刻の違いで結果が変わることがあります。
- **実際の周辺回路**：メモリ、通信の相手、アナログの回路、ソフトウェアの実際の動作が加わります。仕様の読み違いが、ここで初めて分かることがあります。

### 試作の回路は、製品の回路と同じではない

FPGAの試作では、製品のRTLの一部を置き換えることがよくあります。メモリのマクロ、クロックの生成とゲーティング、PLL、リセットの回路、アナログの部分などです。置き換えた部分で起きた不具合や合格は、製品の回路での結果ではありません。どこを置き換えたかを、試作の版ごとに記録します。

### 観測の回路も回路の一部

トレースバッファや自己判定の回路を埋め込むと、面積やタイミングが変わり、観測の回路そのものが誤ることもあります。観測の回路は、それ自体をシミュレーションで検証してから使います。合成で消されないこと（観測されない回路は合成で取り除かれる）も確かめます。

## 3. 観測の手段

| 手段 | 見えるもの | 費用と限界 | このリポジトリの例 |
| --- | --- | --- | --- |
| 自己判定（刺激の生成と署名） | 合否の1ビットと、最終の署名 | どこで誤ったかは分からない。打ち消し合う複数の誤りは署名に残らないことがある | [合成できる自己判定テストベンチ](../../examples/local-synth-testbench/README.md)、[LBIST](../../examples/local-lbist/README.md) |
| トレースバッファ | トリガーの前後の、選んだ信号の数十〜数千クロック | 記録の深さと幅だけのメモリが要る。トリガーをどこに置くかで、見える範囲が決まる | [トレースバッファ](../../examples/local-trace-buffer/README.md) |
| スキャンの読出し | クロックを止めた時点の、全フリップフロップの値 | 止めた時点の1枚だけ。動作を止める必要がある | [内部スキャンとATPG](../../examples/local-scan-atpg/README.md) |
| デバッグの経路 | CPUのレジスタやメモリ、停止・再開・1命令の実行 | ソフトウェアから見える状態だけ。止めると周辺の動作も変わる | [JTAG TAP](../../examples/local-jtag-tap/README.md)、[RISC-Vのデバッグ](../../examples/local-riscv-debug/README.md) |
| 状態のレジスタと計数器 | エラーの回数、最後のエラーの種類、性能の計数 | 何を数えるかを、設計の時に決めておく必要がある | 各例のエラーの状態のレジスタ |
| ソフトウェアのログ | ソフトウェアが見た結果と時刻 | ハードウェアの中の時刻の関係は分からない | — |

1つの手段で全部は見えません。どの不具合のときに、どの手段で何を見るかを、試作の前に決めておきます。例えば、エラーの状態のレジスタを、トレースバッファのトリガーにつないでおけば、エラーが出た前後の入力を記録できます。

## 4. 不具合を持ち帰って固定回帰にする

```mermaid
flowchart LR
  accTitle: 実機の不具合をシミュレーションの固定回帰へ持ち帰る流れ
  accDescr: 実機で不具合を観測したら、トレースや署名などの記録と、回路・ソフトウェア・ボードの版を残す。記録を、既知の状態から始まるシミュレーションの入力に直し、古い版の回路で同じ不具合が再現することを確かめる。原因を直した版で合格したら、その入力を固定の回帰へ加え、実機でも再び確かめる。
  F["実機で不具合を観測"] --> K["記録と版を残す<br/>トレース・署名・設定"]
  K --> C["入力に直す<br/>既知の状態から始める"]
  C --> P["古い版で再現"]
  P --> X["原因を直す"]
  X --> R["固定の回帰へ加える"]
  R --> B["実機で再び確かめる"]
```

1. **記録を残す**：トレースのダンプ、署名、エラーの状態のレジスタを、そのまま保存します。読み出した後に手で編集しません。
2. **版を固定する**：RTL、FPGAのビットストリーム、ソフトウェア、ツールの版、ボードと条件を記録します（下の節）。
3. **既知の状態から始める**：記録の窓の先頭で、回路の中の状態は分かりません。リセットの直後や、状態が決まる事象（例：フレームの区切り）から再生を始めます。窓の中にそうした点がなければ、記録が短すぎて再生できません。トリガーの前に何クロック残すかは、試作の前に決める設計の判断です。
4. **古い版で再現する**：再生の入力で、実機と同じ版の回路をシミュレーションし、同じ不具合が同じ位置で出ることを確かめます。再現しないときは、記録が足りないか、実機とシミュレーションの前提（初期値、非同期の入力、置き換えた回路）が違います。
5. **原因を直し、固定の回帰に加える**：直した版で合格したら、その入力を毎回の回帰へ入れます。古い版では不合格になることも、変異として確かめておきます。そうすれば、回帰が実際にその不具合を見つけられることを示せます。
6. **実機で再び確かめる**：シミュレーションでの合格は、記録した範囲の入力での合格です。実機でも、同じ条件で再発しないことを確かめます。

再生で再現しない不具合を、「シミュレーションでは問題ない」として閉じてはいけません。再現しないこと自体を記録し、記録の手段や条件を見直します。不具合の切り分けの進め方は[失敗の解析](failure-analysis.md)にもあります。

## 5. 記録すべきこと

| 項目 | 内容 |
| --- | --- |
| 回路の版 | RTLのコミット、試作で置き換えた部分の一覧、パラメーター |
| ビットストリームとツール | 合成・配置配線のツールの版、制約、ビットストリームのハッシュ |
| ソフトウェア | ファームウェアとテストプログラムの版、設定値 |
| ボードと条件 | ボードの個体、電源電圧、温度、クロックの周波数、つないだ周辺機器 |
| 観測の設定 | トリガーの条件、記録の深さと位置（トリガーの前後のクロック数）、記録した信号 |
| 観測の結果 | ダンプ、署名、状態のレジスタの値、再現の頻度（何回中何回） |
| 再生 | 再生の入力の作り方、既知の状態の点、シミュレーションでの再現の有無と位置 |

## 6. 検証計画への組込み

- **何をどこで閉じるか**：機能の網羅はシミュレーションとフォーマルで閉じます。試作と実機では、長い試行、実際の周辺との接続、性能、シミュレーションで前提にした値（初期値、非同期の時刻）の確認を受け持ちます。どの要求をどの環境で確かめるかを、計画の表に書きます。
- **実機の合格の意味**：実機での合格は、その版・その条件・その試行で観測した範囲の合格です。網羅の判断には使いません。
- **観測の回路の検証**：埋め込む自己判定やトレースの回路も、要求と目標を持つ検証の対象です。合成した後も残ることを確かめます。
- **サインオフ**：試作と実機で見つけた不具合と、その固定回帰を、サインオフの記録に残します（[サインオフの記録の雛形](../templates/signoff-record.md)）。
