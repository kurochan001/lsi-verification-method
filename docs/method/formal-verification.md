# フォーマル検証の計画・証明・完了判定

[一般化した検証手順](spec-to-verification-method.md)の9.12節を具体化した資料です。仕様をプロパティへ分け、環境の仮定、初期状態、抽象化、対象構成を明示して証明します。反例が見つからなかった範囲と、非有界に証明した範囲を区別し、証明対象から漏れた要求も管理します。

以下は本リポジトリで定めた運用案です。割り込みのコードは説明用に作成した小さなモデルで、製品IPへの適用実績ではありません。末尾に、このコードで実施した動作確認とその限界を記録します。

## 1. 何をフォーマル検証で確認するか

フォーマル検証では、モデルが許す入力と状態遷移について、記述した性質を調べます。証明の結論には、モデル・仮定・初期状態・構成の条件が付いています。「全入力を検証した」と報告するときも、仮定で許された入力と、証明で扱った動作の範囲を明記します。

| 方式 | 問うこと | 記録する範囲 |
| --- | --- | --- |
| プロパティ検証（FPV） | 要求から導いたassertが成り立つか | 対象要求、性質、仮定、初期状態、モデル |
| 到達性の確認 | 必要な状態・事象列へ至る経路があるか | coverの目標、到達トレース、探索範囲 |
| 等価性検証 | 変更前後やRTLとネットリストが対応するか | 比較元と比較先、対応点、初期化・モード・Xの扱い |

等価性の合格だけで、比較元の仕様への適合まで保証したとは扱いません。合成・ECOなどで振る舞いを維持したことと、要求自体が正しく実装されたことを分けます。[EQYの公式資料](https://yosyshq.readthedocs.io/projects/eqy/en/latest/)も等価性検証の参照先です。

最初の対象には、レジスタの更新優先順位、FIFOの境界、仲裁の排他、要求と応答の対応、例外・リセット復帰など、状態と期待する振る舞いを小さく定義できるものを選びます。データ幅、メモリ、長い履歴などで証明が難しくなる場合は、分割と抽象化を計画します。未完了の対象は、重要度と代替検証を記録して残します。

UVMやランダム検証との分担は要求ごとに決めます。制御の不変条件を形式的に証明し、実際のバス・ソフトウェア・複数IPの長いシナリオをシミュレーションで確認するなど、各方式が何を担うかを要求台帳に対応付けます。形式検証用のharnessへUVMのtest・sequenceをそのまま入力できるとは扱いません。

## 2. 要求から証明計画を作る

要求を、少なくとも次の性質へ分けます。

- **安全性（safety）**：起きてはいけないこと。排他違反、データの消失・重複、不正な状態更新など。有限の反例で違反を示せます。
- **期限付きの応答**：受理後Nサイクル以内の完了など。期限の監視を含め、安全性として扱えます。受理条件と、リセット・取消時の扱いも仕様から決めます。
- **活性（liveness）**：期限を置かず、いつか完了すること。有限深さで無失敗だったことでは証明できません。無限の待機経路、fairness、クロック・相手側の進行の前提を扱う方式が必要です。
- **到達目標**：リセット解除、前件、境界、同時動作、異常後の復帰など。assertと組にして、検査対象の条件が実際に可能かを調べます。

「相手側がいつかreadyを返す」という環境の公平性と、「DUTがいつか応答する」という保証を区別します。後者をそのままassumeして同じ性質を証明しません。また、「いつか」と「Nサイクル以内」は別の要求なので、都合のよい期限やfairnessを追加して置き換えません。

各証明項目には、要求ID・改訂、構成・パラメータ、トップ・適用インスタンス、assert・coverのラベル、クロック、受理・完了・取消条件、assume一覧、初期状態、抽象化、使用方式、完了基準を持たせます。要求の全条件がどの項目で検査されるかをレビューします。1個の大きなassertだけにまとめず、リセット値、通常動作、競合、保持、通知などを個別に診断できるようにします。

## 3. 環境の仮定と初期状態を管理する

### 3.1 assumeには出典と満たす側を付ける

仮定台帳には、ID、式、対象信号、適用期間、仕様の出典、必要な理由、満たす側、統合時の確認方法、レビュー担当を記録します。たとえばバスの送信側が満たすプロトコルは、IP単体では仮定にできますが、SoCでは接続先が守ることを別に確認します。IP単体の証明が、統合時の前提確認を免除するわけではありません。

次を混同しないようにします。

- 仕様上の合法入力を定める制約。
- 証明の分割境界で、別の証明結果を使う契約。
- ある動作モードだけを調べるための制限。この場合は残りのモードを別項目として残す。
- 探索を楽にするためだけの制約。合法な動作を消していない根拠が必要で、根拠がなければ全体の証明に使わない。

DUTの出力を常に正しい値に固定する、競合入力を禁止する、FIFOが満杯にならないと仮定する、といった指定で検査対象を消さないようにします。入力違反に対するエラー応答も要求なら、違反を避ける環境だけでは不足です。違反を含む別の計画を用意します。

### 3.2 リセットと履歴を明示する

電源投入時の状態、リセットがかかる前の状態、リセット後に到達できる状態は区別します。未初期化レジスタを、証明の都合で0に初期化しません。リセット後だけを保証する場合は、リセットを成立させる環境条件と、保証の開始点を明記します。

同期／非同期、極性、幅、解除条件、再アサート、部分・ウォームリセットを対象構成に対応付けます。初回のリセットを仮定しても、それ以降のリセットを自動で禁止しません。リセット中にassertを無効にする場合は、リセット値と解除後の振る舞いを別に検査します。

`$past`を使うときは、必要な履歴が存在することを管理します。最初のサイクルの履歴値を有効な観測として使いません。[YosysHQの形式検証構文](https://yosyshq.readthedocs.io/projects/sby/en/stable/verilog.html)では、assume・assert・coverと履歴関数の扱いを確認できます。

### 3.3 空成立と過剰な制約を調べる

同じ構成・仮定・初期状態で、リセット解除、assertの前件、必要な完了経路、境界・競合へのcoverを実行します。制約の矛盾、常時リセット、前件を禁止する仮定、結線ミスで条件が固定されていないかを調べます。仮定を段階的に外す比較も診断に使えます。

一部のcoverが到達するだけで、仮定が妥当とは判断しません。仮定ごとの出典と、合法な入力の種類・時間関係を除外していないかもレビューします。coverが指定深さで未到達だった場合も、その結果だけで仕様上の到達不能とは判断しません。

## 4. モデル、抽象化、証明の分割

### 4.1 モデルの読み込みを検査する

対象ソース・include・マクロ・パラメータ・トップ・ブラックボックス・クロックを保存し、エラボレーション後の階層とプロパティ一覧を確認します。checkerの適用漏れ、未駆動入力、定数化、assertの削除・無効化を検査します。プロパティ数が0の実行を成功として集計しません。SVAやbindの対応範囲は、使用するフロントエンドで確認します。

単一クロックの同期モデルを、非同期リセットや異なるクロックの任意の関係を扱う証明へ読み替えません。複数クロックでは位相・周波数・停止・再開と形式ステップの対応を定めます。2値のモデルで証明した結果と、X/Z・X伝搬を扱う検査も分けます。CDC/RDCの構造・プロトコル、メタスタビリティの物理評価は、一般化手順の14.2節と併せて計画します。

### 4.2 抽象化の向きと根拠を残す

安全性の証明には、実装の許される振る舞いをすべて含む抽象モデルを使う考え方があります。振る舞いを増やしたモデルでも性質が成立し、実装からの対応関係が確認できれば、結論を実装へつなげられます。一方、到達した抽象トレースは実装で再現できないことがあります。活性では、余分な待機経路やfairnessも含めて、性質を保存する根拠が必要です。

メモリを小さくする、カウンタ幅を減らす、データ経路を置き換える、といった変更は自動で妥当とは扱いません。たとえば任意のsymbolic addressでメモリを代表させるなら、読書きの対応、同一アドレスの競合、データ整合性を保つ仕組みと一般化の根拠を記録します。

ブラックボックスの出力を任意値にする場合も、独立性や時間的な関係の扱いを確認します。固定値に置き換えて振る舞いを減らした結果は、その限定範囲の結果として扱います。抽象モデルで未到達でも、モデルが実装の必要な振る舞いを含むと確認できなければ、実装の到達不能の根拠にはできません。

### 4.3 assume-guaranteeの責務を閉じる

分割点（cutpoint）で内部信号を任意入力に変えると、実装では到達しない組み合わせも生まれます。そこで必要な関係を仮定する場合は、その関係を元の実装で証明する別項目を登録します。補助不変条件（invariant）も、初期状態で成立し、遷移で保存される根拠を持たせます。

各分割には、仮定A、保証G、Aを満たす証明のID・版、統合先を記録します。「Aの証明にGを仮定し、Gの証明にAを仮定する」という循環を、根拠なしに閉じません。依存する証明が未完了・古い版なら、上位の結果も未完了として扱います。SBYで複数taskを記述しただけでは、こうした証明依存関係の完了は管理されません。台帳やランナー側で照合します。

## 5. 実行方式と結果を読み分ける

| 結果・方式 | 判断できること | 追加で確認すること |
| --- | --- | --- |
| BMCで反例なし | 初期条件から指定した有限深さまで違反が見つからない | 深さより先の安全性は未証明 |
| k-inductionの証明完了 | ベースケースと帰納段階が成立した性質 | 帰納法の深さ、補助不変条件、仮定の有効範囲 |
| PDR/IC3などによる証明完了 | モデル・仮定の下で対象の安全性が成立する | エンジンの最終判定、対象プロパティ、証明範囲 |
| cover到達 | 目標へ至る具体的な経路がある | 実装との対応、目標の意味、assertの結果 |
| cover未到達 | その実行では経路を得ていない | 有限探索の未達か、到達不能を証明したか |
| 反例・FAIL | 対象モデルに違反の候補がある | 到達可能な実装反例か、抽象化・帰納段階の候補か |
| unknown・timeout・error・中断 | 証明が完了していない | 理由、探索済みの範囲、次の処置 |

帰納段階だけの失敗は、リセットから到達しない状態を起点にしている場合があります。ベースケースの反例と区別し、不変条件の不足や分割の境界を調べます。到達可能な不具合をassumeで消して、証明を通す処置は取りません。

SBYの`bmc`・`prove`・`cover`では、同じPASSでも意味が異なります。`prove`でk-inductionが完了した場合、`depth`は証明探索の設定であり、「その深さまでだけの保証」ではありません。逆に、`bmc`の深さを大きくしただけで非有界の証明にはなりません。[SBYの設定形式](https://yosyshq.readthedocs.io/projects/sby/en/stable/reference.html)

ランナーではtask・mode・個々のプロパティの最終状態を確認します。期待結果をFAILなどに変えられるツールでは、プロセス終了コード0だけで証明済みにしません。複数エンジンや部分実行の結果も、対象・入力・前提を照合してから採用します。

## 6. 反例を解析して検証資産へ戻す

1. 最初に失敗するラベル、時刻、前件、直前状態、入力、リセットを確認する。サンプリングや履歴の1サイクルのずれも調べる。
2. RTLの不具合、プロパティの誤り、環境の仮定の不足・誤り、抽象化による偽反例、設定・ツールの問題に分類する。仕様が決めていない場合は課題票へ戻す。
3. 初期状態からの到達経路を確認する。抽象化・帰納段階の候補は、そのまま製品の不具合と断定せず、具体化や追加探索で調べる。
4. 実装で合法な反例は入力と初期化手順を保存し、必要に応じて直接テストへ変換してシミュレーションでも再現する。仕様の期待値を独立に確認する。
5. 修正後は元の証明、関係するcover、依存する証明、シミュレーション回帰を再実行する。反例のケースだけの合格で閉じない。

仮定の修正には仕様上の根拠を付け、除外される動作と別の検証項目への影響をレビューします。反例・到達トレースは、RTL・harness・仮定・ツールの版と一緒に保存します。

## 7. 割り込みの例：競合の証明と到達

[クロス検証](feature-interaction-verification.md)と[SVA](sva-verification.md)の説明に合わせ、次を仮の仕様とします。イベントでPENDをセット、W1Cクリアでクリアし、同時受理ではセットを優先します。操作がなければ保持し、IRQはPENDとIRQ_ENの論理積です。セット優先はこの例の仕様で、W1C一般の規則ではありません。

この例は**単一クロック・同期リセット・2値のモデル**です。最初の立ち上がりでリセットを仮定し、それ以降の入力とリセットは自由にします。PEND自体には初期値を与えず、`past_valid`だけを履歴管理のために初期化します。リセット前の出力保証、非同期リセット、バスによる受理、実際のCSR実装は範囲外です。

次を`irq_formal.sv`として保存します。説明を小さくするためRTLと検査を同じmoduleに置いていますが、製品への適用では対象RTLへ接続したharnessを用意し、仕様から導いたプロパティを独立にレビューします。

```systemverilog
module irq_formal (
  input wire clk, rst_n, event_accept, clear_accept, irq_en
);
  reg pend;
  wire irq = pend && irq_en;
  always @(posedge clk) begin
    if (!rst_n) pend <= 1'b0;
    else if (event_accept) pend <= 1'b1;
    else if (clear_accept) pend <= 1'b0;
  end

  reg past_valid = 1'b0;
  always @(posedge clk) begin
    past_valid <= 1'b1;
    if (!past_valid) as_initial_reset: assume (!rst_n);
    if (past_valid) begin
      if (!$past(rst_n)) ap_reset: assert (!pend);
      else begin
        if ($past(event_accept && clear_accept))
          ap_set_wins: assert (pend);
        if ($past(event_accept && !clear_accept))
          ap_set_only: assert (pend);
        if ($past(!event_accept && clear_accept))
          ap_clear_only: assert (!pend);
        if ($past(!event_accept && !clear_accept))
          ap_hold: assert (pend == $past(pend));
      end
      ap_irq: assert (irq == (pend && irq_en));
      cp_release: cover (rst_n);
      cp_collision: cover (rst_n && event_accept && clear_accept);
      cp_collision_result: cover ($past(rst_n && event_accept && clear_accept) && pend);
    end
  end
endmodule
```

立ち上がりで観測したPENDを、前の立ち上がりで受理した操作と比較します。現在リセットが有効でも、直前の操作結果は検査し、リセットによる更新は次の観測で`ap_reset`が検査します。すべての検査をリセット中に無効にする方式とは区別します。`ap_irq`はこの小さなモデルでは配線式の照合であり、製品の通知経路まで確認した証跡にはなりません。

同じディレクトリへ次を`irq.sby`として保存します。SBY・Yosys・yosys-smtbmc・Z3が利用可能な環境では、`sby irq.sby bmc`、`sby irq.sby prove`、`sby irq.sby cover`で別々に実行します。

```ini
[tasks]
bmc
prove
cover

[options]
bmc: mode bmc
prove: mode prove
cover: mode cover
depth 8

[engines]
smtbmc z3

[script]
read -formal irq_formal.sv
prep -top irq_formal

[files]
irq_formal.sv
```

この例はYosysの形式検証用immediate assertionと`$past`を使います。[SVAのchecker](sva-verification.md#5-例イベントとw1cの優先順位)のconcurrent assertionを、そのまま全フロントエンドで読めるとする例ではありません。

この3個のcoverはリセット解除・競合・結果への到達確認です。[クロス検証の12目標](feature-interaction-verification.md)や[covergroupの16目標](functional-coverage.md)を列挙して検査したものではありません。これらを形式検証で閉じるなら、各目標の初期PEND、IRQ_EN、前後の受理順序を表す履歴・coverを追加し、対応するassertの証明範囲と同じ仮定で確認します。

### 動作確認の範囲

2026-10-25に上記2個のコードブロックを一時ディレクトリへ保存し、YoWASP版Yosys 0.70（`28ba3cb92`、パッケージ`yowasp-yosys==0.70.0.0.post1259`）と同梱SBY・smtbmc、Z3 5.3.1で実行しました。SBYの版表示は`unknown SBY version`だったため、使用パッケージの版を記録しています。通常例では次を確認しました。

- `bmc`：深さ8で反例なし。
- `prove`：ベースケースと帰納段階が成立し、6個のassertを含むモデルの非有界の証明がPASS。
- `cover`：3個の目標に到達し、トレースを生成。

さらに一時コピーで、クリアを優先する誤実装、競合を禁止する仮定、常時リセットの仮定を試しました。結果は後述の点検に使います。製品IP、複数クロック、X/Z、活性、抽象化・分割の妥当性を実証したものではありません。

YoWASPを使う場合の同等の実行コマンドは次です。通常のネイティブ版ツールでの動作確認は行っていません。

```sh
uv tool run --from yowasp-yosys==0.70.0.0.post1259 yowasp-sby \
  --yosys yowasp-yosys --smtbmc yowasp-yosys-smtbmc \
  --witness yowasp-yosys-witness --sequential irq.sby
```

## 8. 証明の抜けと検査の感度を点検する

プロパティを全部証明しても、記述していない要求の正しさまでは保証しません。要求との双方向の対応、状態・データ・通知の観測点、各構成の適用をレビューします。ツールが提供するcone of influenceや証明カバレッジも診断に使えますが、ツール独自の率を仕様の要求網羅率へ読み替えません。

小さな故障注入で、証明が意図した不具合に反応するかも確認します。上記の例では次の結果でした。

- **クリア優先へ変更**：BMCで`ap_set_wins`の反例を得て、`prove`もFAIL。競合の誤りを検出した。
- **その誤実装に、同時イベントとクリアを禁止するassumeを追加**：BMCと`prove`はPASSになったが、競合と結果のcoverは深さ8で未到達となり、`cover` taskはFAIL。これは合格すべきモデルではなく、必要な競合を仮定で消した例。
- **正しいモデルを常時リセットに制限**：`prove`はPASSだが、3個のcoverがすべて深さ8で未到達となり、`cover` taskはFAIL。リセット解除後の要求を検査した証跡にはしない。

いずれも、coverの有限深さでの未達を、ツールが非有界に到達不能を証明したという報告にはしていません。これらの例では追加した仮定の式から除外の理由を確認できます。実際の検証では、未到達を理由に目標を削除せず、仮定・モデル・目標のどこに原因があるかを調べます。

機能カバレッジの穴を形式検証で調べる場合は、元のbin・cross・サンプリング条件を到達目標へ対応付けます。到達トレースは直接テストやランダムの誘導に使えますが、トレースが得られただけで、別のシミュレーションのcovergroup DBを合格扱いにはしません。到達不能として除外するには、使用したモデルと前提が実際の適用範囲を含む根拠とレビューが必要です。

## 10. 完了判定

要求・構成ごとに、少なくとも次を確認します。

1. 必要な性質と到達目標が要求の全条件に対応し、checkerの適用・有効化が確認されている。
2. 仮定、初期状態、クロック・リセット、モデル、抽象化と分割の根拠がレビューされ、統合先が満たす前提の確認方法もある。
3. 計画した方式で必要な証明が完了している。非有界の証明が必要な項目をBMCの無反例で代用していない。
4. 必須の前件・経路・境界が同じ前提で到達するか、未達・到達不能・対象外の根拠が個別に確認されている。
5. 補助不変条件と依存する証明が同じ適用範囲で有効であり、循環・未完了・古い結果が残っていない。
6. 反例、unknown、timeout、error、未実行を合格へ足していない。未完了は残リスク、代替検証、担当・期限へつながっている。
7. 最終版の証跡があり、必要なシミュレーションや他の解析との分担も満たしている。

報告は「証明済みの件数」だけでなく、対象要求・構成、証明方式、仮定・境界、有限探索のみ、失敗、未実行、判定不能の内訳を示します。プロパティ数の割合と、要求の合格率は別に集計します。例外承認は技術的な証明完了と分け、[サインオフ記録](../templates/signoff-record.md)へつなぎます。
