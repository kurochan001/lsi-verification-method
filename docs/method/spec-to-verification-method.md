# ロジック半導体の仕様書から検証パターンを作る手順

この文書は、[IEEE 1800-2023のPDFから要求を抽出し、テストで検証する手順](../case-study-ieee1800/requirements-to-tests-method.md)を、ロジック半導体の仕様書（製品仕様、IP仕様、レジスタマップ、プロトコル仕様）から検証パターンを作る方法として一般化したものです。
元の手順を規格のテストスイートで実際に使った結果（要求の全抽出、照合、新規テスト、独立検証、計測）を下敷きにしています。半導体の仕様書に適用した実績はまだありません。
このリポジトリで、製品開発の確認項目と計測・判定の規則を追記しています。派生元と追記の範囲は[由来](../../PROVENANCE.md)に記録しています。

対象と対象外：

- **対象**：論理機能の検証です。プレシリコンのRTL検証と、ポストシリコン検証のうち機能を確かめる部分を含みます。指定した負荷・構成での応答サイクル数やタイムアウトも対象です。
- **対象外**：電気的特性（AC/DC、セットアップ・ホールド、電圧・電力の定量評価）。これらはSTA、特性評価、ATEの領域です。量産テストのATPGパターン（ネットリストの故障モデルから作る）も、この手順の要求カバレッジの対象ではありません。ただし、製品開発ではこれらを省略せず、14節の項目として別に管理します。

## 1. 原則

- **期待値は仕様から先に決める。** RTLやシミュレータの出力を期待値に写しません。期待値は、仕様から作った参照モデルか、仕様から直接導いた値です。
- **観測できる形で要求を書く。** 1つの要求には、それが正しいかを判定できる観測点（ポート、レジスタ、割り込み、トランザクション、内部信号へのアサーション）を必ず決めます。
- **誤実装で結果が変わる検査だけを証拠にする。** 「その動作を誤って実装したら、どの観測がどう変わるか」に具体的に答えられない検査は、要求の証拠にしません。
- **作った者と確かめる者を分ける。** 検証パターンと要求との対応は、作成者とは別の検証者が反証を試み、合格したものだけを台帳に取り込みます。不確かなものは却下します。
- **証跡は版に紐づける。** 合格の記録には、要求の改訂、設計と検証環境の入力、構成、ツールの版、実行条件を記録します。どの条件で得た結果かを追跡でき、評価対象と整合する証跡だけを使います（9.6）。
- **仕様の本文を複製しない。** 台帳やテストには要求を自分の言葉で書き、仕様の版と段落を引用します。仕様が機密の場合、AIを使える環境と範囲を最初に決めます。
- **数値を守るより正しい集計を優先する。** 誤りが分かった対応は取り下げ、理由を残します。

| 元の手順（IEEE 1800-2023） | 一般化した手順 |

| 要求台帳（`behaviors.json`） | 要求台帳（JSON／YAML／要求管理ツール） |

| テストの`:lrm:`による節の引用 | テストやチェッカー、カバレッジ項目に付けた要求ID |
| 期待出力ファイル | 参照モデル、スコアボード、アサーション、機能カバレッジ |
| Icarus 13.0とVerilator 5.052の照合（`:oracle:`） | 参照モデル、複数のシミュレータ、形式検証、FPGAプロトタイプの突き合わせ |
| ヘッダ定数・予約語の生成テスト | レジスタマップ、オペコード表、ピン多重化表、エラーコード表からの生成テスト |
| 解釈保留 | 仕様の曖昧さ・矛盾の課題票。作成者に確認できる |
| 入力ハッシュとランナーのハッシュ | テストの入力、RTLのコミット、ツールの版、seed |
| 暫定設計網羅率・実行確認率 | 要求カバレッジ（対応率・合格率）。構成・重要度・種別ごとにも分ける |

## 3. 全体の流れ

```text
仕様書 ─> A. 取り込み（版・段落ID・ハッシュ）
            │
            v
          B. 要求の抽出（観測点つきの最小単位）──> C. 曖昧さの課題票 ──> 仕様の作成者
            │
            ├─> D. 既存の検証資産との照合 ──┐
            └─> E. 検証パターンの作成 ──────┴─> F. 独立した検証 ─> G. 統合・回帰・計測
```

## 4. 準備

### 4.1 入力物

| 入力 | 扱い |
| --- | --- |
| 製品仕様・IP仕様 | 版と改訂履歴を固定する。段落に安定したIDを振る |
| レジスタマップ | 機械可読な原本（IP-XACT、SystemRDL、表計算）を優先する。PDFの表より誤読が少ない |
| プロトコル仕様（標準・社内） | 版を固定する。コンプライアンス要求と任意機能を区別する |
| タイミング図・状態遷移図 | 図ごとにIDを振り、テキスト化した要点と対応させる |
| エラッタ・設計判断の記録 | 仕様と同じく出典として扱う |
| RTL、テストベンチ、既存のテスト・アサーション・カバレッジ | 照合の対象。コミットを固定する |

### 4.2 道具

- 2つ以上の独立した確認先：参照モデル（C、Python、SystemC）、複数のシミュレータ、形式検証ツールなど。
- 要求台帳と照合案を検査する仕組み：元の手順の[照合キット](../../tools/matching_kit/README.md)と同じ役割で、要求ID、観測点、証跡の実在を機械的に検査します。
- 回帰の結果を、RTLのコミット、テストの入力のハッシュ、ツールの版、seedとともに保存する仕組み。

### 4.3 要求台帳の形式

1行の要求に、少なくとも次の項目を持たせます（付録Aに例があります）。

| 項目 | 内容 |
| --- | --- |
| `id` / `revision` | 安定したIDと要求の改訂。受入条件を変えたら改訂を進め、分割・統合は旧IDとの関係を残す |
| `source` | 仕様の名前・版・節・段落（図表ID） |
| `kind` | 機能／違法入力／境界／リセット・初期化／構成／タイミング／性能 |
| `priority` | 開発上の優先度。安全上の分類がある場合は別項目で管理し、数値の重みに読み替えない |
| `behavior` / `acceptance` | 要求と、観測可能な合格基準 |
| `observation_point` | どこで何を観測するか |
| `configuration` | 前提とする構成・パラメータ・製品バリアント |
| `issue` | 未解決の曖昧さ（あれば対応承認を禁止する） |
| `checks` | 対応する検証資産と証跡（空なら未対応） |

### 4.4 検証計画と完了条件

作成を始める前に、対象の仕様・設計の版、必須の構成と動作モード、要求ごとの検証方式、担当者、結果を承認する者を決めます。要求の対応率・合格率と、コード・機能カバレッジの目標は、対象と除外規則を含めて固定します。必須要求の未達を、多数の軽微な要求の合格で埋め合わせません。

完了には、必要な刺激への到達、チェッカーによる判定、必要な構成での合格証跡をそろえます。未解決の不具合・仕様課題・未実行項目と、承認済みの例外を分けて残します。14節の製品開発上の判定とも関連付けます。[サインオフ記録の雛形](../templates/signoff-record.md)を使って、開始時点から記録できます。

検証方式の選定に加え、静的検査、リセット・X伝搬、CDC/RDC、転送、異常・復帰、性能、低電力、セキュリティ、実装・統合などの領域が計画から漏れていないかを確認します。[領域別の点検手順](verification-gap-review.md)と[適用範囲の記録](../templates/verification-scope.md)を使い、必須構成ごとの適用・対象外・未確定、担当、必要な段階、証跡を対応付けます。

## 5. 段階A：仕様の取り込み

1. 仕様書の版を固定し、ファイルのハッシュを記録します。
2. 節・段落・図表に安定したIDを振り、各段落のハッシュを記録します。本文は台帳に入れません。
3. 全段落を、「要求」「説明」「例」「参照」「見出し」のどれかに分類します。「要求」の段落は、どの要求行に対応するかを記録し、要求行の側からも段落を指します。この双方向の対応で、未分類の段落や対応先のない要求を機械的に検出します。分類自体の誤りや、一段落から一部だけを抽出した漏れは、原文とのレビューで確かめます。
4. 仕様が改訂されたら、追加・削除・ハッシュの変わった段落を起点に、参照先・参照元、共通の定義、図表、レジスタ別名などへ影響をたどります。本文が変わらない要求でも、参照する定義が変われば再確認します。要求・チェック・期待値・構成・証跡の再評価範囲を記録し、影響を受けた古い承認と成功証跡を有効な集計から外します。

仕様の種類ごとの注意：

- **レジスタマップ**：フィールド（オフセット、幅、リセット値、アクセス種別、予約ビットの扱い）を1行ずつ要求にします。機械可読な原本から抽出し、PDFとの食い違いは課題にします。
- **プロトコル仕様**：トランザクションの種類、ハンドシェイクの規則、順序の規則、エラー応答、タイムアウトを分けます。「してもよい」（任意機能）と「しなければならない」を区別します。
- **社内IP仕様**：マイクロアーキテクチャの記述（実装の説明）と、外から観測できる振る舞いの要求を分けます。前者は検証の対象にしないか、内部アサーションの対象として別に扱います。

## 6. 段階B：要求の抽出

### 6.1 単位

1行は「前提条件、起こす事象、観測可能な合格基準」がそろった1つの義務です。独立に合否を判定できる義務は分けます。条件と結果の関係が失われるほど細かくは分けません。

### 6.2 書き方の規則

元の手順で、台帳を見直したときに分かったことを一般化した規則です。

- **観測できる形で書く。** 例：仕様が予約ビットを「書き込み無視・読み出し0」と定めるなら、書き込み後の読み出し0と、他フィールドへの影響がないことをそれぞれ確かめます。予約ビットの値や応答を、仕様に根拠なく決めません。
- **正常系と違法系を1行に混ぜない。** 「Xは受理され、Yはエラー応答になる」は2行に分けます。
- **仕様が許す幅を明記する。** レイテンシの範囲、応答の順序の自由、アービトレーションの方式などです。単一の値を期待値にしてよいのは、仕様が決めている場合だけです。
- **構成・実装依存の前提を受入条件で固定する。** 例：「FIFOの深さ=Nの構成で」「バースト長の上限が設定されている場合」。
- **使い方の規則（ソフトウェアやシステム側の義務）と、デバイスの振る舞いを分ける。** 例：「ソフトウェアは初期化完了まで書いてはならない」は、デバイスの要求ではありません。
- **既存の要求と意味が重なる行を増やさない。** 同じ要求が複数の節に現れる場合は、1行にまとめて出典を複数持たせます。
- **リセット直後と初期化の要求を忘れない。** リセット値、リセット中の出力、リセット解除後の最初の動作です。
- **機能同士の関係も要求にする。** 共有状態・資源、優先順位、同時動作、順序、中断・復帰を洗い出します。関係する単体要求と出典を結び付け、組み合わせた場合の規則が未定義なら仕様課題にします（9.8）。

## 7. 段階C：曖昧さの管理

- 仕様の中で整合しない記述、未定義の場合、図と文章の食い違いは課題票にし、該当する要求行に`issue`を付けます。課題が解消するまで、その行に検証資産を対応付けません。
- 解消の根拠は次のいずれかにします。
  - 仕様の作成者の回答
  - 設計判断の記録
  - 仕様の内部にある決定的な根拠（機械可読なレジスタ定義、構文・表の定義など）
- 根拠が推測にとどまるものは解消扱いにしません。
- 解消したら、要求文を採用した解釈で書き直し、根拠を記録します。仕様の改訂やエラッタに反映されたかも追います。
- 社内仕様では、作成者への確認と、回答を仕様・エラッタへ反映する経路を設けます。回答の適用範囲と版を記録し、口頭の回答だけで関係する要求を一律に確定しません。課題票を、仕様の品質の指標としても使えます。

## 8. 段階D：既存の検証資産との照合

### 8.1 照合の対象

既存のテスト、チェッカー（スコアボード）、アサーション、機能カバレッジ項目、形式検証のプロパティを、要求に対応付けます。

### 8.2 基準

1. 要求の`behavior`・`acceptance`と、仕様の該当段落・図表を読む。
2. 検証資産の刺激、チェッカーの比較内容、アサーションの式、カバレッジの定義まで読む。
3. 次の場合だけ対応を登録する。
   - 要求の全条件を、その資産が実際に起こし、観測している。
   - 要求に反する実装なら、比較・アサーションなどの合否が変わる。どの誤りをどの判定が捉えるかを説明できる。
4. 次のものは証拠にしません。
   - テスト名や説明文だけ
   - 信号が動いたことだけ
   - 常に成立するアサーション、空成立しかしないアサーション（前提が一度も成立しない含意など）
   - 真になる入力しかない比較
   - 個数だけを見て、対象の同一性を見ない検査
   - 仕様が順序を決めないことに依存する比較
5. 1つの資産が条件の一部しか見ない場合は、全条件を複数の資産で分担できるならAND集合にします。そうでなければ保留として理由を記録します。
6. 証跡には、刺激の位置（テスト・シーケンスの該当箇所）と、判定の位置（チェッカーの比較、アサーション名、カバレッジ項目名）を、文字列や識別子で残します。

機能カバレッジや`cover`は、必要な事象を観測した証拠です。それだけで応答の正しさを合格にしません。チェッカーまたはアサーションと関連付け、両方の結果を確かめます。カバレッジはドライバの送信予定ではなく、モニタが観測した転送・状態を基に採取します（付録CのUVM資料）。

### 8.3 実績からの目安

元の手順では、既存テストの照合で採用されたのは、未対応の要求の約6〜15%でした。主な理由は、要求の条件を刺激する既存テストがそもそも無いことです。
照合は最初に安く済ませ、残りは新しい検証パターンで埋める計画にします。

## 9. 段階E：検証パターンの作成

### 9.1 方式の選び方

| 要求の性質 | 方式 |
| --- | --- |
| 表で列挙される値（レジスタのリセット値・アクセス種別、オペコード、エラーコード、ピン多重化） | 生成器で網羅する（9.4） |
| 特定の手順で起きる動作（初期化手順、特定のシーケンス、エラー回復） | 直接テスト |
| 組み合わせが多い動作（データ幅、バースト、並行トランザクション） | 制約付きランダムと、要求IDに結びつけた機能カバレッジ |
| 常に成り立つ性質（ハンドシェイクの規則、排他、FIFOのオーバーフローなし） | SVAアサーション。可能なら形式検証で証明する |
| 違法入力への応答（不正アドレス、プロトコル違反、予約値の書き込み） | 直接テストと、応答を確かめるチェッカー |
| タイミング（サイクル数、タイムアウト） | 許容範囲を持つチェッカーとアサーション |
| リセット・初期化、Xの流出、異常・復帰 | 動作中の状態を狙う直接・ランダム試験、必要な4値／X伝搬検査、故障注入と復帰の判定（9.13） |
| クロック・リセット・電源の境界 | CDC/RDC・電源構造の解析と、停止・解除・復帰時の機能検証。必要なpower-awareモデルを使う（9.13） |
| 帯域・遅延・仲裁・進行性 | 負荷条件と測定窓を固定した試験。必要に応じて形式検証で進行性を確認する（9.12〜9.13） |

### 9.2 参照モデル

- 仕様だけから作り、RTLを見て作らないようにします。参照モデルの作成者と、RTLの作成者を分けます。
- 参照モデル自体もレビューの対象です。仕様の段落への追跡を持たせます。
- サイクル精度が要らない要求は、トランザクションレベルで抽象化します。
- 複数の参照実装やシミュレータの一致を裏付けとして数えるときは、構成要素（フロントエンド、ライブラリ、生成元のモデル）を共有していないかを確かめます。共有していれば、その部分についての一致は独立した裏付けになりません。元の手順では、比較に加えた2つのシミュレータが同じフロントエンドを使っており、演算子の優先順位などで同じ誤りをしていました。

### 9.3 チェッカーと期待値

- 仕様が許す幅（レイテンシ、順序）を受け入れます。
- X（論理不定値）、リセット中、構成による違いの扱いを明示します。4値動作を判定する要求は、2値シミュレーションだけでは合格にしません。論理不定値と、仕様が動作を規定しない場合を区別します。
- テスト終了時には、比較が実際に行われた件数、未応答の要求、スコアボードに残った未照合項目も確認します。チェッカーの無効化、早期終了、タイムアウトを合格として扱いません。
- 期待値を先に書き、シミュレーションで確かめます。食い違いは、まず仕様と期待値を確かめ直し、それでもRTL側の誤りならバグとして記録します。期待値をRTLの出力に合わせて直すことはしません。

違法入力のテストは、仕様がデバイスに要求するエラー応答・無視・復帰などを判定します。仕様が入力を禁じるだけで結果を定めていない場合、任意のエラー応答を期待しません。その入力を避けることは、システム側の前提として記録します。コンパイル時の診断を検証する元のケーススタディと、動作中のデバイス応答を検証する手順を区別します。

### 9.4 表形式の仕様は生成器で作る

元の手順で、ヘッダの定数や予約語を検証した方法の一般化です。

- 生成器の参照モデルは、仕様の表（機械可読な原本があればそれ）から作ります。表どうしの一致を、生成器の中で検査します（例：フィールド幅の合計がレジスタ幅と一致する、オフセットが重ならない、版ごとの追加分の和が全体と一致する）。
- レジスタでは、次を網羅します。
  - リセット値
  - アクセス種別ごとの書き込みと読み戻し（RW、RO、WO、W1C、W1S、RC）
  - 予約ビットの扱い
  - 未定義アドレスへのアクセスに対する応答
  - バイトイネーブル
- 違法系のケースも生成します（書き込み禁止のフィールドへの書き込み、範囲外のアドレス）。期待する応答（エラー応答、無視、割り込み）は仕様から決めます。
- 生成物の判定基準（期待値、エラー応答の位置）は、生成器が自動で決めます。手で直さないでください。
- RTLとチェッカーを同じレジスタ定義から生成する場合、両方が一致していても原本の誤りは検出できません。原本と仕様の照合を別担当で行い、アクセス副作用、同時アクセス、リセットとの競合は表の値の照合とは別に検証します。

### 9.5 構成とバリアント

- 要求と必須構成・動作モードの適用表を作り、構成ごとに回帰を回します。代表構成で代用する場合は、その範囲に同じ判定を適用できる根拠と承認を残します。
- 全要求の台帳は保持し、構成ごとに「適用」「対象外」「適用判断が未確定」を区別します。対象外は根拠と承認を残し、構成別の分母から除いた件数も表示します。未実装、未対応、未実行、解釈保留、適用判断が未確定の行を、対象外として除きません。
- 製品全体の要求を合格にするには、適用される必須構成のすべてで条件を満たす必要があります。たとえばFIFO深さ4と16が必須なら、深さ4だけの合格は製品全体の合格ではありません。構成を増やしたら分母と完了判定を再評価します。

### 9.6 再現性

要求の改訂、仕様・RTL・検証環境の版、入力ハッシュ、トップ、パラメータ、マクロ、参照モデル、チェッカー、制約、ランナー、ツールとライブラリの版を、実行IDに紐づけて記録します。シミュレーションにはseedと実行コマンド、実行時間・資源制限、終了理由を残します。seedが異なる実行も、条件を明示した別の証跡として保存します。

形式検証では、対象プロパティ、仮定、初期状態・リセット、抽象化、証明の境界、探索深さ、エンジン、結果を記録します。有限の深さまで反例がない結果と、仮定の下で全到達状態に成り立つことを示す非有界の証明を区別し、`cover`の到達を証明済みに読み替えません。過剰な仮定で必要な事象を除外していないかも確認します。`unknown`、タイムアウト、エラーは未完了です（付録CのSBY資料）。

### 9.7 UVMでの実装

UVM（Universal Verification Methodology）を使う場合は、要求の刺激をtest・sequenceに、観測をmonitorに、正しさの判定をscoreboard・アサーションに、到達の確認を機能カバレッジに対応付けます。sequenceを実行したことやbinの到達だけでは、要求の合格にはしません。

レジスタにはRALを使い、バス経由の検証、モデルの予測、実データとの比較を区別します。採用するUVMライブラリとVIPの版、構成・factory override、checkerの有効化設定も実行証跡に含めます。

構成、要求IDとの対応付け、RAL、UARTの適用例、テストの終了・回帰の合格条件は、[UVMで要求と検証資産を結び付ける](uvm-verification.md)にまとめています。これらは今後適用する運用案です。現行の照合キットには、UVM環境の構築や結果の取り込みを自動化する機能はありません。

### 9.8 機能間の相互作用とクロス検証

機能間の依存関係を表にし、共有する状態・資源、制御・データの依存、リセットや電源による中断から、必須の相互作用を選びます。機能Aと機能Bの単体合格だけで、同時動作や競合も確認済みにはしません。

各相互作用について、事前状態、実際の受理条件、順序・時間差・重なり、期待する状態・データ・通知、復帰条件を決めます。クロスの到達と、結果の正しさの判定を同じシナリオに結び付けます。重要な境界は直接狙い、必要に応じて3機能以上の組も確認します。pairwiseや瞬時のcovergroupのcrossだけでは、順序・中断や高次の相互作用の確認は完了しません。

洗い出し、組み合わせ数の絞り方、時間関係の観測、イベントとW1Cの競合を使った12目標の例、完了判定は、[機能間の相互作用とクロス検証](feature-interaction-verification.md)にまとめています。

### 9.9 制約付きランダム検証

ランダム検証は、仕様上の合法な入力・操作条件の下で、値・順序・タイミング・負荷を変えて探索する方式です。仕様の制約と、特定の状態を多く選ぶための探索方針を分け、難しい合法入力を制約で消さないようにレビューします。生成に成功した数だけでなく、DUTの実際の受理と、結果の比較まで確認します。

test・シナリオ・構成・seed・制約の版を持つ回帰計画を作り、失敗を再現できる環境と刺激を保存します。カバレッジの未達から制約・重み・シナリオを見直し、重要な境界や低頻度の競合は直接テストで補います。seed数や長時間の無失敗だけでは完了としません。

制約の層分け、生成失敗、seedと再現性、回帰の運用、失敗の縮小、割り込みの9実行の計画例は、[制約付きランダム検証の計画・実行・完了判定](constrained-random-verification.md)にまとめています。

### 9.10 SVAのアサーションとカバー

要求を、サンプリングするクロック、前件、期待する後件と期限、リセットなどの無効化条件へ落とします。assertで正しさを判定し、前件と必要な完了経路へのcoverで、意図した条件を検査できたかも確認します。assumeは環境の前提として管理し、DUTの保証事項を仮定へ移して検査を成立させません。

サンプリングとNBA更新、空成立、リセットによる中断、履歴不足、終了時の未完了、ツールの対応と有効化をレビューします。シミュレーションの無失敗、形式検証の有界検査・非有界の証明、coverの到達は、範囲と意味を分けて記録します。

具体的なassert・coverのchecker例と、UVM・クロス・ランダム検証への接続、完了条件は、[SVAのアサーションとカバーによる検証](sva-verification.md)にまとめています。

### 9.11 covergroupによる機能網羅

要求と機能一覧を、操作、状態、値と境界、遷移、応答、異常・復帰、構成ごとの観測目標へ展開します。coverpoint・bin・crossに要求IDとcheckerを結び付け、各要求がどの目標で観測されるかと、モデルに抜けがないかを双方向にレビューします。

実際に受理・完了した同じケースの情報を採取し、到達と結果の合格を対応付けます。個々のcoverpointの100%とcrossの網羅、型全体とインスタンスごとの網羅を分けて確認します。binの粒度、除外、必要ヒット数、重み、mergeで分母や意味が変わっていないかも管理します。

機能モデルの作り方、SVAのcoverとの分担、基本動作の16目標を分類するcollector例、集計と完了条件は、[covergroupで機能を体系的に網羅する](functional-coverage.md)にまとめています。

### 9.12 フォーマル検証

要求を安全性、期限付きの応答、活性、到達目標へ分け、対象構成・クロック・初期状態と証明方式を決めます。環境の仮定には出典と満たす側を記録し、必要な競合や異常を禁止して検査対象を消していないかを、レビューと同じ前提でのcoverで確認します。IP単体の仮定を、SoC統合時に満たすことの確認も計画します。

抽象化が保存する性質と適用範囲を明示し、分割した証明の仮定・保証・補助不変条件の依存関係を管理します。有界検査の無反例、非有界の証明、cover到達、帰納段階の候補反例、unknown・timeoutなどを分けて報告します。等価性の合格を、比較元の仕様適合の証明へ読み替えません。

仮定・初期状態の点検、モデル・抽象化、assume-guarantee、反例解析、割り込みの証明例と完了判定は、[フォーマル検証の計画・証明・完了判定](formal-verification.md)にまとめています。

### 9.13 検証領域の抜けを試験へ展開する

通常機能の合格に加え、初期化・中断・復帰、転送内容と順序、待ち・飽和・進行性、故障・権限違反、クロック・電源境界を確認します。領域ごとに、刺激・事前状態・受理と完了・観測点・checker・期限や閾値を仕様から決め、静的解析・シミュレーション・形式検証・実測の分担を付けます。

機能目標からの点検と、コードカバレッジの未達からの点検を併用します。未達を刺激不足・モデル不足・RTLの問題・根拠付きの対象外や到達不能へ分類し、除外で必要な異常・保護経路を隠さないようにします。構成・接続・ソフトウェアや実装変更後の等価性と統合試験にもつなぎます。

領域別の具体的な試験・合格条件と、割り込みの追加試験案は、[検証計画の抜けを点検し、試験へ展開する](verification-gap-review.md)にまとめています。[適用範囲の雛形](../templates/verification-scope.md)から要求・計画・証跡へ追跡します。製品の専門解析と判定段階は14節に従います。

## 10. 段階F：独立した検証

- **パターンの判定**：検証者は、期待値（参照モデルの出力、チェッカーの判定基準）を仕様から自分で導いて照合します。合法な刺激か（仕様が禁じる使い方をしていないか）、決定性があるか、構成の前提が正しいかも確かめます。期待値が仕様から導けないパターンは欠陥です。
- **照合の判定**：刺激が要求の全条件を起こし、判定が誤実装と区別できる場合だけ採用します。不確かなら却下します。
- **形式検証の判定**：プロパティが要求を表すか、仮定が合法な動作を消していないか、初期状態・抽象化・分割の根拠と依存する証明が有効かを確認します。到達可能な反例と帰納段階・抽象化の候補を区別し、有限深さの無反例やcover到達を非有界の証明へ読み替えません。
- **ミューテーション検証（意図的な誤実装の注入）**：元の設計が合格することを確認してから、RTLの演算子・定数・条件を1か所ずつ誤らせ、意図したチェッカーやアサーションが検出するかを確かめます。未検出、根拠付きの等価変異、適用外、コンパイル不能、タイムアウト・実行エラーを区別します。未検出を直ちに等価と扱わず、刺激不足、到達性、仮定、判定の弱さを調べます。検出率には集計対象と各分類の件数を添えます。安全機構自体の検出・復帰を評価する故障注入とは目的・分母・合格条件を分けます。具体的な手順は[ミューテーション検証](mutation-verification.md)にまとめています。
- **大量の機械的な案**：独立に抽出した値（例：レジスタマップの機械可読な原本と、PDFの表を別の方法で読んだもの）との照合結果に基づいて、まとめて判定してよいことにします。
- **横展開**：検証者がある種類の欠陥を見つけたら、採用済みの全件を同じ観点で点検します。元の手順では、ある宣言の誤りで欠陥とされた3本をもとに点検し、採用済みの1本と既存の7本に同じ誤りが見つかりました。

元の手順の実績では、独立検証で新規テスト624本のうち30本（約5%）が欠陥、照合案2,215件のうち166件（約7%）が却下でした。
欠陥のうち、期待値そのものの誤りは4本だけでした。多くは、仕様が決めない値を期待値に含めたもの、刺激の合法性、違反を検出する位置、メタデータの誤りです。
検証担当には、期待値の再計算だけでなく、これらを確かめさせます。

ここでのRTL変異の検出率は、検証資産の感度を評価する指標です。物理故障モデルによるATPGの故障網羅率や、安全機構の診断網羅率へそのまま読み替えません。

元の手順の検証で実際に見つかった穴を、一般化したチェックリストです。

| 穴 | 対策 |
| --- | --- |
| 型や幅を落とした比較（切り詰め、符号の見落とし）で誤りが隠れる | 全幅で比較し、範囲外の値は検出する |
| 条件の片側だけを刺激している（真だけ、増える場合だけ、片方の向きだけ） | 対照のケースを足す |
| 個数だけを比べ、どの要素かを確かめていない | 対象の識別子・値で照合する |
| 未定義の名前や値が既定値として扱われ、検査が素通りする | 定義されていることも確かめる |
| 規格・仕様が決めないもの（順序、処理系依存の幅、名前の付け方）に依存している | 許容範囲で判定するか、観測しない |
| 違反を検出するパターンで、診断の位置や理由が違反と一致するかを見ていない（別の理由による拒否も合格になる） | 診断の位置と理由を照合し、別の理由による拒否は証跡に数えない |
| 違反を入れたパターンに、意図しない別の違反が重なる | 違反は1つにし、それを除いた入力が合法であることを確かめる |
| パターンに付けた注記（コメント、目印）が、それ自体で仕様違反になる | 注記を置ける場所を仕様で確かめる |
| 言語や仕様の暗黙の既定（宣言の種類、リセット値、予約フィールドの扱い）のせいで、刺激そのものが不正になる | 既定に頼らず明示する |
| メタデータ（4値への依存、非決定性、対象の構成）が実態と食い違い、実行環境や判定方法の選択を誤る | メタデータを実態から機械的に検査する |
| 空成立しかしないアサーション | 前提が成立したことをカバレッジで確かめる |
| 未定義動作・処理系依存に頼る検査 | 対応付けを見送る |
| 構造（共用体、ガード、レジスタの重なり）を見ていない | 構造そのものを観測する検査を足す |

## 11. 段階G：統合・回帰・計測

1. 欠陥ありのパターンと、判定のないパターンを取り除きます。
2. 採用された対応を台帳に統合します。要求の改訂、検証資産の版、観測点、レビューの判定を残し、実行証跡を9.6の入力一式に紐づけます。
3. 回帰を実行し、結果を版ごとに保存します。部分実行の結果は、全体の結果と合成しません。AND集合は、同じ実行回でメンバー全員が合格した場合だけ合格とします。
   回帰では、パターンごとに資源（メモリ、時間）を制限します。違反を入れたパターンが検証ツールを暴走させ、回帰全体を止めることがあります。元の手順では、違法な設計の1本でシミュレータが再帰を止めず、実行環境のメモリ（16GB）を使い切って、その夜の回帰が止まりました。
4. 計測して報告します。

| 指標 | 意味 |
| --- | --- |
| 要求の対応率 | 構成別の対象要求のうち、全条件を判定する検証資産が対応付いた要求の割合（設計側） |
| 要求の合格率 | 同じ対象要求のうち、必要な実行条件を満たす有効な合格証跡がある要求の割合（実行側） |
| 機能間クロスの到達率・合格率 | 承認した必須目標のうち、同じシナリオで相互作用を観測できた数／結果の判定も合格した数を、それぞれ分母に対して示す |
| ランダム回帰の実行状況 | 計画の版・シナリオ・構成ごとの予定、合格、失敗、未実行、判定不能と、生成・受理・比較の件数を示す |
| SVAの評価・到達・証明状況 | 要求・構成・適用先ごとに、assertの失敗、前件・完了経路のcover、中断・未完了、仮定と証明範囲を示す |
| covergroupの機能網羅 | 機能・要求・構成・適用先ごとに、必須bin・crossの到達／合格側の内訳、必要ヒット数、未達・除外を示す |
| フォーマル検証の完了状況 | 要求・構成ごとに、非有界の証明、有限深さのみ、反例、未実行、判定不能を示す。仮定・証明境界、依存する証明、必須coverの結果を添える |
| 検証領域別の状況 | 領域・構成・段階ごとの適用未確定、必須検査、未達・失敗・未実行・判定不能、静的指摘と例外を示す |
| コードカバレッジの未達 | 指標・階層・構成ごとの分子／分母、未達の原因、追加試験・RTL修正・除外の根拠と元の実行IDを示す |
| 性能・進行性の結果 | 構成・負荷・クロック・測定窓と閾値を添え、完了した帯域・遅延、要求元別の待ちと未解決数を示す |
| 重要度別の内訳 | 安全度・重要度ごとの対応率・合格率 |
| 未解決の課題 | 曖昧さの件数、解消までの日数 |
| ミューテーションの検出率 | 判定済みの非等価変異のうち検出できた割合。未完了を含む対象全体の検出済み割合と、等価・適用外・無効・未完了の件数・根拠も示す（[分類・集計](mutation-verification.md#5-検出率と未完了を集計する)） |

- 分母は、固定した台帳と9.5の適用表から求めます。分子・分母の実数、対象外と適用未確定の件数を併記し、分母0は「対象なし」と表示します。未対応・失敗・未実行・判定不能・古い証跡・解釈保留は成功に数えません。例外承認があっても、未達要求の状態を合格に変更しません。
- 全要求を同じ重みで数えると、表から機械的に生成した多数の行で値が大きく動きます。構成・重要度・種類別の内訳を併記します。重み付きの値を補助的に使う場合も、重みと理由を固定し、必須要求の未達を隠しません。安全上の分類を数値化して足し合わせることはしません。
- 要求カバレッジは、コードカバレッジ・機能カバレッジの代わりではなく、補うものです。3つを並べてサインオフの判断に使います。
- 機能間クロスは9.8の必須目標・構成ごとに実数と未達を表示します。相互作用の要求は、必須目標のすべてに有効な合格証跡がある場合に合格とします。到達しただけの目標や、対象外・到達不能の承認を、合格数へ足しません。
- 適用する規格や契約で必要な追跡表は、要求と検証の双方向の対応から出力できるようにします。追跡表があることだけで、それらの適合性を判断しません。

## 12. 並列化とAIの使い方

元の手順では、AIエージェントを作成担当と検証担当に分けて、区間ごとに並列に動かしました。

- 要求を、仕様の節の順に、節を分けない単位（数百要求程度）で担当範囲に分けます。
- 区間ごとに「作成担当（照合、パターン作成）」と「検証担当」を組にします。検証担当には作成担当の説明を鵜呑みにさせず、仕様と資産を自分で読ませます。
- 照合案・判定・作ったパターンの一覧は、追記型のファイルに残します。途中で止めても再開できます。
- 消費の目安（元の手順の実績）：作成担当と検証担当の1組で約50万〜65万トークン、検証担当1体で約15万〜40万トークンでした。検証だけを13区間で行った回は約560万トークン（1区間あたり約43万）でした。並列にすると短時間で消費するので、区間数を絞って始めます。
- 機密の仕様書を扱う場合は、AIを使える環境（社内、データの保存・学習の扱い）を事前に確認します。

## 13. 導入の進め方

1. **パイロット**：1つのIPで一周します。たとえば、レジスタブロックと1つのバスインターフェースを持つ小さなIPです。要求の抽出、既存資産の照合、生成テスト、独立検証、計測の順に進めます。
2. **評価**：次の点を確かめます。
   - 要求の抽出漏れ（段落の分類で検出できたか）
   - 照合の採用率
   - 新規パターンで見つかったバグ・仕様の課題の数
   - ミューテーションの検出率と未検出・未完了の内訳
   - 人手とAIの工数
3. **展開**：台帳の形式、チェックリスト、生成器を共通化し、ほかのIPへ広げます。
4. **仕様へのフィードバック**：課題票と「観測できない要求」の一覧を、仕様の書き方の改善に使います。

## 14. 実際の半導体設計で併せて必要な項目

この節は、ケーススタディからの抽出ではなく、実際の製品開発で必要となる設計・検証・製造上の確認項目をまとめたものです。前節までの要求カバレッジだけでは、テープアウトや量産の可否を判断できません。適用する項目を製品ごとに決め、対象外とする場合も理由と承認者を記録します。

各項目には、少なくとも「判定する開発段階」「対象構成・モード・コーナー」「目標値・判定基準」「入力データの版」「実行結果」「未解決事項・例外承認」「担当者・承認者」を持たせます。ツールを最後まで実行したことと、判定基準を満たしたことは区別します。ここでいう例外承認（waiver、豁免）は、未達事項の影響と残リスクを権限のある担当者が受け入れる記録であり、技術的に合格した記録とは分けます。

機能検証と専門解析の境界にある具体的な試験と引継ぎは、[領域別の点検手順](verification-gap-review.md)を使って計画します。担当が異なる項目も、[適用範囲の記録](../templates/verification-scope.md)から対応するサインオフ項目へ追跡します。

### 14.1 製品要求・アーキテクチャ

- ユースケース、動作モード、外部インターフェース、ブート・初期化、割り込み、デバッグ、エラー処理を仕様化します。
- プロセス、電圧、温度、周波数、スループット、レイテンシ、消費電力、面積、コストの目標と測定条件を決めます。
- 製品バリアント、パラメータ、機能の有効／無効、製造後の設定を整理し、構成ごとの適用要求と検証範囲を決めます。
- 外部IPについて、版、設定、統合条件、既知問題、検証済み範囲、ライセンスを確認します。IP単体の検証結果をSoC統合後の証跡にそのまま流用しません。
- 仕様、アーキテクチャ、マイクロアーキテクチャ、検証計画の相互追跡を持ち、設計判断とその根拠を記録します。

### 14.2 クロック・リセット・非同期境界

- クロック源、分周・逓倍、ゲーティング、周波数切替、クロック停止、生成クロックを一覧化します。
- リセットの種類、非同期／同期、極性、解除順序、最小幅、ウォームリセット、部分リセット、リセット中の入出力を定義します。
- クロックドメイン交差（CDC）とリセットドメイン交差（RDC）を構造検査し、同期器、ハンドシェイク、FIFOなどの方式を個別に確認します。
- データの保持、再収束、グリッチ、リセット解除とクロック停止の組み合わせを検証します。構造検査の合格だけでプロトコルの正しさを保証したことにはしません。
- 同期化後の観測レイテンシをランダムに変えるDynamic CDC／メタスタビリティ影響注入も使い、経路間の相対遅延や再収束への耐性を確認します。基準から−1／0／＋1受信サイクルなどのモデルは、捕捉条件・因果関係・同期方式に応じて範囲を定めます。クロックのジッター、実行ごとのFF段数変更、遷移ごとの注入は確認範囲を分け、物理的なMTBF評価とは区別します（[具体的な手順](verification-gap-review.md#42-同期化遅延のランダム化とメタスタビリティ影響注入)）。
- メタスタビリティの物理的な収束や故障確率を、通常のRTLシミュレーションだけで確認したとは扱いません。同期器の構造・配置・制約と、対象セルやデバイスの特性に基づくMTBFなどの評価を行い、プロトコルの検証と併せて判断します（付録CのCDC資料）。
- クロック・リセット制御自体の故障、ソフトウェアによる切替、割り込みとの競合も確認します。

### 14.3 低電力設計と電源

- 電源ドメイン、電圧ドメイン、電源状態、状態遷移、起動・停止順序を定義します。
- アイソレーション、リテンション、レベルシフタ、電源スイッチの制御と配置を、電源意図記述と実装の両方で確認します。
- 電源喪失、部分電源オフ、保持・復帰、電源投入中の出力、ソフトウェアからの遷移要求を検証します。
- 動的・静止消費電力を動作モードとPVT条件ごとに見積もり、目標との差を追跡します。
- IRドロップ、電源ノイズ、エレクトロマイグレーション（EM）、起動時の突入電流、熱分布を評価します。機能シミュレーションの結果で代替しません。

### 14.4 タイミング設計と制約

- 入出力遅延、クロック定義、生成クロック、クロック間の関係をSDCなどの制約として設計と同期して管理します。
- 製品とファウンドリの条件から、必要な動作モード・PVTコーナー・RCコーナーの組み合わせを定めてSTAを行い、セットアップ・ホールド、リカバリ・リムーバル、最小パルス幅、クロックゲーティングなどを確認します。解析しない組み合わせには根拠を残します。
- 未制約パス、制約の適用漏れ、例外の対象となる始点・終点を検査します。False PathやMulticycle Pathには設計上の根拠と独立したレビューを必須にし、例外で隠した転送の正しさをCDC解析や機能検証で確認します。
- クロストーク、シグナルインテグリティ、オンチップばらつき、クロックの不確かさを、対象プロセスに応じた解析に反映します。
- RTL、論理合成後、配置配線後の制約と解析条件を比較し、タイミングECO後は影響範囲を再検証します。

### 14.5 DFT・量産テスト

- テストモード、テストアクセス、ピン共有、クロック・リセット制御を通常機能と競合しない形で設計します。
- スキャン挿入後の接続、テスト制約、ATPGの故障網羅率と未検出故障の分類を確認します。対象は製品の要求に応じてStuck-at、Transitionなどを選びます。
- 故障モデル、全故障数、検出済み・未検出・検出不能などの分類と計測式を保存します。制約や対象外故障を変えて率が上がった場合は、その理由と承認を示します。
- メモリBIST、必要に応じた修復、ロジックBIST、Boundary Scan、テスト圧縮を確認します。
- DFT挿入前後の機能等価性、タイミング、低電力構造を再確認します。
- ATEのピン、速度、メモリ、電源精度、テスト時間を考慮し、パターン変換後の整合とシリコン上での動作を確認します。
- ウェハテスト、最終テスト、必要に応じたバーンインについて、測定項目、ガードバンド、合否限界、Bin定義、歩留まり解析の方法を決めます。

### 14.6 論理実装・物理設計・製造適合性

- 合成時の不要なラッチ、複数ドライバ、未接続、最適化による意図しない削除を検査します。
- RTLと合成後ネットリスト、配置配線後ネットリストの等価性を確認します。低電力要素やDFTを追加した後も実施します。
- フロアプラン、配線混雑、クロックツリー、タイミング、電力、面積を反復して収束させます。
- LVS、DRC、アンテナ、密度などの物理検証を、対象プロセスの指定したフローとデッキで完了します。
- 信号・電源のEM、ESD、ラッチアップ、電圧・温度による信頼性を評価します。
- DFM、リソグラフィ、製造ばらつき、歩留まりへの影響をファウンドリの要求に従って確認します。
- 設計データ、標準セル・メモリ・IP、PDK、ツール、スクリプトの版を固定し、最終ネットリストとGDSIIなどの出荷データを同一の版に紐づけます。

### 14.7 アナログ・ミックスドシグナル・I/O・パッケージ

- アナログ回路について、PVT、ミスマッチ、ノイズ、線形性、起動時間など、回路種別に応じた特性を仕様化して検証します。
- デジタルとの境界では、電圧レベル、変換精度、タイミング、電源状態、モデルの適用範囲を確認します。
- パッド、ESD保護、プルアップ・プルダウン、駆動能力、スルーレート、シュミットトリガ、入力許容電圧を確認します。
- ピン配置、パッケージ、ボンディング、ボード逃がし、同時スイッチングノイズ、電源・グランド構成をチップ側と併せて評価します。
- 高速I/Oでは、必要に応じてチャネル、ジッタ、等化、シグナル・パワーインテグリティを評価します。

### 14.8 機能安全・セキュリティ

- 対象製品では、危害分析、安全目標、安全機構、診断網羅、故障反応時間、独立監視を計画し、適用規格のワークプロダクトと整合させます。
- 永久故障だけでなく、一時故障、共通原因故障、潜伏故障、安全機構自体の故障を検討します。
- セキュリティでは、資産と脅威を定義し、Secure Boot、鍵・秘密情報、デバッグアクセス、テストモード、権限分離、改ざん検出を確認します。
- 製造・開発・出荷後のライフサイクル状態を区別し、鍵の設定・失効、更新とロールバックの方針、スキャンやデバッグからの情報漏えいとアクセス制限を確認します。
- 故障注入や不正入力で安全・セキュリティ機構が実際に働くことを検証し、例外承認した残リスクを記録します。

### 14.9 ソフトウェア・システム統合・ポストシリコン

- レジスタ仕様、ヘッダ、ドライバ、ファームウェア、診断ソフトウェアの版をRTLと整合させます。
- ブート、例外、割り込み、DMA、低電力遷移、デバッグ、実際のソフトウェアワークロードをシステム環境で確認します。
- 性能・帯域・レイテンシについて、競合やバックプレッシャのある条件も評価します。必要に応じてエミュレーションやFPGAプロトタイプを使います。
- シリコン評価では、サンプル、プロセスロット、電圧、温度、周波数を記録し、特性評価、Shmoo、Errata、再現手順を管理します。
- ポストシリコンで見つかった問題を仕様・RTL・検証環境のどの層の問題か切り分け、回帰テストと要求台帳へ還元します。
- 量産後の故障解析、RMA、歩留まり、フィールド障害を設計とテストへフィードバックします。

### 14.10 サインオフと変更管理

機能、タイミング、物理、DFT、信頼性などの結果を1つのサインオフ台帳で一覧化し、判定する開発段階を分けます。シリコンでしか得られない結果は、テープアウト前には評価計画・準備状況を確認し、実測の合否は後の段階で判定します。

| 判定する段階 | 主に確認するもの |
| --- | --- |
| テープアウト可否 | 最終設計の機能検証、等価性、CDC/RDC、STA、電源・物理検証、DFT、適用する信頼性解析。シリコン評価・ATE立上げの計画と準備 |
| 初回シリコンの評価完了 | ブリングアップ、機能・特性の実測、プレシリコンとの相関、不具合とエラッタ、ATEパターン・合否限界の確認 |
| 量産・出荷可否 | 製品で必要な認定・信頼性評価、量産テストの妥当性、歩留まり、未解決不具合と出荷条件の承認 |

製品ごとに各段階の必須項目を決めます。少なくとも、その段階について次を満たしてから判断します。

1. 各項目が合格、またはその段階で許容される例外承認になっている。対象外は根拠付きで承認され、未判定や将来実施予定と混同されていない。
2. 結果が、その段階の対象となるRTL、制約、ネットリスト、レイアウト、IP、PDK、ツールの版、またはシリコン個体・ロット・評価条件に紐づいている。
3. 一部の構成やコーナーだけの結果を、全体の合格とみなしていない。
4. 最終変更後に必要な機能回帰、等価性、STA、物理検証、DFT検査が再実行されている。
5. 未解決の仕様課題、設計課題、製造上の制約が、残リスクとして明示されている。

例外承認には、対象の要求・構成・コーナー・版、理由、影響、代替策、残リスク、承認者、期限または失効条件を残します。設計や適用条件が変わったら再承認し、古い承認を自動で引き継ぎません。承認の証拠がないものは未承認です。記録には[雛形](../templates/signoff-record.md)を使えます。

変更管理では、差分から要求、チェック、制約、構成、物理データへの影響をたどり、再実行項目と、そのまま利用する結果の根拠を記録します。最終版に対して必要な検査がそろうまで、影響を受けた項目の承認を再開しません。

要求カバレッジ、コードカバレッジ、故障網羅率、STA、DRC/LVSなどは、それぞれ別のリスクを見る指標です。いずれか1つの100%で他の項目を免除せず、サインオフでは全項目を併せて判断します。

## 15. 限界

- 電気的特性、実周波数での性能保証、消費電力、アナログ特性は、この手順の機能検証だけでは判定できません。サイクル単位の要求の検証に加え、14節に挙げた専門の設計・解析・評価が必要です。
- 状態空間が大きい設計では、形式検証が状態爆発で終わらないことがあります。9.12節の抽象化・分割を検討し、未証明の範囲と代替検証を残します。制約付きランダムとカバレッジで補った結果を、非有界の証明完了には数えません。
- 参照モデル自体が誤っていると、RTLと同じ誤りを見逃します。参照モデルの独立したレビューと、仕様への追跡が必要です。
- AIのレビューは、人の承認ではありません。台帳と報告に、担当者と方法を明記します。
- 要求の対応率が100%でも、仕様の全動作を網羅したという証明にはなりません。機能間の関係は9.8で定めた目標と機能カバレッジ・形式検証で評価します。目標自体の抜けは、相互作用表と仕様のレビューで確認します。

## 付録A：記録の例

要求行（YAML）：

```yaml
id: UART-REG-LCR-WLS-RESET
revision: 1
source: {spec: UART IP Spec, version: "2.3", section: "5.4.2", paragraph: "P0412"}
kind: reset
priority: medium
behavior: After reset, LCR.WLS (word length select) reads 2'b11 (8 data bits).
acceptance: After reset deassertion, the first completed APB read of LCR, before any LCR write, returns WLS = 2'b11.
observation_point: APB read data of LCR
configuration: [uart-apb-base, uart-apb-lowpower]
issue: null
checks: []
```

構成IDは、パラメータ・モード・前提条件を固定した適用表を参照します。この例では両構成で合格が必要です。他フィールドのリセット値は、それぞれの要求で判定します。

照合案（JSON、元の手順の`propose.py add`の記録形式を参考にした例）：

以下は汎用化後の記録の案です。現行の照合キットはIEEE 1800の要求ID・節・テスト配置を前提にするため、このUARTの例をそのまま投入することはできません。

```json
{"requirement_id": "UART-REG-LCR-WLS-RESET",
```
