# ロジック半導体の仕様書から検証パターンを作る手順

この文書は、[IEEE 1800-2023のPDFから要求を抽出し、テストで検証する手順](../case-study-ieee1800/requirements-to-tests-method.md)を、ロジック半導体の仕様書（製品仕様、IP仕様、レジスタマップ、プロトコル仕様）から検証パターンを作る方法として一般化したものです。
元の手順を規格のテストスイートで実際に使った結果（要求の全抽出、照合、新規テスト、独立検証、計測）を下敷きにしています。半導体の仕様書に適用した実績はまだありません。

対象と対象外：

- **対象**：論理機能の検証です。プレシリコンのRTL検証と、ポストシリコン検証のうち機能を確かめる部分を含みます。
- **対象外**：電気的特性（AC/DC、セットアップ・ホールド、電圧・電力の定量評価）。これらはSTA、特性評価、ATEの領域です。量産テストのATPGパターン（ネットリストの故障モデルから作る）も、この手順の対象ではありません。

## 1. 原則

- **期待値は仕様から先に決める。** RTLやシミュレータの出力を期待値に写しません。期待値は、仕様から作った参照モデルか、仕様から直接導いた値です。
- **観測できる形で要求を書く。** 1つの要求には、それが正しいかを判定できる観測点（ポート、レジスタ、割り込み、トランザクション、内部信号へのアサーション）を必ず決めます。
- **誤実装で結果が変わる検査だけを証拠にする。** 「その動作を誤って実装したら、どの観測がどう変わるか」に具体的に答えられない検査は、要求の証拠にしません。
- **作った者と確かめる者を分ける。** 検証パターンと要求との対応は、作成者とは別の検証者が反証を試み、合格したものだけを台帳に取り込みます。不確かなものは却下します。
- **証跡は版に紐づける。** 合格の記録は、RTLのコミット、テストの入力、ツールの版、seedが一致する場合だけ有効とします。
- **仕様の本文を複製しない。** 台帳やテストには要求を自分の言葉で書き、仕様の版と段落を引用します。仕様が機密の場合、AIを使える環境と範囲を最初に決めます。
- **数値を守るより正しい集計を優先する。** 誤りが分かった対応は取り下げ、理由を残します。

## 2. 元の手順との対応

| 元の手順（IEEE 1800-2023） | 一般化した手順 |
| --- | --- |
| 規格のPDFと出典ブロック | 仕様書の版と段落ID（図表・タイミング図・レジスタ表を含む） |
| 要求台帳（`behaviors.json`） | 要求台帳（JSON／YAML／要求管理ツール） |
| `kind`：正常系／違法系／境界 | 機能、違法入力、境界、リセット・初期化、構成、タイミング、性能 |
| テストの`:lrm:`による節の引用 | テストやチェッカー、カバレッジ項目に付けた要求ID |
| 期待出力ファイル | 参照モデル、スコアボード、アサーション、機能カバレッジ |
| Icarus 13.0とVerilator 5.052の照合（`:oracle:`） | 参照モデル、複数のシミュレータ、形式検証、FPGAプロトタイプの突き合わせ |
| ヘッダ定数・予約語の生成テスト | レジスタマップ、オペコード表、ピン多重化表、エラーコード表からの生成テスト |
| 解釈保留 | 仕様の曖昧さ・矛盾の課題票。作成者に確認できる |
| 入力ハッシュとランナーのハッシュ | テストの入力、RTLのコミット、ツールの版、seed |
| 暫定設計網羅率・実行確認率 | 要求カバレッジ（対応率・合格率）。重要度で重みを付ける |

## 3. 全体の流れ

```text
仕様書 ─> A. 取り込み（版・段落ID・ハッシュ）
            │
            v
          B. 要求の抽出（観測点つきの最小単位）──> C. 曖昧さの課題票 ──> 仕様の作成者
            │
            ├─> D. 既存の検証資産との照合 ──┐
            └─> E. 検証パターンの作成 ──────┴─> F. 独立した検証 ─> G. 統合・回帰・計測
```

## 4. 準備

### 4.1 入力物

| 入力 | 扱い |
| --- | --- |
| 製品仕様・IP仕様 | 版と改訂履歴を固定する。段落に安定したIDを振る |
| レジスタマップ | 機械可読な原本（IP-XACT、SystemRDL、表計算）を優先する。PDFの表より誤読が少ない |
| プロトコル仕様（標準・社内） | 版を固定する。コンプライアンス要求と任意機能を区別する |
| タイミング図・状態遷移図 | 図ごとにIDを振り、テキスト化した要点と対応させる |
| エラッタ・設計判断の記録 | 仕様と同じく出典として扱う |
| RTL、テストベンチ、既存のテスト・アサーション・カバレッジ | 照合の対象。コミットを固定する |

### 4.2 道具

- 2つ以上の独立した確認先：参照モデル（C、Python、SystemC）、複数のシミュレータ、形式検証ツールなど。
- 要求台帳と照合案を検査する仕組み：元の手順の[照合キット](../../tools/matching_kit/README.md)と同じ役割で、要求ID、観測点、証跡の実在を機械的に検査します。
- 回帰の結果を、RTLのコミット、テストの入力のハッシュ、ツールの版、seedとともに保存する仕組み。

### 4.3 要求台帳の形式

1行の要求に、少なくとも次の項目を持たせます（付録Aに例があります）。

| 項目 | 内容 |
| --- | --- |
| `id` | 安定したID。仕様の版が変わっても、意味が同じなら変えない |
| `source` | 仕様の名前・版・節・段落（図表ID） |
| `kind` | 機能／違法入力／境界／リセット・初期化／構成／タイミング／性能 |
| `priority` | 重要度、安全度（ASILなど） |
| `behavior` / `acceptance` | 要求と、観測可能な合格基準 |
| `observation_point` | どこで何を観測するか |
| `configuration` | 前提とする構成・パラメータ・製品バリアント |
| `issue` | 未解決の曖昧さ（あれば対応承認を禁止する） |
| `checks` | 対応する検証資産と証跡（空なら未対応） |

## 5. 段階A：仕様の取り込み

1. 仕様書の版を固定し、ファイルのハッシュを記録します。
2. 節・段落・図表に安定したIDを振り、各段落のハッシュを記録します。本文は台帳に入れません。
3. 全段落を、「要求」「説明」「例」「参照」「見出し」のどれかに分類します。「要求」の段落は、どの要求行に対応するかを記録し、要求行の側からも段落を指します。この双方向の対応で、抽出漏れを機械的に検出します。
4. 仕様が改訂されたら、ハッシュの変わった段落だけを再確認します。

仕様の種類ごとの注意：

- **レジスタマップ**：フィールド（オフセット、幅、リセット値、アクセス種別、予約ビットの扱い）を1行ずつ要求にします。機械可読な原本から抽出し、PDFとの食い違いは課題にします。
- **プロトコル仕様**：トランザクションの種類、ハンドシェイクの規則、順序の規則、エラー応答、タイムアウトを分けます。「してもよい」（任意機能）と「しなければならない」を区別します。
- **社内IP仕様**：マイクロアーキテクチャの記述（実装の説明）と、外から観測できる振る舞いの要求を分けます。前者は検証の対象にしないか、内部アサーションの対象として別に扱います。

## 6. 段階B：要求の抽出

### 6.1 単位

1行は「1つの条件または1つの観測」です。複数の条件を述べる文は分けます。

### 6.2 書き方の規則

元の手順で、台帳を見直したときに分かったことを一般化した規則です。

- **観測できる形で書く。** 例：「予約ビットに書いても影響しない」は、「予約ビットに1を書いた後、そのレジスタを読むと予約ビットは0で、他のフィールドも変わらない」と書く。
- **正常系と違法系を1行に混ぜない。** 「Xは受理され、Yはエラー応答になる」は2行に分けます。
- **仕様が許す幅を明記する。** レイテンシの範囲、応答の順序の自由、アービトレーションの方式などです。単一の値を期待値にしてよいのは、仕様が決めている場合だけです。
- **構成・実装依存の前提を受入条件で固定する。** 例：「FIFOの深さ=Nの構成で」「バースト長の上限が設定されている場合」。
- **使い方の規則（ソフトウェアやシステム側の義務）と、デバイスの振る舞いを分ける。** 例：「ソフトウェアは初期化完了まで書いてはならない」は、デバイスの要求ではありません。
- **既存の要求と意味が重なる行を増やさない。** 同じ要求が複数の節に現れる場合は、1行にまとめて出典を複数持たせます。
- **リセット直後と初期化の要求を忘れない。** リセット値、リセット中の出力、リセット解除後の最初の動作です。

## 7. 段階C：曖昧さの管理

- 仕様の中で整合しない記述、未定義の場合、図と文章の食い違いは課題票にし、該当する要求行に`issue`を付けます。課題が解消するまで、その行に検証資産を対応付けません。
- 解消の根拠は次のいずれかにします。
  - 仕様の作成者の回答
  - 設計判断の記録
  - 仕様の内部にある決定的な根拠（機械可読なレジスタ定義、構文・表の定義など）
- 根拠が推測にとどまるものは解消扱いにしません。
- 解消したら、要求文を採用した解釈で書き直し、根拠を記録します。仕様の改訂やエラッタに反映されたかも追います。
- 社内仕様では作成者に確認できるので、元の手順（公式な正誤表がない規格）より早く、確実に解消できます。課題票を、仕様の品質の指標としても使えます。

## 8. 段階D：既存の検証資産との照合

### 8.1 照合の対象

既存のテスト、チェッカー（スコアボード）、アサーション、機能カバレッジ項目、形式検証のプロパティを、要求に対応付けます。

### 8.2 基準

1. 要求の`behavior`・`acceptance`と、仕様の該当段落・図表を読む。
2. 検証資産の刺激、チェッカーの比較内容、アサーションの式、カバレッジの定義まで読む。
3. 次の場合だけ対応を登録する。
   - 要求の全条件を、その資産が実際に起こし、観測している。
   - 誤実装なら、比較・アサーション・カバレッジの結果が変わる。
4. 次のものは証拠にしません。
   - テスト名や説明文だけ
   - 信号が動いたことだけ
   - 常に成立するアサーション、空成立しかしないアサーション（前提が一度も成立しない含意など）
   - 真になる入力しかない比較
   - 個数だけを見て、対象の同一性を見ない検査
   - 仕様が順序を決めないことに依存する比較
5. 1つの資産が条件の一部しか見ない場合は、全条件を複数の資産で分担できるならAND集合にします。そうでなければ保留として理由を記録します。
6. 証跡には、刺激の位置（テスト・シーケンスの該当箇所）と、判定の位置（チェッカーの比較、アサーション名、カバレッジ項目名）を、文字列や識別子で残します。

### 8.3 実績からの目安

元の手順では、既存テストの照合で採用されたのは、未対応の要求の約6〜15%でした。主な理由は、要求の条件を刺激する既存テストがそもそも無いことです。
照合は最初に安く済ませ、残りは新しい検証パターンで埋める計画にします。

## 9. 段階E：検証パターンの作成

### 9.1 方式の選び方

| 要求の性質 | 方式 |
| --- | --- |
| 表で列挙される値（レジスタのリセット値・アクセス種別、オペコード、エラーコード、ピン多重化） | 生成器で網羅する（9.4） |
| 特定の手順で起きる動作（初期化手順、特定のシーケンス、エラー回復） | 直接テスト |
| 組み合わせが多い動作（データ幅、バースト、並行トランザクション） | 制約付きランダムと、要求IDに結びつけた機能カバレッジ |
| 常に成り立つ性質（ハンドシェイクの規則、排他、FIFOのオーバーフローなし） | SVAアサーション。可能なら形式検証で証明する |
| 違法入力への応答（不正アドレス、プロトコル違反、予約値の書き込み） | 直接テストと、応答を確かめるチェッカー |
| タイミング（サイクル数、タイムアウト） | 許容範囲を持つチェッカーとアサーション |

### 9.2 参照モデル

- 仕様だけから作り、RTLを見て作らないようにします。参照モデルの作成者と、RTLの作成者を分けます。
- 参照モデル自体もレビューの対象です。仕様の段落への追跡を持たせます。
- サイクル精度が要らない要求は、トランザクションレベルで抽象化します。

### 9.3 チェッカーと期待値

- 仕様が許す幅（レイテンシ、順序）を受け入れます。
- X（未定義値）、リセット中、構成による違いの扱いを明示します。
- 期待値を先に書き、シミュレーションで確かめます。食い違いは、まず仕様と期待値を確かめ直し、それでもRTL側の誤りならバグとして記録します。期待値をRTLの出力に合わせて直すことはしません。

### 9.4 表形式の仕様は生成器で作る

元の手順で、ヘッダの定数や予約語を検証した方法の一般化です。

- 生成器の参照モデルは、仕様の表（機械可読な原本があればそれ）から作ります。表どうしの一致を、生成器の中で検査します（例：フィールド幅の合計がレジスタ幅と一致する、オフセットが重ならない、版ごとの追加分の和が全体と一致する）。
- レジスタでは、次を網羅します。
  - リセット値
  - アクセス種別ごとの書き込みと読み戻し（RW、RO、WO、W1C、W1S、RC）
  - 予約ビットの扱い
  - 未定義アドレスへのアクセスに対する応答
  - バイトイネーブル
- 違法系のケースも生成します（書き込み禁止のフィールドへの書き込み、範囲外のアドレス）。期待する応答（エラー応答、無視、割り込み）は仕様から決めます。
- 生成物の判定基準（期待値、エラー応答の位置）は、生成器が自動で決めます。手で直さないでください。

### 9.5 構成とバリアント

- 要求に構成の前提を持たせ、構成ごとに回帰を回します。
- 構成によって適用されない要求は、分母から除くのではなく「その構成では対象外」と記録します。

### 9.6 再現性

seed、テストの入力、RTLのコミット、ツールの版を、すべての実行結果に記録します。

## 10. 段階F：独立した検証

- **パターンの判定**：検証者は、期待値（参照モデルの出力、チェッカーの判定基準）を仕様から自分で導いて照合します。合法な刺激か（仕様が禁じる使い方をしていないか）、決定性があるか、構成の前提が正しいかも確かめます。期待値が仕様から導けないパターンは欠陥です。
- **照合の判定**：刺激が要求の全条件を起こし、判定が誤実装と区別できる場合だけ採用します。不確かなら却下します。
- **故障注入（ミューテーション）**：RTLの演算子・定数・条件を1か所ずつ誤らせ、チェッカーやアサーションが検出するかを確かめます。検出できない変異は、検証パターンの弱さか、観測できない差（等価な変異）です。
- **大量の機械的な案**：独立に抽出した値（例：レジスタマップの機械可読な原本と、PDFの表を別の方法で読んだもの）との照合結果に基づいて、まとめて判定してよいことにします。

元の手順の検証で実際に見つかった穴を、一般化したチェックリストです。

| 穴 | 対策 |
| --- | --- |
| 型や幅を落とした比較（切り詰め、符号の見落とし）で誤りが隠れる | 全幅で比較し、範囲外の値は検出する |
| 条件の片側だけを刺激している（真だけ、増える場合だけ、片方の向きだけ） | 対照のケースを足す |
| 個数だけを比べ、どの要素かを確かめていない | 対象の識別子・値で照合する |
| 未定義の名前や値が既定値として扱われ、検査が素通りする | 定義されていることも確かめる |
| 規格・仕様が順序を決めないものに依存している | 許容範囲で判定する |
| 空成立しかしないアサーション | 前提が成立したことをカバレッジで確かめる |
| 未定義動作・処理系依存に頼る検査 | 対応付けを見送る |
| 構造（共用体、ガード、レジスタの重なり）を見ていない | 構造そのものを観測する検査を足す |

## 11. 段階G：統合・回帰・計測

1. 欠陥ありのパターンと、判定のないパターンを取り除きます。
2. 採用された対応を台帳に統合します。統合は、そのときのテストの入力とRTLのコミットに紐づけます。
3. 回帰を実行し、結果を版ごとに保存します。部分実行の結果は、全体の結果と合成しません。AND集合は、同じ実行回でメンバー全員が合格した場合だけ合格とします。
4. 計測して報告します。

| 指標 | 意味 |
| --- | --- |
| 要求の対応率 | 検証資産が対応付いた要求の割合（設計側） |
| 要求の合格率 | 版の一致する合格の証跡がある要求の割合（実行側） |
| 重要度別の内訳 | 安全度・重要度ごとの対応率・合格率 |
| 未解決の課題 | 曖昧さの件数、解消までの日数 |
| 故障注入の検出率 | 変異を検出できた割合（等価な変異を除く） |

- 全要求を同じ重みで数えると、表から機械的に生成した多数の行（レジスタのフィールドなど）で値が大きく動きます。重要度で重みを付けた値か、種類別の内訳を必ず併記します。
- 要求カバレッジは、コードカバレッジ・機能カバレッジの代わりではなく、補うものです。3つを並べてサインオフの判断に使います。
- 機能安全や航空の規格が求める、要求と検証の双方向の追跡表は、台帳からそのまま出力できるようにします。

## 12. 並列化とAIの使い方

元の手順では、AIエージェントを作成担当と検証担当に分けて、区間ごとに並列に動かしました。

- 要求を、仕様の節の順に、節を分けない単位（数百要求程度）で担当範囲に分けます。
- 区間ごとに「作成担当（照合、パターン作成）」と「検証担当」を組にします。検証担当には作成担当の説明を鵜呑みにさせず、仕様と資産を自分で読ませます。
- 照合案・判定・作ったパターンの一覧は、追記型のファイルに残します。途中で止めても再開できます。
- 消費の目安（元の手順の実績）：作成担当と検証担当の1組で約50万〜65万トークン、検証担当1体で約15万〜40万トークンでした。並列にすると短時間で消費するので、区間数を絞って始めます。
- 機密の仕様書を扱う場合は、AIを使える環境（社内、データの保存・学習の扱い）を事前に確認します。

## 13. 導入の進め方

1. **パイロット**：1つのIPで一周します。たとえば、レジスタブロックと1つのバスインターフェースを持つ小さなIPです。要求の抽出、既存資産の照合、生成テスト、独立検証、計測の順に進めます。
2. **評価**：次の点を確かめます。
   - 要求の抽出漏れ（段落の分類で検出できたか）
   - 照合の採用率
   - 新規パターンで見つかったバグ・仕様の課題の数
   - 故障注入の検出率
   - 人手とAIの工数
3. **展開**：台帳の形式、チェックリスト、生成器を共通化し、ほかのIPへ広げます。
4. **仕様へのフィードバック**：課題票と「観測できない要求」の一覧を、仕様の書き方の改善に使います。

## 14. 限界

- 電気的特性、性能・電力の定量評価、アナログ回路は対象外です。
- 状態空間が大きい設計では、形式検証が状態爆発で終わらないことがあります。制約付きランダムとカバレッジで補います。
- 参照モデル自体が誤っていると、RTLと同じ誤りを見逃します。参照モデルの独立したレビューと、仕様への追跡が必要です。
- AIのレビューは、人の承認ではありません。台帳と報告に、担当者と方法を明記します。
- 要求の対応率が100%でも、仕様の全動作を網羅したという証明にはなりません。組み合わせの網羅は、機能カバレッジと形式検証で別に評価します。
