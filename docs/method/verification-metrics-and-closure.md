# 検証の指標を推移で読み、収束を判断する

1回の回帰の合否だけでは、検証が終わりに近づいているかは分かりません。不具合の見つかり方、未解決の件数、カバレッジ、合否の揺れを**回ごとに並べて**読み、最後に流出した不具合を振り返ります。この文書は、その指標の作り方と読み方をまとめます。[実行例](../../examples/local-closure-trend/README.md)では、架空の11回分の履歴から傾向の表を作り、すべての数を別のコードと手の数えで照合します。

指標は判断の材料です。数がそろっても、それだけで合格やサインオフにはなりません。最終の判断は、[サインオフ記録](../templates/signoff-record.md)で、証跡と責任者を残して行います。

## 1. 1回の結果を正しく数える

推移の前に、1回分の数え方を決めます。ここを誤ると、どの推移も意味を失います。

| 結果 | 数え方 | 誤りやすい点 |
| --- | --- | --- |
| 合格 | 予定した全ケースが完了し、判定が合格 | 予定より少ないケースで終わったものを合格にする |
| 不合格 | 完了し、チェッカーが失敗を報告 | 環境の不良（ツールがない、ディスクが一杯）を回路の不合格にする |
| 未完了 | 時間切れ、起動しなかった、途中で止まった | 時間切れを合格にする。逆に、不具合の検出に数える |

未完了は、合格でも不合格でもない第3の状態として数えます。時間切れが続くなら、その原因（回路のハング、ランナーの上限、計算機の混雑）を[失敗の切り分け](failure-analysis.md)の手順で調べます。[統合ランナー](../../tools/REGRESSION.md)は、時間切れや予定ケースの欠けを合格にしない作りで、その結果（`summary.json`）をそのまま入力にできます。

## 2. 不具合の見つかり方の推移

不具合は、見つけた回・解決を確かめた回・再発した回を記録します。

- **新規と再発を分けます。** 一度解決した不具合が戻ったものを新規に数えると、見つかる数が減っていないように見えます。
- **解決は、修正を確かめた回で数えます。** 修正を入れた回ではなく、同じ入力で合格を確かめた回です。
- **回路・テストベンチの不具合と、環境の不良を分けます。** 環境の不良は、回路の品質の指標に入れません。ただし件数は別に残します。環境の不良が多い期間は、回路の結果も信頼しにくいからです。
- **見つけた手段も残します。** 回帰、レビュー、フォーマル、上位の結合など。回帰が何も見つけなくなっても、レビューで見つかり続けるなら、回帰の刺激やチェッカーに抜けがある可能性があります。

新規の数が減ってきたことは、収束の兆しの1つです。ただし、刺激を変えていない、チェッカーが弱い、回帰が止まっている、という理由でも新規は減ります。その場合は、次の節以降の指標と、[変異による検出力の確認](mutation-verification.md)で裏付けます。

## 3. 未解決の件数

未解決の件数は、各回の終わりの時点で、見つけた・再発したものから解決したものを引いた数です。重大度ごとに分けて数えます。

- 全体の回帰が合格していても、未解決の不具合は残っていることがあります。レビューで見つけたもの、回帰に再現の試験がまだないものです。
- 「合格だから未解決0」とは扱いません。回帰の合否と不具合の記録は、別の情報源です。

## 4. カバレッジの推移

カバレッジは、指標ごとに分けて並べます。

| 決まり | 理由 |
| --- | --- |
| 機能カバレッジとコードカバレッジを合算しない | 分母の意味が違う。合算した割合は、どちらの完了も示さない |
| 合格した実行の分だけを計上する | 不合格の実行で届いた目標は、正しい動作で届いたとは言えない |
| 計上しなかった構成の数を並べて書く | 割合が100%でも、計上した構成が減っているだけのことがある |
| 分母の変更を記録する | 目標を足せば割合は下がり、コードを消せば分母が減る。どちらも回路の後退ではない |

実行例の表では、ある回の機能カバレッジが60/60（100%）に見えます。実際は6構成のうち2構成を計上しておらず、全体が完了したわけではありません。割合だけを見ず、分母と未計上の数を必ず一緒に読みます。計画の作り方と、未達の項目の扱いは、[機能カバレッジ](functional-coverage.md)と[コードカバレッジ](code-coverage.md)にあります。

## 5. 回帰の安定度（合否の揺れ）

同じ計画で、合格と不合格の両方が出たジョブを「揺れている」と数えます。

- **同じ計画**とは、同じコミット・同じseed・同じプロファイル（同じ刺激）のことです。seedが違えば刺激が違うので、結果が違っても揺れではありません。違うseedで見つかった不合格は、不具合の手がかりとして扱います。
- **未完了は判定に数えません。** 合格と時間切れの組は、揺れではなく、時間切れの原因を調べる対象です。
- 揺れの原因は、テストベンチの競合、初期化していない値、並列実行の干渉、時間に依存した判定などです。原因を直すまでは、揺れたジョブの合格を収束の根拠にしません。
- 再実行で合格したことで、最初の失敗を消しません。[履歴レポート](../../tools/REPORTING.md)は、最初の失敗を残したまま最後の試行で判定し、古い成功へ戻りません。

揺れの多い回帰は、新規の不具合が減って見えても信頼できません。揺れの件数そのものも、推移として並べます。

## 6. 流出した不具合の振り返り

最後の回帰の後に、上位の結合・試作・シリコンの評価・出荷後で見つかった不具合を「流出」と呼びます。流出は、検証の計画と手段の弱点を直接示す情報です。

| 振り返る点 | 例 |
| --- | --- |
| どこで見つかったか | 上位の結合、FPGAの試作、シリコンの立上げ |
| なぜ見逃したか | 仕様の読み違い、計画にない場面、刺激が届かない、チェッカーがない、カバレッジの目標がない、フォーマルの仮定が強すぎる |
| どの検査で見つかるはずだったか | 処理中に次の要求を出し続ける刺激、ビットの中央の半分だけ正しい波形 |
| 何を足したか | 固定の回帰、チェッカー、カバレッジの目標、レビューの観点 |
| ほかに同じ型の抜けはないか | 同じ書き方のテストベンチ、同じ握手の部品 |

振り返りは[流出不具合の分析の雛形](../templates/escape-analysis.md)で記録します。見逃した型は、[レビューの観点](../templates/review-checklists.md)へ足します。このリポジトリのレビューで見つかった試験の抜け（空きサイクルがない、処理中の要求がない、「ちょうど」と「1つ超え」の片方しかない、など）も、その観点の表に入っています。

## 7. 収束を判断する

収束の基準は、計画の段階で決めておきます。後から結果に合わせて決めると、基準の意味がなくなります。

| 基準の例 | 確かめる指標 |
| --- | --- |
| 直近の数回の回帰で、不合格と未完了がない | 回ごとの合格・不合格・未完了 |
| 未解決の不具合が、決めた重大度以上で0件 | 未解決の件数 |
| 必須の機能カバレッジの目標がすべて届き、計上しなかった構成がない | 指標ごとのカバレッジ、未計上の数 |
| 揺れたジョブの原因がすべて解決している | 揺れの一覧と、対応する不具合の記録 |
| 新規の不具合の見つかり方が落ち着き、検出力の確認が済んでいる | 新規の件数の推移、変異の検出の結果 |

基準を満たしていない項目は、満たしていないまま記録します。例外として進めるなら、権限のある人が理由と残るリスクを書きます。実行例の判定は、満たしていない基準の名前を並べるだけで、承認はしません。

## 8. 実行例

[収束の傾向の実行例](../../examples/local-closure-trend/README.md)は、11回分の架空の履歴から、上の指標を1つの表にします。数え方の誤り9種類（時間切れを合格に数える、再発を新規に数える、不合格の実行のカバレッジを計上する、seedの違いを揺れに数える、など）を生成器へ入れ、別に書いた数え直しが、決めた場所で食い違うことを確かめます。履歴の作り方の参考には、実際の時間切れと再実行を使う[履歴レポートの実行例](../../examples/local-regression-report/README.md)があります。

## 9. この文書の範囲

- 指標の目安（何件なら収束か、何%なら十分か）は書いていません。製品・工程・リスクで変わるからです。
- 不具合管理や検証管理の製品は扱っていません。どの道具を使っても、1〜6節の数え方の約束は同じです。
- 検証の削減とテストの選び方は[検証の削減](verification-reduction.md)、回帰の運用は[継続的リグレッション](continuous-regression.md)にあります。
