# 検証計画の抜けを点検し、試験へ展開する

[一般化した検証手順](spec-to-verification-method.md)の4.4節・9.13節と、14節の製品開発上の項目を具体化する資料です。検証方式をそろえることに加え、初期化、転送、異常、復帰、負荷、電源、統合などの動作が計画から漏れていないかを確認します。

2026-10-25の見直しでは、既存資料にクロック・リセット、低電力、性能、安全・セキュリティなどの概要はあるものの、試験条件・観測点・合格基準までの展開が不足していました。lint、X伝搬、コードカバレッジの未達分析も含め、以下を補います。これは本リポジトリの運用案で、製品での実行済みの結果ではありません。

## 1. 適用する検証領域を先に決める

次の一覧をIP・SoC・構成ごとに確認します。すべての製品へ同じ検査を課すものではありません。非同期境界や電源遮断などがない場合も、構成図・仕様を根拠に対象外と判断し、未確認とは分けます。[適用範囲の記録](../templates/verification-scope.md)へ担当・必要な段階・要求・証跡を登録します。

| 領域ID | 点検する領域 | 主な試験・解析と確認する結果 |
| --- | --- | --- |
| SCOPE-STATIC | 静的検査・エラボレーション | 幅・符号・ラッチ・駆動・結線、構成ごとの読み込み、警告の処置 |
| SCOPE-RESET-X | リセット・初期化・X伝搬 | 起動、動作中・部分リセット、保持・取消、初期化前の値の流出 |
| SCOPE-CDC-RDC | クロック・リセット境界 | 構造解析、転送の整合、位相・周波数・解除順序・停止復帰 |
| SCOPE-PROTOCOL-DATA | プロトコル・データ整合性 | 待ち・同時転送、欠落・重複・順序、幅変換・境界・メモリ |
| SCOPE-FAULT-RECOVERY | 異常・故障と復帰 | 不正操作、エラー・タイムアウト、故障注入、封じ込め・復旧 |
| SCOPE-PERFORMANCE | 性能・負荷・進行性 | 帯域・遅延、飽和と解消、仲裁、公平性、停止・飢餓 |
| SCOPE-POWER | 低電力・電源遷移 | 電源状態と遷移、遮断・保持・復帰、クロック停止、wake-up |
| SCOPE-SECURITY | 権限・セキュリティ・安全機構 | 許可・拒否、状態遷移、秘密情報、対策の故障時の反応 |
| SCOPE-CODE-COVERAGE | コードカバレッジの未達 | 実装にあって機能モデルにない経路、未到達・除外の分析 |
| SCOPE-EQUIVALENCE | 等価性・実装変更 | 合成・DFT・低電力・ECO前後の対応、未証明の分割・モード |
| SCOPE-SYSTEM-SW | システム・ソフトウェア統合 | 接続・アドレス・割り込み、DMA・ドライバ・実ワークロード |
| SCOPE-PHYSICAL | タイミング・物理・製造・実測 | STA、DFT/ATPG、DRC/LVS、電源・信頼性、AMS、シリコン評価 |

この一覧自体が仕様の完全な分類とは限りません。ブロック図、外部端子、クロック・リセット・電源、レジスタとメモリ、エラー経路、運用・製造モードを別々の入口として照合し、どの行にも対応しない機能・接続・要求を探します。

## 2. 静的検査と構成ごとの読み込み

RTLだけでなく、testbench・checker・生成コードも対象にします。幅の切り詰め、符号、暗黙ネット、未駆動・未接続、複数ドライバ、不要なラッチ、組み合わせループ、到達しない分岐などを、採用したルールセットで検査します。たとえばVerilatorには[lint専用の実行方式](https://verilator.org/guide/latest/verilating.html)がありますが、検出できる内容はツール・版・設定ごとに確認します。

パラメータの最小・最大、幅1、オプションの有無、必須のマクロ・製品バリアントでエラボレーションします。FIFO深さなどに制限があれば合法集合を仕様化し、禁止構成が受け付けられたときの診断も確認します。代表構成だけで全構成の合格にしません。

警告の一括抑止で合格にせず、ルール・対象箇所・理由・影響・承認・失効条件を記録します。終了コード、解析したトップ・ソース・構成、未解決の指摘、新規と既存の除外を確認します。lintで問題がないことと、動作が仕様に合うことは別に判定します。

## 3. リセット・初期化・X伝搬

初回起動だけでなく、次の状態でリセットを入れます。

- アイドル、要求の受理直前・同時・直後、応答待ち、完了直前。
- FIFOが空・満杯、割り込みが保留、エラー処理中、クロック停止中。
- 部分・ウォームリセットで、相手側や保持領域には状態が残っている場合。

状態・出力のリセット値と、保持する値、取り消す処理、返す応答、再開条件を仕様から決めます。scoreboardも同じ規則で「完了」「仕様に基づく取消」「未解決」を分けます。リセット時に未照合の台帳を無条件に空にして、取りこぼしを隠しません。解除後は最初の有効トランザクションが正しく処理され、古い応答や割り込みが再出現しないかを判定します。

4値シミュレーションや対応するX伝搬方式では、未初期化メモリ・レジスタ、無効な選択、リセット解除時の制御などが、有効な出力・判定へ流れるかを調べます。仕様が値を要求する期間とvalid条件を明示し、無効なデータバスまで常にknownとする検査は避けます。比較前の`bit`への変換などでX/Zを消さず、未知値を検出します。

通常の4値シミュレーションと、シミュレータ固有のX伝搬処理、2値の初期値ランダム化は、方式と保証する範囲を分けて記録します。Xを0/1へ置換する試験だけでX伝搬を検証したとは扱いません。X伝搬の未対応・無効化された階層や構文も記録します。

完了には、リセット種別×実行中の処理×保持・取消の各必須目標と、解除後の比較結果をそろえます。Xの検査では有効な観測期間、未知値の発生・流出、checkerの有効化を残します。

## 4. CDC/RDCとクロック制御

### 4.1 構造とクロック・リセット条件

クロック・リセットのドメインと関係を一覧化し、IP境界とSoCでの接続を照合します。静的なCDC/RDC解析では、同期器だけでなく、パルス、複数ビット、非同期FIFO、ハンドシェイク、再収束、リセット解除を確認します。未分類の交差や、クロック・リセット定義の不足を除外として消しません。

動的検証では、合法な周波数比・位相差、送信元が速い／遅い、連続イベント、片側だけのリセット、クロック停止・再開を狙います。送信側の受理と受信側の完了を結び付け、仕様に応じてイベントの欠落・重複、複数ビットの不整合、デッドロックを判定します。最短パルス幅や入力保持期間が環境条件なら、仮定と、その成立を確認する側を記録します。

解析の合格には、対象交差・制約・構造・除外のレビューと、必要な機能プロトコルの結果を対応させます。RTLの位相を変える試験だけでは、メタスタビリティの物理的な収束を実証できません。配置・セル・制約・MTBFなどの扱いは[一般化手順の14.2節](spec-to-verification-method.md#142-クロックリセット非同期境界)へつなぎます。[AccelleraのCDC/RDC資料](https://www.accellera.org/downloads/standards/clock-domain-crossing)は、IPからSoCへ解析情報を引き継ぐ際の参照先です。

### 4.2 同期化遅延のランダム化とメタスタビリティ影響注入

同期化後に値が見える時刻を変えて、受信側が遅延の不確定さに耐えるかを調べる手法は、Dynamic CDC、metastability-effects modeling／injectionなどとして使われています。商用CDC製品にも採用されている方法です。[SiemensのCDC-FX解説](https://resources.sw.siemens.com/en-US/white-paper-questa-cdc-fx-metastability-effects-delay-modeling/)では、RTLシミュレーションへメタスタビリティによる非決定的な遅延の影響をモデル化する方式が説明されています。

基準の同期化遅延に対して、受信クロックで−1／0／＋1サイクルの違いを作るモデルもあります。[semifyの公開Dynamic CDCモデル](https://github.com/semify-eda/dynamic_cdc)には、setup／hold違反時に旧値・新値のどちらへ収束するかによって、通常の観測から前後する例が示されています。ただし、この3値や確率分布がすべての同期器に共通の物理モデルという意味ではありません。対象回路・捕捉条件・基準時刻に応じて許される振る舞いを決めます。

「ジッターを入れる」という表現は、次の方式を分けて記録します。

| 方式 | 変えるもの | 確認する範囲 |
| --- | --- | --- |
| クロックの位相・周期のジッター | クロックエッジの時刻 | 入力遷移と受信エッジの関係。通常のRTLだけではメタスタビリティによる捕捉の不確定さまで表さない |
| 同期化FFの段数・モデル遅延を実行ごとに変更 | 各同期器の固定レイテンシ | 遅延の構成差や、経路間の固定した到着差への耐性 |
| 転送・捕捉ごとに遅延の不確定さを注入 | 同じ同期器でも変わり得る観測時刻 | メタスタビリティの影響による相対順序の変化、再収束、プロトコルの耐性 |

検証用にFF段数や遅延タップを変える実装は、遅延を揺さぶる手段として使えます。実行ごとに段数を固定するだけの試験と、同じ実行中でも遷移ごとに捕捉結果を変える試験は、確認範囲を分けます。実際に使っていた方式がどちらかを、計画と証跡に明記します。

### 4.3 注入モデルを作るときの条件

合成する同期器の構造と、検証用の振る舞いモデルを区別します。実装のFF段数を減らした回路が安全だと、この試験から判断しません。モデルの適用箇所・enableを記録し、注入なしの構造と通常動作も確認します。

モデルは少なくとも次をレビューします。

- **時間の基準**：基準遅延Nと−1／0／＋1の単位を、どの受信クロックのどの捕捉から数えるか定義する。−1は基準モデルより早く観測するという意味で、未来の入力を先読みしてよいという意味ではない。
- **注入の条件**：setup／holdの近傍など、捕捉が不確定になる条件と旧値・新値の選択を定義する。窓の時間幅・単位・timeprecisionも保存する。無条件に遅延を変える広いストレス試験を併用する場合は、実回路を模した注入と区別する。
- **遷移の整合**：遅延タップを毎サイクル無条件に切り替えたため、モデルだけが古い値を再出力したり、余分なパルスを作ったりしていないか確認する。既知の入力列、短い／長いパルス、連続遷移、リセットでモデル自体の振る舞いを確かめる。
- **相関と独立性**：別々の同期器を通る制御の相対遅延を変え、受信側で再収束する条件を狙う。同じ同期器の出力を共有するfanoutへ、根拠なく別々の乱数を与えない。複数ビットやGray符号は、対象の転送方式が許す関係を保ってモデル化する。
- **適用する同期方式**：単一ビット、toggle／pulse、req/ack、bundled data、非同期FIFOを区別する。データバスの各ビットへ独立な段数変更を入れるだけで、正しい複数ビットCDCを検証したことにはしない。
- **初期化と解除**：リセット中・解除直後、クロック停止・再開時の注入状態と履歴を定義する。RDCの構造やリセット解除条件の検査は別に残す。

実行前には、モデル単体の既知の入力で、許した遅延と出力列を確認します。注入なしでは正しい回路が合格し、遅延差への依存を意図的に入れた小さな誤回路をcheckerが検出することも確認します。これにより、モデル・刺激・checkerのどこが検査に寄与したかを判断します。

### 4.4 観測目標と完了判定

注入した回数に加え、各同期器で**実際に観測された遅延**、0→1／1→0、捕捉条件、経路間の相対到着順、再収束時の状態を採取します。−1／0／＋1を選ぶ乱数が出ても、対象信号が変化していなければ、その遅延の確認には数えません。

たとえば別々の同期器A・Bの出力が再収束するなら、ΔA×ΔBは3×3の9候補ですが、注入条件とモデル上で許される組を確認して必須目標を決めます。両方へ同じ遅延を入れるだけでなく、Aが先／同時／Bが先になる条件を狙い、仕様に従って取りこぼし・重複・誤った組合せ・デッドロックを判定します。req/ackでは、それぞれの受信クロックとデータ保持・応答の関係を確認します。

基準レイテンシへ固定したscoreboardが合法な遅延差を誤検出しないよう、受理と識別子・順序・データを追跡します。ただし応答期限や必要なパルス幅などの要求まで緩めてはいけません。仕様と環境条件が認める範囲内で、判定を行います。

証跡には、モデルと版、置換・注入したインスタンス、基準遅延・許容遅延、実行ごと／遷移ごとの選択、注入条件・窓・確率、インスタンスごとのseed・相関、クロック条件、注入と観測のカバレッジ、checkerの結果を残します。乱数の分布を、シリコンでの故障確率へ読み替えません。静的CDC/RDC・物理設計・MTBF評価と組み合わせて判断し、この試験単独でCDCのサインオフ完了とはしません。

## 5. プロトコルとデータ整合性

プロトコル検査と、転送内容のend-to-endの比較を両方用意します。プロトコルが合法でも、宛先・ID・データが違う場合を検出できるようにします。

- 待ちなし、1サイクル・長時間・断続的なバックプレッシャ、連続転送、同時送受信。
- 最大outstanding、ID再利用の境界、複数ID・チャネルの完了順序、取消・再試行。
- 幅変換、バイトイネーブル、アラインメント、バーストとアドレス境界、符号拡張・エンディアン。
- メモリ・FIFOの先頭／末尾、ラップ、同一アドレスの競合、read-during-write、設定とデータ転送の競合。

待ち中のデータ保持や応答の順序は、採用するプロトコルの要求に従います。仕様が認める並べ替えを誤検出せず、認めない欠落・重複・誤配送を検出します。ID・アドレス・バイトマスク・データを追跡し、受理数、完了数、仕様上の取消数、未解決数の整合を確認します。

全0・全1だけでなく、ビット位置を識別できるデータやアドレス依存データを使い、レーン交換・上位ビット欠落・アドレスの別名化を検出します。メモリマクロのモデル・read/write競合の定義も固定します。これらの機能検証を、製造故障を対象にするMBIST・ATPGの代わりにはしません。

完了には、必須の境界・順序・競合へ到達し、同じトランザクションの内容と副作用が比較された証跡が必要です。タイムアウトで未解決を捨てたり、応答数だけの一致で合格にしたりしません。

## 6. 異常・故障と復帰

不正アドレス・権限・長さ、予約値、プロトコル違反、応答の遅延・停止、ECC・パリティなど、製品にある異常経路を選びます。各項目に、異常を起こす場所・条件、検出点、エラー応答・通知、許される副作用、封じ込め、復帰方法、期限を付けます。仕様が未定義の反応を、任意の期待値で固定しません。

ECCなら、対象符号が保証する故障モデルの下で、訂正可能・検出のみ・保証範囲外を区別します。通知が出るだけでなく、訂正データ、書戻し・scrub、エラーカウンタ、割り込み、影響しないチャネルの継続も仕様に応じて判定します。再試行で二重書込みなどの副作用が起きないかも確認します。

故障注入では、対象のビット・信号・部品、故障種別、注入時刻・期間、解除、観測窓を保存します。対象へ注入が届いたこと、検出・通知・封じ込め・復帰が実行されたことを別々に観測します。forceで対象を固定し続けたため復帰できない、といった試験側の影響も切り分けます。

正常な対照ケース、注入ケース、復帰後の正常ケースを一組にします。検出なし、検出したが反応が遅い、誤訂正、復帰不能、他機能への波及を分類します。仕様・安全分析に基づく故障モデルと分母がない結果から、診断網羅率や安全水準を主張しません。安全機構の条件を変更したら解析と試験の両方を再確認します。

## 7. 性能・負荷・進行性

単発の正しい応答に加え、単独・競合・偏った負荷、最大キュー長、長いバックプレッシャ、飽和と負荷解消後を検査します。仲裁では全要求元の競合、一部の連続要求、優先度変更、低優先度の進行を確認します。公平性や最大待ち時間は、環境が応答する条件も含めて仕様化します。

測定する値と区間を先に決めます。

- レイテンシ：要求の受理から、対応する応答の完了まで。最後のbeatを完了とするかなどを定義する。
- 帯域：測定区間で実際に完了した有効payload量／時間。提示した要求量やバス上の全転送量とは分ける。
- 進行性：要求元ごとの完了数・最大待ち・未解決件数。全体の帯域だけで一部の飢餓を隠さない。

測定窓をまたぐ要求、ウォームアップ、ドレイン、取消、クロック停止の扱いを固定します。リクエスタや応答モデル自身の帯域制限でDUTへ負荷が届いていない場合を見分けます。平均値だけで最大遅延の要求を判定しません。有限のシミュレーションで停止しなかったことと、[形式的な進行性の証明](formal-verification.md#2-要求から証明計画を作る)も区別します。

合否には、構成・クロック・負荷・測定窓・閾値・実測値・未解決数を残します。サイクル単位の性能検証と、実周波数を保証するSTA・シリコン評価は別に判定します。

## 8. 低電力・電源状態の遷移

RTLと電源意図記述（UPFなど）の版・対象ドメイン・階層を固定します。電源状態、合法／禁止の遷移、保持対象、アイソレーション、wake-up源、クロックとリセットの順序を検証計画へ展開します。[AccelleraのUPF資料](https://accellera.org/resources/videos/introduction-of-ieee-1801-2024-upf-4-0)も参照し、実際に採用する規格とツールの対応版を記録します。

アイドルだけでなく、処理中、割り込み保留、エラー中に停止・復帰します。要求の排出・取消、電源遮断前後の出力clamp、保持・非保持領域の値、復帰後の再初期化、wake-upの取りこぼし・重複を判定します。保持制御や復帰順序を意図的に変える試験は、仕様が定める異常反応に対応付けます。

電源オフの影響をモデル化できるpower-awareな環境で、状態遷移と境界の振る舞いを確認します。通常RTLで電源制御信号を切り替えただけでは、状態消失やアイソレーションを実際に検証したとは扱いません。Xの検査も、オフ領域内部と、値が規定されるalways-on側の境界を区別します。

完了には、必要な電源状態・遷移・保持データ・動作中の競合の結果と、静的な電源構造の確認をそろえます。消費電力、IRドロップ、EMなどは[14.3節](spec-to-verification-method.md#143-低電力設計と電源)の解析・実測へつなぎます。

## 9. 権限・セキュリティ・安全機構

資産、脅威・故障モデル、許可される操作、権限・ライフサイクル状態、保護機構を先に定義します。許可された操作が成功する対照ケースと、権限・状態・アドレスなどを一つ変えて拒否されるケースを作ります。デバッグ・テストモード、ロック後の変更、部分リセット、低電力復帰との組み合わせも確認します。

拒否応答だけでなく、データ・鍵・メモリ・レジスタへの副作用がないこと、別名アドレスや別経路から回避できないこと、通知・監査が仕様に従うことを判定します。鍵の消去を要求するなら、トリガから消去完了までの期限と、アクセス可能な残存コピーの範囲を定義します。

保護機構には6節の故障注入を対応付け、検出・安全な反応・復帰を確認します。[OpenTitanの対策検証](https://opentitan.org/book/doc/contributing/dv/sec_cm_dv_framework/index.html)は共通プリミティブを使う検査の実例ですが、その仕組みを採用しない設計にも自動で適用できるとは扱いません。

秘密値による出力・タイミングへの依存は、比較する実行の前提と観測範囲を定めます。機能テストだけで、物理的なサイドチャネルや実デバイスへの故障攻撃まで検証済みとはしません。必要な安全・セキュリティの専門評価と[14.8節](spec-to-verification-method.md#148-機能安全セキュリティ)へ接続します。

## 10. コードカバレッジの未達を閉じる

[covergroupによる機能網羅](functional-coverage.md)に加え、RTLの行・分岐・条件／式・toggle・FSM状態と遷移など、ツールが提供する指標から必要なものを選びます。同じ名称でも定義が同じとは限らないため、版・計測設定・階層・有効期間・除外前後の分母を保存します。リセット中の計測を除くなら、リセット動作の検査と計測を別に残します。

未達箇所ごとに、次のいずれかを調べます。

1. 仕様にはあるが、要求・機能モデル・試験から漏れた動作。
2. 刺激、仮定、構成、サンプリング・計測設定の不足。
3. デッドコードや誤った条件分岐など、RTLの問題。
4. 対象構成では使わないコード、または到達不能だと根拠を示せるコード。

追加テスト、checker・coverageの修正、RTLの修正、[到達性の解析](formal-verification.md#8-証明の抜けと検査の感度を点検する)、根拠付きの除外へつなぎます。到達しただけで結果を比較しないテストを、機能要求の合格には数えません。未達を消すためにRTLの分岐を削除する場合も、仕様・実装の変更としてレビューします。

除外には、箇所と版、指標、構成、理由、証明・設計判断、承認、失効条件を持たせます。正常入力では到達しない安全・セキュリティの保護経路も、故障注入では必要になることがあります。通常回帰の到達不能を、その経路の検証免除へ直結させません。

mergeするDBの入力・構成・計測定義・除外を照合し、元の実行IDを保存します。指標・階層・構成ごとに未達を報告し、全体の平均や単一の100%で隠しません。プロジェクトで定めた目標と除外の妥当性を併せて判断します。[OpenTitanの計測・レビューの運用](https://opentitan.org/book/doc/contributing/dv/methodology/index.html)と[Verilatorのcoverage説明](https://verilator.org/guide/latest/simulating.html#coverage-analysis)も参照先です。

## 11. 等価性とシステム・ソフトウェア統合

等価性検証では、比較元・比較先、構成、通常／テスト／低電力モード、状態対応、初期化、ライブラリ・ブラックボックス、分割・除外を固定します。合成、DFT、低電力要素、ECOの変更後に必要な比較を行い、未証明のpartitionや未対応点を合格へ足しません。仕様変更を含むECOは、振る舞いを変える範囲と維持する範囲を分けます。比較元の仕様適合と等価性の役割は[フォーマル検証](formal-verification.md#1-何をフォーマル検証で確認するか)に従います。

統合では、IP単体の結果に加えて接続・アドレスデコード・割り込み番号と極性・クロック・リセット・電源・設定値を照合します。重複・未割当アドレス、幅・エンディアン変換、外部IPの前提、バス競合を確認します。機械生成したRTL・ヘッダ・RALが一致しても、原本とシステム仕様の独立した照合は必要です。

実際のドライバ・ファームウェアで、起動、レジスタ操作、DMA、割り込み処理、エラー復帰、停止・復帰を実行します。割り込みのmask／clearとイベントの競合、CPU・DMAの同時アクセス、キャッシュや順序制約がある構成の可視性などを、採用するアーキテクチャに従って判定します。ソフトウェアの正常終了だけで合格にせず、転送データ・副作用・通知・未解決件数を確認します。

性能や観測機能が異なるエミュレーション・FPGA・実シリコンを使う場合は、その環境で判定できる要求を明記します。入力とIP・RTL・ソフトウェアの版、ボード・デバイス条件、モデルの制限を証跡へ含めます。

## 12. 物理・製造・実測の担当へつなぐ

機能検証の計画にも、次の担当・判定段階・証跡への接続を残します。詳細な合格値や必要コーナーは、製品・PDK・ライブラリ・契約・適用規格に従って決めます。

- [タイミング・制約](spec-to-verification-method.md#144-タイミング設計と制約)：未制約パス・例外、モードとコーナー、最終ECO後のSTA。
- [DFT・量産テスト](spec-to-verification-method.md#145-dft量産テスト)：scan・MBIST・ATPG、故障分類、ATE変換後の結果、テストモードの機能との競合。
- [論理実装・物理・製造適合性](spec-to-verification-method.md#146-論理実装物理設計製造適合性)：最終ネットリスト、DRC/LVS、電源・信頼性、製造データ。
- [AMS・I/O・パッケージ](spec-to-verification-method.md#147-アナログミックスドシグナルioパッケージ)：モデルの適用範囲、PVT、アナログ境界、実装・ボード条件。
- [シリコン・システム評価](spec-to-verification-method.md#149-ソフトウェアシステム統合ポストシリコン)：個体・ロット・電圧・温度・周波数、プレシリコンとの相関、エラッタ・回帰。

テープアウト前に必要な解析と、シリコン入手後に行う実測を区別します。後段階の項目を計画済みにしたことは、実測に合格したことではありません。

## 13. 小さなIPで追加する試験の例

既存の割り込みの12クロス目標・16個の機能目標を変更せず、別の要求・計画として次を追加する例です。以下は未実施で、対象RTLへそのまま投入できるテストではありません。リセット値・取消・受理条件などは、製品仕様から確定してから期待値にします。

| 試験案 | 刺激・条件 | 観測と判定 |
| --- | --- | --- |
| IRQ-RESET-RECOVERY-EXAMPLE | PEND保持・IRQ mask中・イベント受理との境界でリセットし解除する | 規定のリセット値・保持、解除後の最初のイベントと通知、古い通知の再出現 |
| IRQ-BUS-STALL-EXAMPLE | CSRアクセスへ待ちを入れ、イベントとW1Cを競合させる | 要求の提示と実際の受理を区別し、受理時刻に基づく更新優先・応答・副作用 |
| IRQ-ACCESS-DENY-EXAMPLE | 同じCSR操作を許可状態と禁止状態で行う | 許可側の更新、禁止側の応答と無副作用。権限機構がないなら根拠付きで対象外 |
| IRQ-LOAD-PROGRESS-EXAMPLE | 合法な最大頻度のイベントとCSRアクセスを継続し、その後負荷を止める | 仕様が保証する記録・通知・アクセスの遅延と復帰。sticky bitへイベント数の保存を勝手に要求しない |

各試験に構成、初期化、受理・完了、checker、観測目標、終了条件を付け、[機能間クロス](feature-interaction-verification.md)へつなぎます。低電力や非同期境界がある場合は、その状態遷移・停止・解除との組み合わせも追加します。

## 14. 記録と完了判定

領域ごとの適用判断から、要求、試験・解析、checker、観測目標、実行証跡、残課題まで追跡します。[適用範囲の雛形](../templates/verification-scope.md)で未確認を残し、[サインオフ記録](../templates/signoff-record.md)へ集約します。

完了の判断には、必須構成と領域の適用が確定し、必要な試験・解析の結果、比較・判定、未達・除外・残リスクのレビューがそろっていることが必要です。未実装、未実行、判定不能を対象外へ移しません。新機能、構成、接続、電源・リセット、故障モデル、ソフトウェアが変わったら、この一覧と依存する証跡を再評価します。
