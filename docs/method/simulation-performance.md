# シミュレーションの時間を測り、短くする

回帰が遅くなったら、まず時間の内訳を測ります。推測で最適化すると、効かない所を直したり、検査の強さを落としたりします。この文書は、内訳の測り方と、波形の出力・4値と2値・ビルドの分け方が時間にどう効くかを、手元で測った数値とともにまとめます。

## 1. 内訳を分けて測る

1回の実行の時間は、次の3つに分かれます。

| 部分 | 中身 | 測り方 |
| --- | --- | --- |
| ビルド | Icarusの変換、Verilatorの変換とC++のコンパイル | ビルドのコマンドだけを時間を測って実行する |
| 実行 | シミュレーターが回路を動かす時間 | ビルド済みの実行ファイルだけを実行する |
| ランナー | 入力の生成、ログの判定、証跡の保存、子プロセスの起動と待ち | Pythonの `cProfile` で、ランナー全体を動かす |

**壁時計の時間と、子プロセスのCPU時間を両方記録します。** 共有の計算機では、ほかの仕事のために壁時計の時間が大きく揺れます。CPU時間（ユーザーとシステムの和）は、混み具合の影響を受けにくい値です。Pythonでは `resource.getrusage(resource.RUSAGE_CHILDREN)` の差で、子プロセスのCPU時間を取れます。

**同じ条件で3回以上測り、中央値を使います。** 1回目だけキャッシュが冷えている、といった差を避けるためです。計算機の混み具合（負荷平均）も一緒に残します。

## 2. 手元で測った例

次の条件で測りました（2026-11-21）。

- 対象：[FIFOの例](../../examples/local-fifo/README.md)の `sync_fifo`（幅16・深さ16）を、乱数で読み書きする小さなテストベンチで20万サイクル動かす。テストベンチはこの測定のために書いたもので、リポジトリには入れていない。
- 計算機：macOS arm64。ほかの仕事と共有していて、負荷平均は120〜130。
- ツール：Icarus Verilog 14.0開発版（`ca6b8d3`）、Verilator 5.052（`--binary --timing`）。
- 各条件3回の中央値。

| 条件 | 壁時計（秒） | CPU（秒） |
| --- | --- | --- |
| Icarus：ビルド | 0.03 | 0.02 |
| Icarus：実行、波形なし | 2.88 | 0.72 |
| Icarus：実行、波形あり（VCD 36 MB） | 5.72 | 1.41 |
| Verilator：ビルド、`-j 1`、ccacheなし | 23.0 | 5.83 |
| Verilator：ビルド、`-j 4`、ccacheなし | 7.23 | 5.79 |
| Verilator：ビルド、`-j 4`、`--trace` つき、ccacheなし | 8.13 | 7.12 |
| Verilator：ビルド、`-j 4`、ccacheが効いた場合 | 0.53 | 0.35 |
| Verilator：実行、`--trace` なし | 0.29 | 0.071 |
| Verilator：実行、`--trace` つきで波形を出さない | 0.22 | 0.070 |
| Verilator：実行、`--trace` つきで波形あり（VCD 35 MB） | 0.37 | 0.134 |

壁時計の時間はCPU時間の3〜4倍で、混み具合のために大きく揺れています。比べるときはCPU時間を見ます。

この例から読めることです。

- **波形の出力は、実行のCPU時間をほぼ2倍にしました。** IcarusでもVerilatorでも同じ傾向で、VCDは20万サイクルで約36 MBでした。
- **Verilatorは、`--trace` つきでビルドしても、波形を出さなければ実行の時間は変わりませんでした。** ビルドのCPU時間は約2割増えました。
- **ビルドの並列（`-j 4`）は、壁時計の時間を約3分の1にしましたが、CPU時間は変わりません。** 並列は待ち時間を減らすだけで、計算の量は減りません。
- **ccacheが効くと、Verilatorのビルドはほぼ0になります。** 同じソースを何度もビルドする回帰では、ビルドの再利用の効果が大きくなります。
- **短い実行では、Verilatorの時間のほとんどがビルドです。** この例では、ビルドのCPU時間5.8秒に対し、実行は0.07秒でした。Icarusは逆に、実行がほとんどです。

## 3. 波形の出力

波形は、失敗の解析に欠かせない一方で、時間と容量を大きく使います。

- すべてのケースで全信号を出すのではなく、出す範囲（`$dumpvars` の階層）と期間（`$dumpoff`・`$dumpon`）を絞れます。このリポジトリの例は、ケースごとに波形を保存し、長い統計のケースでは先頭だけを出すもの（[誤り訂正の例](../../examples/local-fec-ber/README.md)）があります。
- 失敗したケースだけを、波形つきで実行し直す方法もあります。この場合は、同じseed・同じ入力で失敗が再現することを先に確かめます。再現しない失敗は、波形なしの最初の実行の証跡を残します。
- 波形を出すかどうかで結果が変わってはいけません。上の測定では、波形あり・なしで、テストベンチが最後に出す読出しの和が同じでした。

## 4. 4値と2値

Icarusは4値（0・1・X・Z）で、Verilatorは2値で動きます。上の測定で実行のCPU時間は約10倍違いましたが、Icarusは解釈して実行し、VerilatorはC++へ変換して実行するので、**この差のすべてが4値か2値かによるものではありません。**

- 2値のシミュレーターでは、Xは0か1になり、初期化の漏れやXの伝搬は見えません。このリポジトリでは、Xの確認が要る例はIcarusで実行し、リセットの漏れのように4値でも見逃すものは[フォーマル](../../examples/local-reset-x-formal/README.md)で確かめています。
- **シミュレーターを変えると、同じseedでも乱数の列が変わりました。** 上の測定で、`$random(seed)` に同じseedを与えても、IcarusとVerilatorで最初の値から違いました（読出しの和も違いました）。このリポジトリの多くの例は、刺激をPythonで作ってファイルで渡すので、シミュレーターを変えても刺激は変わりません。シミュレーターを変えて速くするときは、刺激が同じであることを先に確かめます。

## 5. ビルドの分け方

- **同じ構成のビルドを、ケースの間で使い回します。** このリポジトリの[共通シミュレーションランナー](../../examples/local-common/README.md)は、構成と変異の組ごとに1回だけビルドし、そのビルドで固定・ランダム・診断のケースを実行します。
- **並列は、ビルドの壁時計の時間を減らします。** 計算機の数（コア数）以上には効かず、ほかの仕事と共有しているときは効きが小さくなります。
- **ccacheのような道具は、同じソースのビルドを速くします。** ソースやオプションが変わると効きません。測るときは、キャッシュが効いた結果と効かない結果を分けて書きます。上の表では、ccacheを止めた値（`CCACHE_DISABLE=1`）と、効いた値を分けています。

## 6. ランナーの時間を見る

FIFOの例のランナーを `cProfile` で動かすと、全体0.37秒のうち、11回の子プロセス（ビルドと実行）の起動と待ちが0.34秒でした。Python自身の処理（入力の生成、ログの判定、証跡の書出し）は約0.03秒です。

```sh
python3 -m cProfile -o fifo.prof examples/local-fifo/run.py --out artifacts/fifo-profile
python3 -c "import pstats; pstats.Stats('fifo.prof').sort_stats('cumulative').print_stats(12)"
```

この例では、ランナーを速くしても全体はほとんど変わりません。ケースが多く1回が短い例では、子プロセスの起動の時間が目立つようになります。その場合は、1回の起動で複数のケースを実行する形にできますが、ケースの間で状態が残らないこと（リセット、乱数の状態、ファイル）を別に確かめる必要があります。

Verilatorには、実行の内訳を出すオプション（`--prof-exec` と、付属の `verilator_gantt` など）があります。この文書の測定では使っておらず、結果は確かめていません。使い方はVerilatorの説明書で、使う版のものを確かめてください。

## 7. 速くするときに守ること

- **検査の強さを落として速くしない。** 波形を減らす、ケースを減らす、seedを減らすときは、何を確かめなくなるかを記録します。ケースの選び方は[検証の削減](verification-reduction.md)にあります。
- **速くした前後で、同じ入力の結果が同じであることを確かめる。** 判定の件数、JUnitの件数、最後の出力が一致することを見ます。
- **時間の上限を、短くなった時間に合わせて詰めすぎない。** 混んだ計算機では時間が数倍になります。このリポジトリのCIは、統合ランナーにコマンドの上限60秒を渡しています。上限の扱いは[統合ランナー](../../tools/REGRESSION.md)と[継続的リグレッション](continuous-regression.md)にあります。

## 8. この文書の範囲

数値は、1つの小さなテストベンチを、混んだ1台の計算機で測ったものです。回路の大きさ、信号の数、テストベンチの書き方、計算機が違えば、比は変わります。手順の参考として使い、自分の回路では測り直してください。商用のシミュレーターは扱っていません。
