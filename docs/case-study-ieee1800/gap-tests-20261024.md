## 確認方法

照合の区間ごとに、テストと照合案を書く担当と、それを反証する検証担当を別のエージェントにしました（[手順書](requirements-to-tests-method.md)の6〜8節）。
今回検証したのは次の13区間です。

- p02（6.3.2.1〜6.16）、p03（6.16.1〜7.3）、p04（7.3.1〜8.25）、p06（10.10〜11.12）、p11（18.17.6〜20.4.1）
- p16（24.3〜28.5）、p17（28.6〜30.4.7.3）、p18（30.5〜32.8）、p19（32.9〜37.9）
- p21（37.17〜37.31）、p22（37.32〜37.54）、p23（37.55〜37.85）、p24（38.2〜38.36.2）

検証担当は、PDFの該当節から期待結果を独自に導き、テストの出力・診断と突き合わせました。
シミュレータでの実行も、Icarus Verilog 13.0とVerilator 5.052（seed 1/73）で確かめています。

| 対象 | 判定 | 採用 | 却下・欠陥 |
| --- | ---: | ---: | ---: |
| 照合案 | 2,215 | 2,049 | 166 |
| 新規テスト | 624 | 594 | 30 |

- 採用された照合案のうち4件は、取り込んでいません。
  3件は欠陥とされたテストか未検証の区間のテストを、1件のAND集合は未検証の区間のテストを含むためです。
- 同じ要求に複数の案が採用された場合は、最初の案だけを取り込みました。
- 欠陥とされた30本と、未検証の区間のテストは`tests/`に入れていません。

欠陥とされた30本の内訳は次のとおりです。

| 欠陥の種類 | 本数 |
| --- | ---: |
| 違法系の`:expected_stderr_regex:`が、違反の行ではなく前後の合法な行を指す | 6 |
| 違法系に、意図した違反とは別の違反が同じ箇所にある（例：automaticタスクの項目への階層参照、13.3.1） | 3 |
| 正常系に、規格上合法といえない構文がある | 4 |
| 強度を出力するのに`:fourstate: no`になっている | 5 |

## 実行証跡

| 実行回 | 結果 |
| --- | --- |
| `coverage/results/gap-tests-20261024-icarus13.json`（Icarus Verilog 13.0、v13_0-dirty） | 239 pass、355 known |
| `coverage/results/gap-tests-20261024-verilator-seed1.json`（Verilator 5.052、seed 1） | 203 pass、391 known |
| `coverage/results/gap-tests-20261024-verilator-seed73.json`（Verilator 5.052、seed 73） | 203 pass、391 known |
| `coverage/results/gap-refinement-20261024-*.json`（下記の3本の再実行） | 各3 known |

- 2つのseedの結果は、すべてのテストで一致しました。
- 違法系では、実行器は診断の行番号だけを照合します。
  そのため、Icarusの33本とVerilatorの14本は、構文の非対応など別の理由で同じ行を拒否して`pass`になっています。
  これらのシミュレータは`:oracle:`に記録していません。違法系の実行確認には`:oracle:`の記録が必要です（[管理手順](coverage-rules.md)）。
- Verilatorで成功する正常系のうち3本は、`:fourstate: yes`なので`:oracle:`にVerilatorを記録していません。
  これは、Verilatorを記録するテストを`:fourstate: no`に限る決まりによるものです。

## 取り込み後に直したテスト

3本を直しました。

`tests/ch8/test_param_class_package_vs_module_instance_specializations.sv`の`module holder (input int d);`を、`input var int d`に直しました。

- ANSI形式のポートで種類（net/var）を省いた`input`は、既定のネット型のネットになります（23.2.2.3）。
- ネットに使えるデータ型は4状態の整数型などに限られ、2状態の`int`は使えません（6.7.1）。
- 規格自身も、2状態型の入力ポートの例では`input var int`と書いています（23.2.2）。

p06とp16の検証担当が、ほかの3本を同じ理由で欠陥と判定しました。そこで、採用分を同じ観点で点検し、この1本が該当しました。

次の2本からは、`:lrm:`の引用節を1つずつ外しました。

- `tests/ch37/test_vpi_interface_tf_decl_relations.sv`：25.7.4
- `tests/ch30/test_specify_pulse_trailing_edge_limits.sv`：30.7.3

どちらも、使う構文の背景として引いた節で、その節の要求は対応付けていません（コメントの説明は残しています）。
引用した節にはそれぞれ2本以上のテストが必要です（`coverage_depth.py --check --minimum-tests 2`）。この2節を引用するテストは、ほかにありませんでした。

3本とも、観測する動作と期待出力は変わりません。直した後に両シミュレータで再実行し、台帳の入力ハッシュを更新しました。

## 既存テストへの指摘

同じ形のポート宣言は、次の既存テスト7本にもあります。
既存テストの入力は、照合では変更しない方針なので、今回は直していません。

ほかの6本は、ポートの種類を観測していません（VPIを使っていません）。

## ツールの修正

`tools/matching_kit/merge.py`は、統合済みの保留判断を、説明文が同じかどうかで見分けています。
統合後に説明文の先頭へ指摘番号（`M98: `など）を付けると、別の判断とみなして再び追加していました。
番号を除いて比べるように直しました。この不具合で重複して追加された32件（M98〜M129と同じ判断）は削除しています。
