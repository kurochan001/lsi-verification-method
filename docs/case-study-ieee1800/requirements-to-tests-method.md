# IEEE 1800-2023のPDFから要求を抽出し、テストで検証する手順

本資料はkirimasim-testsでの適用記録です。数値・ツール版・作業状況は本文に記載した確認時点のもので、パス・コマンド・CIは特記のない限り複製元の構成を前提とします。[実行に必要なファイルと復元先](../../tools/README.md#動作確認する場所と依存ファイル)も参照してください。

この文書は、規格のPDFを出発点に、要求台帳を作り、既存テストとの照合と新規テストの作成で検証を積み上げ、網羅率を計測するまでの手順をまとめたものです。
2026-10-22〜24の作業（要求の全抽出、20%→52.2%までの照合・テスト追加、台帳の見直し）で使った方法を、別の担当者が同じ結果を再現できる形で書いています。
作業はまだ途中で、未完了の部分は「既知の限界」に書いています。

関連資料: [要求抽出の結果](requirement-extraction.md) / [未解決事項](requirement-extraction-notes.md) / [計測規則と更新手順](coverage-rules.md) / [テストの書式](https://github.com/kurochan001/kirimasim-tests/blob/0da4f2fc/README.md#test-format) / [半導体の仕様書への一般化](../method/spec-to-verification-method.md)

## 1. 前提と原則

- **規格の本文を複製しない。** PDFと抽出テキストはリポジトリの外に置きます。台帳・テスト・コメントには、要求を自分の言葉で書き、節番号と出典ブロックIDを引用します。ヘッダの定数名と値、予約語のように、インターフェースそのものである事実は扱えます。
- **期待値は規格から先に決める。** シミュレータの出力を期待値に写しません。シミュレータは、期待値を確かめるためと、`:oracle:`を記録するためだけに使います。
- **作った者と確かめる者を分ける。** 照合案と新規テストは、作成者とは別の検証者が反証を試み、合格したものだけを台帳へ取り込みます。不確かなものは却下します。
- **AIのレビューは人の承認ではない。** 台帳の`reviewer`欄と資料に、その旨を必ず書きます。
- **数値を守るより正しい集計を優先する。** 誤りが分かった対応は取り下げ、基準値は理由を付けて書き直します。

## 2. 全体の流れ

```text
PDF ─┬─> A. 出典索引・節台帳（位置とハッシュだけ）
     └─> B. 要求の抽出と出典監査（behaviors.json / requirement-audit.json）
              │
              ├─> C. 台帳の見直し（観測可能な形への組み替え、解釈保留の解消）
              │
              ├─> D. 既存テストとの照合 ──┐
              ├─> E. 新規テストの作成 ────┤─> F. 独立した検証 ─> G. 統合・計測・記録
              └─> E'. 表形式の要求の生成テスト ┘
```

各段階の成果物は`coverage/`の台帳と`docs/`の資料で、Gの統合時にまとめて検査します。

| 段階 | 主な成果物 | 次へ進める条件 | 詳細 |
| --- | --- | --- | --- |
| A. 出典索引・節台帳 | `requirement-source-index.json`（ページ・行の位置、ブロックのSHA-256）、`standard-sections.json` | 全節の位置とブロック境界を記録する。本文は含めない | [4章](#4-段階ab要求の抽出と出典監査) |
| B. 要求の抽出と出典監査 | `behaviors.json`、`requirement-audit.json` | 全ブロックを分類し、要求の`source_spans`と双方向に照合する | [4章](#4-段階ab要求の抽出と出典監査) |
| C. 台帳の見直し | 書き直した要求行、`source_note`の経緯、理由付きの基準値 | 解釈保留は規格内部の根拠で解消するか、決め手として欠けているものを記録する | [5章](#5-段階c台帳の見直し) |
| D. 既存テストとの照合 | 照合案（`checks`・`evidence`）、`test-matching-reviews.json` | 誤実装なら期待出力が変わると、具体的な値で説明できる場合だけ登録する | [6章](#6-段階d既存テストとの照合) |
| E／E'. 新規テストの作成・生成 | `tests/`のテスト、`generators/`の生成器、`:oracle:` | 期待値を規格から先に決め、シミュレータで確かめる | [7章](#7-段階e新規テストの作成) |
| F. 独立した検証 | テストの判定（`testverdict`）、照合案の判定（`verdict`） | 作成者とは別の検証者が反証を試み、合格したものだけを残す | [8章](#8-段階f独立した検証) |
| G. 統合・計測・記録 | `coverage/results/`の結果、統合した台帳、生成物、文書 | 全検査が通り、統合直前の入力が承認時の入力と一致する | [9章](#9-段階g統合計測記録) |

## 3. 準備

### 3.1 資料

- 規格のPDFと、`pdftotext -layout`で抽出したテキスト（`out/lrm_pdftotext_layout.txt`）を、1つの資料ディレクトリに置きます。ツールの既定の場所は`tools/requirement_source.py`の`DEFAULT_SOURCE`です。
- PDFと抽出テキストのSHA-256は、`coverage/standard-sections.json`と`coverage/requirement-source-index.json`に固定されています。
  `python3 tools/behavior_coverage.py --check --verify-source <資料dir>`で、手元の資料が同じ版であることを確かめます。

### 3.2 シミュレータ

保存済みの実行証跡と同じ版を使います。版が違う結果は、別の実行回として扱われます。

| シミュレータ | 版 | 用途 |
| --- | --- | --- |
| Icarus Verilog | 13.0（`Icarus Verilog version 13.0 (stable) (v13_0-dirty)`） | 第一の確認先。`iverilog@13.0` |
| Verilator | 5.052 | Icarusが規格に従わない、またはコンパイルできない場合。seed 1と73の両方で一致したら`verilator@5.052` |

Icarus 13.0は、`v13_0`タグからビルドします。macOSでは、次の2点が必要です。

- Homebrewのbison（`PATH=/opt/homebrew/opt/bison/bin:$PATH`）を使う。
- `driver/main.c`の`#include "ivl_alloc.h"`の後に、`#if defined(__APPLE__)` `#include <mach-o/dyld.h>` `#endif`を足す。

ビルドしたものは、実行ファイルの位置からライブラリを探すので、場所を移しても動きます。
`run_icarus.py --iverilog-bin <dir>/bin`で指定します。Verilatorは`OBJCACHE=ccache`を付けるとビルドが速くなります。

照合案の受付、検証者の判定、統合を機械化した補助スクリプトです。使い方は[キットのREADME](../../tools/matching_kit/README.md)にあります。
照合案・判定・メモは、リポジトリ外の作業ディレクトリに追記型のJSONLとして置きます。リポジトリを変えるのは`merge.py`だけです。

承認時スナップショットの照合は、2026-10-26に本リポジトリで加えた改訂です。承認後に照合案・テスト入力・関連要求が変わった場合や、スナップショットのない旧形式の承認では、新規の統合を停止します。変更後の内容を独立にレビューしてから承認し直します。ケーススタディ当時の上流ツールとの差は[照合キットの説明](../../tools/matching_kit/README.md#workflows)と[由来](../../PROVENANCE.md)に記録しています。

## 4. 段階A・B：要求の抽出と出典監査

[要求抽出の結果](requirement-extraction.md)と[計測規則](coverage-rules.md)に詳しい規則があります。要点は次のとおりです。

1. **出典索引**：全1,740節について、PDFのページと行の位置、出典ブロックの境界、各ブロックのSHA-256を記録します（`requirement-source-index.json`、本文は含めない）。
2. **節台帳**：各節の規定と参考の別、状態（`unreviewed`→`in_progress`→`complete`／`no_behavior`）、確認メモを記録します（`standard-sections.json`）。
3. **要求の行**（`behaviors.json`）：1行は「1つの条件または観測の単位」です。
   - `id`、`clause`、`kind`（`normal`／`error`／`boundary`）、`modality`、`behavior`、`acceptance`、`source_note`、`source_spans`（節とブロックID）、`checks`を持たせます。
   - `checks: []`は未対応の意味です。
4. **出典監査**（`requirement-audit.json`）：全ブロックを`requirements`／`heading`／`informative`／`example`／`reference`のどれかに分類します。`requirements`の場合は、どの要求に対応するかを書きます。`source_spans`と双方向で照合されます。
5. **解釈保留**：規格の中で整合しない記述は、`interpretation_issue`を付けて行に残し、節を`in_progress`にします。この行にはテストを対応付けられません。
6. **分母**：登録行の全体が暫定値の分母です。`denominator_review.state`は、意味上の重複整理と保留の解決を経て承認されるまで`pending`のままにします。

抽出のときに守ること（見直しで分かったこと）：

- **観測できる形で書く。** 「予約されている」ことは、識別子に使うと拒否されることでしか観測できません。このような行は、最初から`kind: error`で書きます。
- **正常系と違法系を1行に混ぜない。** 「Xは受理され、Yは拒否される」は2行に分けます。照合の道具が、正常系の行に違法系テストを対応付けることを拒むためです。
- **実装依存の前提を受入条件で固定する。** 例：`begin_keywords`を書かないときのキーワード集合は実装依存なので、版を明示した範囲で書く。
- **使い方の規則（アプリケーション側の義務）や値の意味づけは、ヘッダの宣言を述べる行と分ける。** 例：「各値形式に対応するメンバー」「ユーザーは直接インクルードしないこと」。宣言は宣言の行に、使い方は使い方の行にします。
- **既存の行と意味が重なる行を増やさない。** 分母が膨らみ、確定値の承認が難しくなります。

## 5. 段階C：台帳の見直し

### 5.1 観測可能な形への組み替え

要求IDと`source_spans`を保ったまま、`kind`、`behavior`、`acceptance`を書き直し、`source_note`に変更の日付と理由を追記します。
要求の内容が変わるので、基準値を理由付きで書き直します。

```sh
python3 tools/behavior_coverage.py --write-baseline --update --require-source-reviewed \
  --history coverage/behavior-history.json --reason '具体的な理由'
```

分母のSHA-256は変わります。変更前後の割合を比べるときは、分母を明記します。

### 5.2 解釈保留の解消

規格の公式な正誤表がないことを前提に、次の基準で判断します。

- **解消する**：規格の内部に決定的な根拠がある場合。
  - 本文の綴りが、規範的なヘッダ（附属書I/K/M）やAPI・構文・表の定義と食い違い、定義側が一貫している場合。
  - 式の誤りが、同じ概念を定める本文や他の式から一意に復元できる場合。
- **保留を続ける**：規範どうしが実質的に衝突し、どちらを採っても他方を捨てる場合。根拠が推測にとどまる場合。

手順：

1. 論点ごとに、分析担当が判断・根拠（節とブロックID）・書き直した要求文・節の確認メモを作る。
2. 別の検証担当が反証を試みる。
3. 採用された論点の行から`interpretation_issue`を外し、`source_note`に採用した解釈を追記する。
4. 節に他の保留が残らなければ、`standard-sections.json`と`requirement-audit.json`の両方で`complete`にする。
5. 保留を続ける論点には、[未解決事項](requirement-extraction-notes.md)に「決め手として欠けているもの」を書く。

書き直した要求文が、正常系と違法系の混在を新たに作っていないかも確認します（4章）。

## 6. 段階D：既存テストとの照合

### 6.1 候補と制約

- 候補は、要求の節を`:lrm:`で引用しているテストに限られます（`behavior_coverage.validate()`の制約）。
- 違法系の要求（`kind: error`）には、`:should_fail_because:`付きの違法系テストだけを対応付けられます。
- 解釈保留の行、既存の保留判断がある組、取り下げ済みの組、利用禁止のテストは使えません。

### 6.2 対応を登録する基準

1. 要求の`behavior`・`acceptance`・`source_spans`と、該当節の本文・図表を読む。
2. テストの`.sv`、C helper（`:vpi_c:`／`:dpi_c:`）、include、期待出力まで読む。
3. 「この動作を誤実装したら期待出力が変わるか」を、具体的な値・時刻・型・対象で答えられる場合だけ登録する。
4. 次のものは、要求全体の証拠にしません。
   - 引用節・テスト名・説明文・APIが呼ばれた事実だけ
   - 非NULLだけの確認、常に0でも通る検査、真になる入力しかない比較
   - 別の型へ代入して元の型が見えない確認
   - count／typeだけで対象の同一性を見ない検査
   - 規格が順序を決めない評価（同じ式の中の関数呼び出しの順など）に依存する観測
5. 独立した複数条件の一部しか見ていなければ登録しません。全条件を複数のテストで分担できるなら、`check_groups`（グループ内はAND、グループ間はOR）にします。
6. `checks`には、テスト、日本語の観測内容と誤実装との区別、日付、担当、入力digest、`evidence`（刺激の行と期待出力の行の文字列anchor）を残します。

### 6.3 保留判断

対応を見送った理由が後の作業に役立つ場合は、`test-matching-reviews.json`に記録します。

- 区分は`partial_observation`／`oracle_issue`／`citation_refinement`／`compound_requirement`です。
- 説明文の先頭に、通し番号（M01、M02…）を付けます。
- 期待値が規格と矛盾するテストや、正常系なのに違法な構文を含むテストは`oracle_issue`です。テスト自体はこの作業では直しません。

### 6.4 実績

照合だけでは、区間あたり8〜35要求（未対応要求の約6〜15%）しか採用されませんでした。
主な理由は、要求の条件を刺激する既存テストがそもそも無いことです。照合は最初に安く済ませ、残りは新規テストで埋めます。

## 7. 段階E：新規テストの作成

### 7.1 共通の規則

READMEの「Test format」「Metadata」「How a test is judged」「Tests with C code」「Where the expected outputs come from」「Contributing」に従います。要点は次のとおりです。

- `tools/new_test.py chNN test_<内容> --lrm "節 ..."`で雛形を作ります。置き場所は、先頭の引用節の章のディレクトリです。対応付ける要求の節は、必ず`:lrm:`に含めます。
- 1本で、密接に関連する1〜数個の要求を完全に検証します。誤実装なら出力が変わるよう、対照となるケースを入れます（真と偽、境界の両側、x/zを扱う要求ではxとzの両方）。出力は規格が決める値だけにし、実際の値を表示します。
- 期待値を先に書き、`runsim`で確かめます。一致しなければ、まず自分の期待値を規格で確かめ直します。シミュレータ側の誤りなら、`docs/simulator-differences.md`とテストのコメントに書きます（未対応の構文は記録しない）。
- `:oracle:`の付け方：
  - Icarus 13.0が一致すれば`iverilog@13.0`を付ける。
  - Verilatorのseed 1と73の両方が一致すれば`verilator@5.052`を付ける。
  - どちらも一致しなければ`spec`だけにする。
  - kirimasimとLyraの結果は`:oracle:`に記録しない。これらは、期待値の裏付けを増やすための比較用です（nightlyで実行）。
  - `:fourstate:`と`` `timescale ``は実態に合わせる。
- 違法系のテストは、`kind: error`の要求にだけ使います。エラーは1つだけにし、`:expected_stderr_regex:`でファイルと行を示します。未対応構文のエラーを、規格違反の検出と取り違えないようにします。
- コメント行を「Verilator」という語で始めないでください（BADVLTPRAGMAになる）。実行に数秒以上かかるテストや、巨大なメモリを使うテストは避けます。

### 7.2 VPI・DPIのテスト

- CとC++の両方でコンパイルできるように書き、`extern "C"`で囲みます（VerilatorはC++としてコンパイルする）。
- Verilatorは、`vpi_register_systf`で登録したシステムタスクを呼べません。Verilatorでも動かしたい出力は、`cbStartOfSimulation`などのコールバックか、`vlog_startup_routines`から出します。
- 標準ヘッダだけをインクルードします（`vpi_user.h`、`sv_vpi_user.h`、`svdpi.h`、Cライブラリ）。
- どちらのシミュレータでも動かない`:oracle: spec`のテストは、1800-2023版の標準ヘッダ（Verilator同梱の`vltstd`）に対して、CとC++の両方でコンパイルできることを確かめます。

### 7.3 ヘッダの規定を検証する技法

附属書I/K/L/Mのような、ヘッダの定数・宣言の要求に使った技法です。

- **定数**：`#ifdef`で囲み、未定義なら行が欠けるようにします。値は`enum`の初期化子に使い、整数定数式でなければコンパイルを止めます。さらに`1 / (INT_MIN <= c && c <= INT_MAX)`でint範囲外も止めたうえで、数値を出力します。
- **型と宣言**：`SAME_TYPE(e, T)`で、評価されない式の型を完全一致で比べます。Cでは`_Generic`、C++では`decltype`と自作の`same<A,B>`テンプレートを使います（`<type_traits>`は使えない）。関数はリンクされないので、シミュレータが実装していない関数でも宣言だけを検査できます。
- **構造体**：フィールドの順序は`offsetof`の大小で確かめます。共用体であることは、全メンバーの`offsetof`が等しいことで確かめます。typedef名は、ポインタ型の一致で確かめます。
- **ガード**：アプリケーション側で先にガードマクロと別の型を定義し、ヘッダが型定義を省くことを確かめます（省かなければ二重定義でコンパイルが止まる）。2つのヘッダを順に読み込む方法でも確かめます。二重インクルードの検査では、マクロを別の値に定義し直してから読み込み、値が保たれることを見ます。
- **マクロの値**：`#if`は未定義の名前を0として扱うので、`defined()`も確かめるか、Cの定数式へ退避して比べます。式そのものが規定されている場合は、展開結果を文字列化して比較します。
- **自己確認**：規格本文のソースから復元した参照ヘッダに対して、テストをネイティブでコンパイル・実行し、期待出力と一致することを確かめます。

### 7.4 表形式の要求は生成器で作る

1行が「表の1セル」に当たる要求（予約語、定数など）は、`generators/`に生成器を書きます。

- 参照モデルは規格の表から作ります。表どうしの一致（例：版ごとの追加分の和が附属書Bと一致すること）を、生成器の中で検査します。
- 違法系のケースは`Case(should_fail_because=...)`とし、本文のエラー行を「`// illegal`」で終えます。`common.render`が、その行番号から`:expected_stderr_regex:`を作ります。
- 実行結果から`generators/oracles.txt`に`:oracle:`を記録し、`generate.py`で書き直します。`record_oracles.py`は、`--verilator`を付けると対象外の生成テストまで`spec`に戻すので、新しいケースだけを同じ規則で追記します。
- 生成器のコメントを直すと、エラーの行番号が変わることがあります。照合案のanchorも合わせて直します。

## 8. 段階F：独立した検証

検証者は、作成者の説明を鵜呑みにせず、規格本文とテストを自分で読んで反証を試みます。

- **テストの判定**（`testverdict`）：期待出力の全行を規格から自分で導いて照合します。合法性、決定性、メタデータ、lint、`:oracle:`の記載と実際の一致も確かめます。期待値が規格から導けないテストは`defective`です。
- **照合案の判定**（`verdict`）：刺激が要求の全条件を起こし、期待出力が誤実装と区別できる場合だけ`accept`にします。テストが`defective`なら`reject`、不確かなら`reject`です。
- **変異による検出力の確認**：規格どおりのヘッダや入力を1か所ずつ誤らせ、出力が変わるかビルドが止まることを確かめます（変異試験）。
- **大量の機械的な案**：独立に抽出した値（例：PDFの表から別の方法で取り出した一覧）との照合結果に基づいて、スクリプトで一括判定してよいことにします。
- **横展開**：検証者がある種類の欠陥を見つけたら、採用済みの全件を同じ観点で点検します。
  2026-10-24には、`input int`で欠陥とされた3本をもとに点検し、採用済みの1本と既存テスト7本に同じ形が見つかりました。
- **実績**：2026-10-24の13区間では、新規テスト624本のうち30本（約5%）が欠陥、照合案2,215件のうち166件（約7%）が却下でした。
  欠陥30本のうち、期待値そのものの誤りは4本でした。残りは、規格が決めない値の出力（7本）、設計の合法性（7本）、違法系のエラー行（6本）、メタデータ（5本）、書きかけ（1本）です。

これまでの検証で見つかった穴（同じ種類の誤りを最初から避けるためのチェックリスト）：

| 指摘 | 対策 |
| --- | --- |
| `(int)`キャストで、浮動小数の定義を区別できない | `enum`の初期化子に使う |
| int範囲外の値が切り詰められて一致する | 範囲検査で0除算させる |
| 共用体であることを確かめていない | 全メンバーの`offsetof`が等しいことを見る |
| ガードは定義の有無しか見ていない | 先にガードを定義して、ヘッダが省くことを確かめる |
| `#if`は未定義の名前を0として扱う | `defined()`を併用するか、Cの定数式へ退避する |
| 未定義動作に依存する検査（例：32ビットのシフト） | 対応付けを見送る |
| 複合要求の一部（z側だけ、縮む場合がない、片方の向きだけ）しか観測していない | 対照のケースを足すか、AND集合にする |
| 個数だけで、同一性を見ていない | 対象の名前・値で照合する |
| 同じ`$display`の中の評価順に依存する | 規格が順序を決めない観測をしない |
| 違法系の`:expected_stderr_regex:`が、違反の前後にある合法な行を指す | 「`// illegal`」の行と照らし、正しい実装がその行で報告することを確かめる |
| 違法系に、意図した違反とは別の違反が重なる（例：automaticタスクの項目への階層参照） | 違反を1つにし、それを除いた設計にエラーがないことを確かめる |
| ANSI形式で種類を省いた入力ポートで、ネットに使えない型（`input int`などの2状態型、仮想インターフェース）を使う | `input var int`のように`var`を付ける（23.2.2.3、6.7.1） |
| 違反の行に付けた説明のコメントが、それ自体で違反になる（`` `line ``と同じ行のコメントは22.12で禁止） | 指令の行にはコメントを置かない |
| 強度やtri-stateを出力するのに`:fourstate: no`になっている | 強度の構文を使うテストは`:fourstate: yes`にする |
| 未サイズの値の`$bits`、同時刻の事象の順序、VPIの反復順や要素名のように、規格が決めない値を出力する | 出力しないか、規格が決める形に変える |

## 9. 段階G：統合・計測・記録

1. `defective`のテストと、判定のないテストを取り除きます（または、リポジトリ外へ退避します）。生成物は`tests/`を全件走査するので、未検証のテストを作業ツリーに残したまま再生成しないでください。
2. 残ったテストのlintを通し、事前実行で`:oracle:`の記載と実際の結果が食い違わないことを確かめます。
   新しいテストが、ほかに引用するテストのない節を1本だけで引用していないかも、ここで`coverage_depth.py --check --minimum-tests 2`で確かめます。引用した節には2本以上のテストが必要です。背景として引いただけの節なら、`:lrm:`から外します。
3. 記録用に本実行し、`coverage/results/<名前>-<日付>-icarus13.json`、`-verilator-seed1.json`、`-verilator-seed73.json`として保存します。全件の結果は上書きしません。部分実行の結果も合成しません。
4. 採用された案を統合します。統合は「未対応の要求」だけを受け付けます。この参照実装では、テストと照合案を確定し、独立レビューと承認時スナップショットの記録を済ませてから統合します。統合直前の入力が承認時の入力と一致しなければ、統合を停止して再レビューします。

   ```sh
   python3 tools/matching_kit/merge.py <work>/proposals/<wave> \
     --reviewer '<モデル名> (AI); not an independent human review' --date YYYY-MM-DD
   ```

5. 生成物を更新します。

   ```sh
   python3 tools/behavior_coverage.py --update --require-source-reviewed --history coverage/behavior-history.json
   python3 tools/requirement_matching.py --update
   python3 tools/suite_stats.py --update
   python3 tools/suite_catalog.py --update
   python3 tools/coverage_depth.py --update
   ```

   統合した後でテストを直した場合は、次のようにします。
   - 直したテストを再実行し、`coverage/results/<名前>-refinement-<日付>-*.json`のように別名で保存します。
   - 刺激・期待値・要求との対応を独立に再レビューし、承認後に台帳の`inputs_sha256`を新しい入力で計算し直します。
   - 基準線との差になるので、`behavior_coverage.py --update --require-source-reviewed --write-baseline --reason '<理由>'`で理由を残します。
   - `--history`は、作業の最後に1回だけ付けます。付けるたびに、履歴が1件増えます。

6. 文書を更新します：結果報告（新規）、README、`coverage/README.md`の結果ファイル一覧、`docs/nightly-results.md`のmain集計、累積の指摘資料、`docs/simulator-differences.md`。
7. 全検査を通してからコミットします。

   ```sh
   python3 -m unittest discover -s tools -p 'test_*.py'
   python3 tools/behavior_coverage.py --check --require-source-reviewed --verify-source <資料dir>
   python3 tools/requirement_matching.py --check
   python3 tools/suite_stats.py --check
   python3 tools/suite_catalog.py --check
   python3 tools/coverage_depth.py --check --minimum-tests 2
   python3 generators/generate.py --check
   python3 tools/lint_metadata.py
   git diff --check
   ```

8. push した後、最初のnightly（または手動実行）で、すべてのシミュレータのジョブが最後まで走ったことを確かめます。
   新しいテストが、シミュレータを暴走させることがあるためです。2026-10-24には、違法なシーケンスの循環でVerilatorが再帰を止めず、ランナーのメモリを使い切ってジョブが止まりました。いまはVerilatorのジョブでプロセスごとのメモリを制限しています。

### 計測の読み方

- **暫定値**：全登録行を同じ重みで数えます。附属書の定数や予約語は、1個が1行です。このため、それらの行で値が大きく動きます。全体の値と並べて、本文（1〜40章）だけの値と章別の内訳を必ず載せます。
- **実行確認**：証跡の入力・ランナーのハッシュが現行版と一致する`pass`だけを数えます。`known`、`unsupported`、`fail`、古い入力は数えません。
  違法系の要求は、`:oracle:`に固定版のトークンがあるシミュレータの結果だけを数えます。
  AND集合は、同じシミュレータの同じ実行回でメンバー全員が成功した場合だけ数えます。
- **確定値**：分母の承認（意味上の重複整理と解釈保留の解決）までは出しません。

## 10. 並列化と費用

規模の大きい照合とテスト作成は、要求を節の順に約220要求ずつの担当範囲に分けて、並列に進めました。

| 構成 | 内容 | 実績 |
| --- | --- | --- |
| 照合担当＋検証担当 | 引用テストのある要求を照合する | 1組で約50万〜65万トークン。採用は8〜35要求 |
| テスト作成担当＋検証担当 | 照合で埋まらない要求に新規テストを書く | 作成担当1体で10〜76本のテストと、数十〜200件超の対応案 |
| 照合とテスト作成を1体で | 既存テストで足りればそれを使い、足りなければ書く | 引用テストのない範囲では、実質テスト作成 |
| 検証だけ | 作成済みの案とテストを検証する | 1体で約15万〜40万トークン |

- 同時に動かす担当は、マシンの負荷（シミュレータのビルド）を見て決めます。今回は18コアで、load average 6〜9程度でした。
- **中断と再開**：照合案・判定・テストの一覧は、すべて追記型のファイルに残します。中断時は、未検証のテストをリポジトリ外へ退避します。再開時は、まず検証だけを行い、足りなければ作成を再開します。
- **費用の目安**：附属書ヘッダの検証は3回で約130万トークン、解釈保留46件の見直しは約110万、予約語の生成テストの検証は約15万でした。
  13区間の検証だけ（照合案2,215件、新規テスト624本、2026-10-24）は約560万トークンで、1区間あたり約43万でした。

## 11. 再現性のために固定するもの

- 資料：PDFと抽出テキストのSHA-256、出典索引のSHA-256。
- 台帳：分母のSHA-256（`behavior-summary.json`）、基準値（`behavior-baseline.json`の理由）、履歴（`behavior-history.json`）、計測規則の版（`metric_policy_version`）。
- テスト：入力digest（テスト本体、期待値、C、include、`:files:`）、ランナーのSHA-256、シミュレータの版とseed。
- 判断：照合案と判定のJSONL、検証者の識別子、日付、担当、使った指示文（Workflowスクリプト）。
- 生成テスト：生成器の`VERSION`と`oracles.txt`。
