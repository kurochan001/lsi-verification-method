# PLLのロック待ち・クロック停止検出・復帰

PLLをクロックと `LOCKED` の動作モデルで表し、そのPLLを使う回路の起動と復帰を検証します。AONは「常時動作する監視用クロック」の略です。AON側でPLLを監視し、下流の動作許可とリセットを制御します。[クロック停止とリセットの教材](../local-clock-reset/README.md)から、独立したクロックの監視へ進めます。

ロック後の周期・パルス幅・ジッターは、[PLLクロックの測定実習](../local-pll-clock-quality/README.md)で確認できます。

## クロックとリセットの契約

1. AON側へ `pll_locked` を2段で同期し、連続してHighを観測した回数が `LOCK_CYCLES` に達するまで待ちます。
2. クロックが進んでいることは、別に確認します。AON側が1件ずつ `probe` を反転して要求し、PLL側がローカルの立上りを使って `ack` を返します。要求と応答はそれぞれ2段で同期します。
3. ロック条件と応答確認の両方が成立すると、AON側の `clock_permit` がHighになります。下流の `work_reset_n` はその後のPLLクロック2エッジ目で解除します。
4. ロック喪失を同期して観測するか、`TIMEOUT` 回のAONエッジで応答が返らなければ動作許可を落とします。下流リセットのアサートは非同期なので、PLL側のエッジを待ちません。応答が期限の判定と同じエッジで見えた場合は、応答を優先します。
5. クロック停止による `clock_missing` は、次の応答を確認したときにクリアします。ロックとクロック活動が揃えば自動で復帰します。応答回路はシステムリセットで初期化し、下流がリセット中でも応答できます。

PLL側がAON側より速い場合でも、要求が1件ずつなので、単純に毎エッジ反転する信号を間引いて観測する問題を避けられます。正常時のタイムアウト値は、クロック比の上限と同期段の往復遅延に合わせます。本例の10nsのAONに対して、PLLの周期は34ns／4ns、`LOCK_CYCLES` は5／7、`TIMEOUT` は24／16サイクルです。監視回路自体のシステムリセットにも、各ローカルクロックでの同期解除を使います。

## 何を検証するか

Pythonがクロック供給・ロック入力・期待状態を時系列で作ります。TBはPLLクロックを独立して発振させ、停止要求後は予定されたエッジでLowに止めます。AON側の観測時に、出力と期待状態を比較します。下流リセットの解除エッジはPLLクロックと別に観測し、許可後の2回目の立上りと一致することを確認します。

- クロックが動いてもロックがなければ起動しないこと、短いロック通知では解除せず、十分なロックで起動することを確認します。
- ロックだけを落としてPLLクロックを動かし続ける場合と、`LOCKED` をHighのままPLLクロックを止める場合を区別します。後者では、固定試験で停止入力から `TIMEOUT+4` AONサイクル以内に停止検出と下流リセットを照合します。
- 再ロック・クロック再開・停止中のシステムリセット後に、下流の小さなワークロードが再開することを確認します。ランダム試験では停止とロック喪失の順序や期間を変えます。
- ロックの確認期間省略、ロック喪失無視、タイムアウト無視、下流リセットの同期解除省略を意図的に入れ、対応した判定で検出します。

## 実行と波形

```sh
python3 examples/local-pll-recovery/run.py --out artifacts/pll-smoke
python3 examples/local-pll-recovery/run.py --profile nightly --seed 42 --out artifacts/pll-nightly
```

[pll_guard.sv](rtl/pll_guard.sv)は監視とリセット制御、[pll_guard_tb.sv](tb/pll_guard_tb.sv)は動作モデルと自己判定、[model.py](model.py)は固定・ランダムの試験条件、[requirements.json](requirements.json)は3要求・9目標です。smoke／nightlyのJUnitは14／18件です。例えば `slow-pll-boundaries/wave.vcd` で `pll_clk`、`pll_locked`、`probe`、`ack`、`clock_missing`、`clock_permit`、`work_reset_n` を順に追えます。

PLL本体の発振・周波数追従はTBがシナリオとして与えます。ジッター、位相ノイズ、ロック時間の物理的な妥当性、特定マクロの再初期化手順、CDC/RDC制約と実装後タイミングは別の確認です。個々のPLLを使う場合は、ロック喪失後のリセット要否も対象マクロの仕様に従います。 [AMDのロック確認例](https://docs.amd.com/r/en-US/pg046-aurora-8b10b/Step-3-MMCM-Lock-Check)

使用したシミュレータと検証結果は[実行記録](../../PROVENANCE.md#pll-adc-pwm)を参照してください。
