# 回帰の履歴から収束の傾向を表にする

複数回の回帰の結果と不具合の記録から、合否・未解決の不具合・カバレッジ・合否の揺れ・流出の推移を1つの表にする例です。表のすべての数を、別に書いた数え直しのコードと、手で数えた期待値で照合します。指標の作り方と読み方は[検証の指標と収束の判断](../../docs/method/verification-metrics-and-closure.md)にあります。

`data/` の履歴は、この例のために作った**架空のもの**です。11回分の回帰の結果を、[統合ランナー](../../tools/REGRESSION.md)の `summary.json` と同じ形（`id`・`success`・`started`・`message`）で書き、ジョブ名も架空の `ip-fifo` などにしています。このリポジトリの実際の実行結果ではありません。

```sh
python3 examples/local-closure-trend/run.py --out artifacts/closure-trend
python3 examples/local-closure-trend/run.py --profile nightly --out artifacts/closure-trend-nightly
```

Python 3.10以上だけで動きます。シミュレーターは使いません。

## 入力

| ファイル | 内容 |
| --- | --- |
| `data/index.json` | 回帰の実行の並び。表はこの順に作る |
| `data/campaigns/c01.json`〜`c11.json` | 1回分の結果。日付・コミット・seed・プロファイル、ジョブごとの結果、合格したジョブの機能カバレッジとコードカバレッジ（ヒット数と分母） |
| `data/issues.json` | 不具合の記録（見つけた・解決した・再発したときの実行）と、最後の実行の後に見つかった流出 |
| `data/criteria.json` | 収束の基準（直近の安定した実行の数、許す未解決の数、機能カバレッジの完了、揺れの解決） |

## 数え方の約束

| 列 | 数え方 |
| --- | --- |
| 合格・不合格・未完了 | 時間切れ（`job timeout`・`command timeout`）と、起動しなかったジョブは**未完了**。合格にも不合格にも数えない |
| 新規・再発・解決・未解決 | 回路とテストベンチの不具合だけ。再発は新規に数えない。解決は、その修正を確かめた実行で数える |
| 環境 | ランナーや環境の不良。回路の不具合の数とは分ける |
| 機能カバレッジ・コードカバレッジ | 指標ごとに分け、合算しない。合格したジョブの分だけを計上する |
| 未計上 | カバレッジを計上しなかったジョブの数（不合格・未完了・記録なし） |
| 揺れ | 同じ計画（コミット・seed・プロファイル）で、合格と不合格の両方が出たジョブの数。seedが違えば別の計画で、未完了は判定に数えない |

分母が変わった実行（目標を足した、コードを消した）は、表の下に別に書きます。カバレッジの割合が下がって見えても、分母の変更なら回路の後退ではありません。

読み方の例です。

- **c05の機能カバレッジは60/60（100%）に見えます。** 計上したのは合格した4ジョブだけで、未計上が2つあります。割合だけを見ると、全体が完了したと誤って読みます。
- **c05とc06は同じ計画です。** `ip-apb` が不合格から合格へ変わったので、揺れとして数えます。原因はテストベンチの競合（BUG-003）で、c07で解決しています。
- **c08とc09は同じコミットですが、seedが違います。** `soc-dma` の不合格から合格への変化は揺れではなく、違う刺激で結果が違っただけです。c08の不合格は不具合（BUG-004）として扱います。
- **c10とc11は、全ジョブが合格しています。** それでも、レビューで見つけた不具合（BUG-005）が未解決なので、収束の基準を満たしません。

## 確かめていること

| 検査 | 内容 |
| --- | --- |
| `inventory` | 固定の履歴が、下の拒否の規則をすべて通る |
| `trend-table` | 表を作り、`trend.json` と `trend.md` を保存する |
| `recount` | `recount.py` が同じ入力を別の方法で数え直し、全セル・全集計が一致する |
| `markdown-roundtrip` | `trend.md` の表を読み戻すと、`trend.json` と一致する |
| `hand-counts` | `expected.json`（この例を作るときに手で数えた値）と一致する |
| `reject-*`（7件） | 結果の欠け、ジョブの重複、日付の逆転、存在しない実行への参照、ありえない不具合の履歴、分母を超えるヒット、予定にないジョブのカバレッジを、それぞれ決めたラベルで拒否する |
| `mutation1`〜`9` | 生成器に入れた数え方の誤り9種類を、数え直しが決めた場所で見つける |
| `random-01`〜 | 乱数で作った履歴（smoke 3件、nightly 12件）でも、生成器と数え直しが一致する |
| `requirements` | 8つの要求の目標がすべて合格した |

数え直しの `recount.py` は、`trend.py` を読み込まずに書いています。未解決の数は、見つけた・再発したを+1、解決を−1とする累積和で求めます（生成器は未解決の集合を持ちます）。揺れは計画ごとに見た判定の集合で、分母の変更は分母の並びの隣どうしの比較で求めます。

### 数え方の誤り（変異）

| 変異 | 誤り | 最初に食い違う場所 |
| --- | --- | --- |
| 1 | 時間切れを合格に数える | `passed@c02` |
| 2 | 再発を新規にも数える | `new_defects@c07` |
| 3 | 解決を次の実行で数える | `open@c03` |
| 4 | 環境の不良を不具合に数える | `new_defects@c03` |
| 5 | 不合格のジョブのカバレッジも計上する | `functional@c01` |
| 6 | 分母の変更を報告しない | `denominator_changes` |
| 7 | seedの違いを同じ計画とみなす | `flaky@c09` |
| 8 | 流出を報告から外す | `escapes` |
| 9 | 収束の判定で未解決の不具合を見ない | `verdict` |

どれも、実際の報告で起こりやすい誤りです。どれか1つでも予定と違う場所で食い違うか、食い違わなければ不合格です。

JUnitはsmoke 25件、nightly 34件です。nightlyは乱数の履歴が9件増えます。

## セルフテスト

12件です。手で数えた値の再現、変異と拒否のラベル、時間切れの分類、seedの違い、Markdownの読み戻しと1セルの書換えの検出、基準をゆるめたときの判定、乱数の履歴150件での一致と、それらが揺れ・再発・分母の変更・未完了・環境の不良をすべて含むこと、smokeとnightlyの実行と出力先の再利用の拒否を確かめます。

```sh
python3 -m unittest discover -s examples/local-closure-trend/tests
```

## 確認範囲と残る制限

- 入力は架空の履歴です。実際のプロジェクトの指標の値や、よい・悪いの目安を示すものではありません。
- 履歴レポート（[`regression_report.py`](../../tools/REPORTING.md)）は、同じ計画の再実行を照合して採用結果を決める道具です。この例は、その外側で、**計画が変わっていく複数回の回帰**を並べて傾向を読む教材です。レポートの出力を直接読むのではなく、`summary.json` と同じ形の結果を入力にしています。
- 不具合の記録は手で書いたもので、不具合管理の道具とはつないでいません。
- カバレッジは、ジョブごとのヒット数と分母の和です。ジョブの間で目標が重なる場合（同じ目標を2つのジョブが数える）は扱いません。
- 収束の判定は、満たしていない基準を並べるだけです。人の承認やサインオフの代わりにはなりません。[サインオフ記録の雛形](../../docs/templates/signoff-record.md)と併せて使います。

## 確認記録

2026-11-21に、Python 3.13でsmoke（seed 17・3・100）とnightlyを実行し、すべて合格しました。セルフテスト12件も合格です。

生成器（`trend.py`）の写しへ、計画した変異とは別の誤りを11個入れ、固定の検査が気付くかを確かめました。最初は、次の3個を固定の検査が見逃しました。

- 未完了の判定を `job timeout` だけにする誤り：固定の履歴に、ほかの形の未完了がなかった。
- 同じ計画の未完了と合格を揺れに数える誤り：同じ計画の中に未完了がなかった。
- 流出を最初の1件だけ報告する誤り：流出が1件しかなかった。

固定の履歴に、起動しなかったジョブ（c02）、コマンドの時間切れ（c04）、同じ計画の中の時間切れ（c05）、2件目の流出を足しました。分母が減る場合（c10）は、注入の前に固定の履歴と乱数の履歴の両方へ足してあります。取り直すと、11個すべてを固定の検査（数え直し、手の数え、Markdownの読み戻し、拒否）が見つけました。
