# 環境の進行条件と完了期限をフォーマル検証する

2要求元をラウンドロビンで受け付け、固定時間の処理後に応答を返す小さなRTLです。受信側が進む条件を明記し、受付・完了の期限を証明します。READYが止まっても壊れない安全性と、期限内に終わる性質を分ける教材です。

## 契約と期限

要求は受理されるまで保持します。応答は所有者とともにREADYまで保持し、その取引が完了してから次を選びます。SERVICEは処理段数、READY_GAPはREADYが連続0になれる長さの制約を表します。

通常タスクでは、READYが連続READY_GAPクロック0にならないことを仮定します。すなわち、連続した0は最大READY_GAP−1回です。要求がいつか来ることや、2要求の同時到着は仮定しません。

リセットを挟まない区間で、次の保守的な期限を検査します。

- 受付済み要求の完了：受付エッジから`SERVICE+READY_GAP+3`クロック以内。
- 待っている要求の受付：要求を初めて観測したエッジから`2×(SERVICE+READY_GAP+3)`クロック以内。

完了監視のageは受付時に0へ更新し、各エッジの更新前の値を検査します。このため実装の比較値は完了期限−1です。SVAのサンプリングとカウンターの更新順を、経過クロック数と区別します。最短・最大実測レイテンシを求めた結果ではありません。

`service1-gap2`は完了6／受付12クロック、`service2-gap3`は完了8／受付16クロックの期限です。後続リセットは未完了の義務を破棄し、状態・監視カウンターを初期化します。

## タスク

各構成8タスク、計16件のJUnitです。

- `deadline-proof`：期限、応答保持・所有者・排他、監視台帳とRTLの一致、カウンター等12条件を、仮定の下で非有界に証明します。補助条件もassertです。
- `scenario-cover`：競合、応答待ち、各要求元の完了、長い待ち、未完了時リセット、復帰の7目標を到達確認します。
- 4変異：固定優先による飢餓、待ち中の応答消失、処理停止、所有者の誤りを、それぞれ予定assertの反例で確認します。
- `unfair-safety-proof`：READYの期限仮定と完了期限assertを外しても、安全性を証明します。
- `detect-missing-fairness`：READYを停止させる仮定で、完了期限に違反する反例を要求します。これはRTL変異ではなく、環境条件を外した診断です。

無限時間にいつかREADYが上がる、という一般の公平性を用いたLTLの活性証明ではありません。有限の進行条件から、期限超過しないことを安全性プロパティとして証明します。

## 実行

[共通フォーマル手順](../local-formal-common/README.md)の固定版ツールを使います。

```sh
. /tmp/lsi-bus-formal-venv/bin/activate
python3 examples/local-progress/run.py
python3 examples/local-progress/run.py --task detect-missing-fairness
python3 -m unittest discover -s examples/local-progress/tests -v
```

既定の探索深さは24です。下げると必要な期限違反や到達目標まで届かない場合があります。UNKNOWN・TIMEOUT・予定外の違反は成功にしません。ソース・仮定・プロパティ一覧、正常到達14目標、変異8反例、進行条件を外した2反例を別に保存します。単一クロック・2値・同期リセットで、実機の公平性やシステム全体のデッドロックを証明した結果ではありません。計画確認は3テストです。
