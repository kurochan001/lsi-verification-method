# 連結リスト型のバッファ管理の保存則を確かめる

ネットワークのスイッチや通信の受信回路は、データを置くバッファを番号で管理します。空いているバッファはフリーリストに並べ、受け取ったパケットのバッファは宛先ごとのキューにつなぎ、送り終えたら返します。リストは、バッファごとの「次の番号」の表（next-pointer）でつなぐのが普通です。この管理を誤ると、次のことが起きます。

- **リーク**：返したバッファがどこにも戻らず、空きが減り続けて、いつか止まる。
- **二重解放**：同じバッファを2回返し、同じバッファが2つのパケットに使われる。
- **連結の切れ**：「次の番号」を書き忘れて、キューが途中で別のリストへつながる。

どれも、起きてから長い時間がたって初めて症状が出るので、出力の比較だけでは見つけにくい誤りです。この教材では、「どのバッファも、フリーリスト・どれか1つのキュー・読出し側が保持中の、ちょうど1か所にある」という保存則を、毎サイクルのシミュレーションの検査と、すべての入力列についてのフォーマルの証明で確かめます。

似た構造の物理レジスタの管理は、[リネーム表・フリーリスト・ROBの例](../local-rename-rob/README.md)にあります。あちらはビットマップのフリーリストで、こちらは連結リストです。メモリ全体での位置付けは、[メモリの検証手順](../../docs/method/memory-verification.md)にあります。

## 仕様

[`buffer_manager.sv`](rtl/buffer_manager.sv)は、NB個のバッファとNQ本のキューを持ちます。フリーリストとすべてのキューは、1つの「次の番号」の表`nxt`を共有する連結リストで、それぞれ先頭・末尾・個数を持ちます。

| 操作 | 入力 | 動作 | 受け付けないとき |
| --- | --- | --- | --- |
| 投入 | `enq_valid`・`enq_q` | フリーリストの先頭のバッファ（`enq_id`）を、キュー`enq_q`の末尾へつなぐ | フリーリストが空（`enq_ready`が0） |
| 取出し | `deq_valid`・`deq_q` | キュー`deq_q`の先頭のバッファ（`deq_id`）を外し、保持中にする | キューが空（`deq_ready`が0） |
| 返却 | `rel_valid`・`rel_id` | 保持中のバッファを、フリーリストの末尾へ戻す | そのバッファが保持中でない（`rel_ready`が0）。何も変えない |

決めたことは次のとおりです。

- **同じサイクルの操作**：3つの操作は同じサイクルに来てよく、どれもサイクルの始めの状態を見ます。そのサイクルに返したバッファは、同じサイクルの投入には使いません。同じサイクルに取り出したバッファは、同じサイクルには返せません。
- **同じキューの投入と取出し**：キューに1個だけのとき、その1個が出て新しい1個が入ります。先頭と末尾がどちらも新しいバッファになります。
- **フリーリストが1個か空のとき**：1個のフリーリストから1個出し、同時に1個返すと、返したバッファが先頭と末尾になります。空のフリーリストへ返すときも同じです。
- **二重解放の拒否**：空きのバッファ（2回目の返却を含む）と、キューにあるバッファの返却は、受け付けません。回路は保持中のバッファを1ビットずつ覚えています。
- **リセット**：同期リセットです。すべてのバッファが番号順にフリーリストに並び、キューは空、保持中のバッファはなくなります。
- **readyの見え方**：`enq_ready`・`deq_ready`・`rel_ready`は、validが0のサイクルでも、そのときの入力（`deq_q`・`rel_id`）に対する値を出します。テストベンチは、validのないサイクルでもこの値をモデルと比べます。

## シミュレーションで確かめること

[`model.py`](model.py)は、フリーリストを先入れ先出しのリスト、キューをリスト、保持中のバッファを集合で持ちます。フリーリストの順は仕様で決まっている（返したバッファは末尾）ので、投入されるバッファの番号まで予測でき、テストベンチは番号をそのまま比べます。

テストベンチは、各サイクルの入力を与えた直後に出力を比べ、クロックの後に、回路の表（検査用の出力ポート）を使って全リストをたどり直します。たどり直しはモデルを使いません。

| 検査ラベル | 内容 |
| --- | --- |
| `BM_FULL`・`BM_EMPTY`・`BM_RELEASE` | 投入・取出し・返却を受けるか断るかが、モデルと同じ |
| `BM_ID` | 受けた投入と取出しのバッファの番号 |
| `BM_LINK` | 毎サイクル：各リストを個数の分だけたどった最後が、そのリストの末尾である |
| `BM_DOUBLE`・`BM_LEAK` | 毎サイクル：バッファが2か所以上にある・どこにもない |
| `BM_COUNT` | 毎サイクル：フリーリストと各キューの個数が、モデルと同じ |
| `BM_RESET`・`BM_X` | リセット後に保持中のバッファがないこと、出力と表にXがないこと |
| `BM_TIMEOUT` | 1行が終わらない（検査とは別のラベル） |

連結が切れると、たいていリークと二重の居場所が同時に起きるので、`BM_LINK`を最初に報告します。

### 固定シナリオと目標

固定シナリオは、`b16-q4`で72行、`b8-q2`で46行です。空のキューからの取出し、末尾へのつなぎ、返却とその2回目、キューにあるバッファと空きのバッファの返却、同じキューで1個と2個のときの同時の投入と取出し、すべての空きの投入と断られる投入、空のフリーリストへの返却、1個のフリーリストでの同時の投入と返却、3つの操作の同時、全バッファの保持、返したバッファの再利用、バッファが使われている状態でのリセットを含みます。

同時の投入と取出しの場面では、新しいバッファの番号が、末尾のバッファの古い「次の番号」と違うように並べています。リセット直後の表は番号順につながっているので、順に投入しただけでは、つなぎ忘れても偶然正しい番号が残っていて、誤りが見えません。

[要求カタログ](requirements.json)は6要求・17目標で、どちらの構成でも固定シナリオだけで17目標に届きます。ランダムな刺激は、3つの操作をそれぞれの確率で同時に出し、返却の4分の3は保持中のバッファ、残りは任意の番号です。完了の件数は、行数、受けた投入・取出し・返却、断った返却、リセットの6種類を照合します。

## 7つの誤りと、見つける検査

| 番号 | 誤り | シミュレーション | フォーマルの反例 |
| --- | --- | --- | --- |
| 1 | 返却したバッファを、保持中から外すがフリーリストへつながない（リーク） | `BM_LEAK` | `ai_cover` |
| 2 | 保持中でないバッファの返却を受ける（二重解放） | `BM_RELEASE` | `ap_release_held` |
| 3 | 空でないキューへの投入で、古い末尾から新しいバッファへつながない | `BM_LINK` | `ap_tail` |
| 4 | 1個のキューの同時の投入と取出しで、先頭を「出たバッファの次」にする | `BM_LINK` | `ap_tail` |
| 5 | 空のキューからの取出しを受ける | `BM_EMPTY` | `ap_deq_nonempty` |
| 6 | 空のフリーリストからの投入を受ける | `BM_FULL` | `ap_enq_room` |
| 7 | 1個のフリーリストでの同時の投入と返却で、先頭を「出たバッファの次」にする | `BM_LINK` | `ap_tail` |

- **変異1**は、出力には長い間現れません。空きが1つずつ減り、なくなって初めて投入が止まります。保存則の検査は、返し忘れたそのサイクルに見つけます。
- **変異4と7**は、「リストが空になって、同じサイクルにまた1個入る」場合だけの誤りです。1個を超えるリストでは、先頭を「次」へ進めるのが正しいので、同じ書き方が通ります。
- **フォーマルの変異1**は、選んだ1つのバッファの性質（`ap_no_leak`）ではなく、全体の補助の不変条件`ai_cover`（どのバッファもどこかにある）を予定にしています。反例を探すソルバーは、リークしたバッファとは別のバッファを選ぶことがあるからです。

`--demo-bug 1`〜`7`で、正常回路の計画に誤りを入れられます。

## フォーマルで証明すること

[`formal.py`](formal.py)は、RTLの`` `ifdef FORMAL``に書いた性質を、最初のリセット以外に入力の制約を置かずに証明します。3つの操作は、どの値でも、同じサイクルにでも来ます。

性質は、自由に選んだ1つのバッファ`f_b`（`anyconst`）について書きます。各リストを個数の分だけたどり、`f_b`に出会った回数と、保持中かどうかを足して、居場所の数を数えます。

| 検査 | 内容 |
| --- | --- |
| `ap_no_leak`・`ap_no_double` | 選んだバッファの居場所は、ちょうど1つ |
| `ap_tail` | 空でないリストは、たどった最後が末尾である |
| `ap_release_held`・`ap_deq_nonempty`・`ap_enq_room` | 返却・取出し・投入を受けるのは、保持中のバッファ・空でないキュー・空でないフリーリストのときだけ |

選んだ1つのバッファの性質だけでは、帰納法が成り立ちません。到達できない状態では、ほかのバッファのリストが壊れていてもよく、そこから選んだバッファの居場所が変わりうるからです。そこで、全バッファについての補助の不変条件4つを、同じタスクでアサーションとして証明します。仮定（assume）にはしていません。

| 補助 | 内容 |
| --- | --- |
| `ai_distinct` | どのリストも、同じバッファに2回出会わない |
| `ai_disjoint` | リストどうし、リストと保持中のバッファは重ならない |
| `ai_cover` | どのバッファも、どこかにある |
| `ai_counts` | 個数の合計がNBで、どの個数もNB以下 |

`scenario-cover`は、断られる投入、1個のキューの同時の投入と取出し、1個のフリーリストの同時の投入と返却、断られる返却、別のキューへの3つの同時の操作の5つに到達できることを確かめます。

### 証明できた大きさ

証明は、Z3によるk帰納法（深さ2。1ステップの帰納法）で、すべての長さの入力列についての証明です。

| 構成 | バッファ・キュー | 証明 |
| --- | --- | --- |
| `b4-q2` | 4・2 | 成立（約30秒） |
| `b4-q4` | 4・4 | 成立（約2分） |

8バッファの構成（8・2と8・4）は、帰納段階が数分で終わらず、証明できていません。8バッファと16バッファは、シミュレーションだけで確かめています。深さ1は、帰納の仮定を何も置かない形になるので使えません。

## 確認範囲と残る制限

- **扱わないもの**：バッファの中身（データ）、複数の投入口や取出し口、キューの優先度、満杯のときの破棄の方針、エラー訂正、表のRAM化と読出しの遅れ。
- **環境の約束**：同じサイクルに取り出したバッファは返せません。この約束は回路が守らせるもので、テストベンチもその前提で刺激を作ります。
- **証明の大きさ**：非有界の証明は4バッファまでです。たどる回数がバッファの数に比例するので、大きな構成では重くなります。
- **独立性**：モデルとRTLは、同じ人が同じ仕様から書いています。毎サイクルの表の検査は、モデルを使わずに回路の表から保存則を数え直すもので、モデルと共通の誤解に左右されません。

## 確認記録

2026-11-21に、macOS arm64、Python 3.13、Icarus Verilog 14.0開発版、Verilator 5.052（lintのみ）、YoWASP版Yosys 0.70とSBY、Z3 4.15.3で確認しました。

- smoke（seed 17・3・100）とnightly（`--timeout 60`）が合格しました。JUnitはsmoke 20件、nightly 24件です（構成ごとに固定1、ランダム1／3、変異7と、要求と目標の判定1）。両構成とも17／17目標です。
- フォーマルは、2構成×9タスクの18件がすべて予定どおりでした。証明2件、到達2件、変異の反例14件です。負荷の高い状態で全体が約4分、証明は`b4-q2`が約30秒、`b4-q4`が約2分でした。
- セルフテスト15件が合格しました（skipなし）。
- RTLは、`--lint-only --Wall`で、両構成と4バッファの構成、変異0〜7で警告0件です。

計画にない誤りも、写しのRTLへ1つずつ12個入れて、smokeの機能のケース（固定シナリオとランダム）にかけました。

| 結果 | 個数 | 内容 |
| --- | --- | --- |
| 固定シナリオが両構成で検出 | 9 | リセット時の末尾・個数・つなぎの順の誤り、投入の番号を末尾から取る、取り出したバッファを保持中にしない、validなしの返却、同じキューの同時操作の個数、空のフリーリストへの返却、1個のキューを空と見る、など |
| 試験の抜けとして直したもの | 1 | 2個のキューの同時の投入と取出しでつながない誤りを、最初の固定シナリオは見逃した。新しいバッファの番号が、末尾の古い「次の番号」と偶然同じだったため。並びを変えて、固定シナリオで見つかるようにした |
| 合格のまま残るもの | 2 | 空のキューの先頭と末尾のリセット値。個数が0の間は使われず、最初の投入で書き換わるので、動作に差が出ない |
