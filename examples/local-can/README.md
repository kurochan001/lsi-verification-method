# CAN 2.0Aのコントローラー3ノードを、ビット単位のモデルと照合する

CAN（Controller Area Network）は、複数のノードが1本のバスを共有し、識別子の小さいフレームが競合に勝つ通信方式です。フレームの形だけでなく、競合の負け方、誤りの知らせ方、誤りを数えてバスから離れる規則、クロックの違うノードどうしでビットを合わせる仕組みまでが、プロトコルに含まれます。この教材では、標準フォーマット（識別子11ビット）のコントローラーを3つつなぎ、クロックの周波数を少しずつ変えたうえで、バスに現れるビット列と各ノードの報告を、ビット単位の参照モデルと照合します。

[オートモーティブLSIの検証手順](../../docs/method/automotive-verification.md)は、CANなどのバス規格を「教材では扱っていない」としています。この例は、その部分のうちCAN 2.0のパートAを扱います。ISO 11898への適合、CAN FD、拡張フォーマット（29ビットの識別子）、物理層（トランシーバー、終端、電気特性）は対象外です。出典は公開されているBosch CAN Specification 2.0で、本文は写していません。節番号は[末尾](#参考にした資料)にまとめ、照合の程度も書きました。

## 対象回路

[`can_node.sv`](rtl/can_node.sv)は、送信バッファ1本と受信の出力を持つコントローラーです。バスの値は0がドミナント、1がレセッシブです。

| 端子 | 向き | 内容 |
| --- | --- | --- |
| `can_rx`、`can_tx` | 入力、出力 | バスの値と、このノードが出す値 |
| `tx_valid`、`tx_ready`、`tx_id`、`tx_rtr`、`tx_dlc`、`tx_data` | 入力（`tx_ready`は出力） | 送信要求。`tx_data`は最初のバイトがビット63〜56 |
| `tx_done` | 出力 | 送信が成功した1クロックのパルス |
| `rx_valid`、`rx_id`、`rx_rtr`、`rx_dlc`、`rx_data` | 出力 | 受信したフレーム。自分が送ったフレームは出さない |
| `err_valid`、`err_code` | 出力 | 検出した誤り。1ビット、2スタッフ、3 CRC、4フォーム、5 ACK、6過負荷の条件 |
| `arb_lost`、`sync_kind` | 出力 | 競合に負けた／同期の種類（1ハード同期、2ビットを伸ばした、3縮めた） |
| `tec`、`rec`、`mode` | 出力 | 送信・受信のエラーカウンターと状態（0エラーアクティブ、1エラーパッシブ、2バスオフ） |

実装した規則は次のとおりです。

- **フレーム**：SOF、識別子11ビット、RTR、予約2ビット、長さコード4ビット、データ0〜8バイト、CRC 15ビット、CRCデリミター、ACKスロット、ACKデリミター、EOF 7ビット、その後のインターミッション3ビット。長さコードが9以上のデータフレームは8バイトとして扱います。リモートフレームはデータを持ちません。
- **ビットスタッフ**：SOFからCRC列までは、同じ値が5ビット続いた直後に反転したビットを入れます。挿入したビットも次の5ビットに数えます。CRC列の最後の5ビットが同じ値なら、その後にも入れます。
- **CRC**：生成多項式は`0x4599`（15ビット）で、SOFからデータの終わりまでの、スタッフを除いたビットにかけます。
- **競合**：識別子とRTRの送信中に、レセッシブを出してドミナントを読んだ送信側は、誤りとせずに受信へ切り替わり、バスが空いた後に再送します。
- **誤りの検出**：ビット（出した値と読んだ値の不一致）、スタッフ（同じ値が6ビット）、CRC、フォーム（CRCデリミター・ACKデリミター・EOF・エラーデリミターのドミナント）、ACK（ACKスロットがレセッシブ）。CRCの誤りだけは、ACKデリミターの次のビットからフラグを出します。
- **誤りの知らせ方**：エラーアクティブのノードはドミナント6ビット、エラーパッシブのノードはレセッシブ6ビットのフラグを出します。パッシブのフラグは、同じ値を6ビット続けて読むまで待ちます。その後はレセッシブを1ビット読むまで待ち、合わせて8ビットのデリミターの後にインターミッションへ進みます。
- **カウンター**：送信側の誤りは送信カウンターを8増やし、受信側の誤りは受信カウンターを1増やします。受信側がフラグの直後にドミナントを読むと、さらに8増やします。アクティブのフラグの送信中にレセッシブを読むと、8増やしてフラグをやり直します。送信の成功で送信カウンターを1減らします。受信の成功（ACKを出して読めた時点）で、受信カウンターを1減らし、127を超えていれば127にします。
- **カウンターを増やさない2つの場合**：エラーパッシブの送信側がACKの誤りを検出し、パッシブのフラグの間にドミナントを読まなかった場合。識別子の送信中に、レセッシブのスタッフビットを出してドミナントを読んだ場合。
- **エラーパッシブとバスオフ**：どちらかのカウンターが128以上でエラーパッシブです。フラグの種類は、その誤りで数える前の状態で決めます。エラーパッシブのノードは、自分が送信側だったフレームの後、インターミッションに続けて8ビット待ってから送ります。送信カウンターが256以上になるとバスから離れ、11ビット連続のレセッシブを128回読むと、カウンターを0にして戻ります。
- **バスへの参加**：リセットの後は、11ビット連続のレセッシブを読むまで送受信しません。
- **過負荷の条件**：インターミッションの1・2ビット目、受信側のEOFの最後のビット、デリミターの最後のビットのドミナントには、カウンターを変えずにドミナント6ビットのフラグで応えます。自分から過負荷フレームを要求することはありません。
- **ビットタイミング**：1クロックを1タイムクォンタムとし、1ビットは`1 + TSEG1 + TSEG2`クォンタムです。`TSEG1`の後でサンプルします。バスが空いているとき、サスペンド中、インターミッションの3ビット目のレセッシブからドミナントへのエッジで、ビットの先頭を合わせます（ハード同期）。それ以外のエッジでは、`SJW`クォンタムまでビットを伸縮します（再同期）。同期は1ビットに1回で、直前のサンプルがレセッシブのときだけです。自分がドミナントを出しているときの遅れたエッジには従いません。

仕様と違う点、実装していない点は次のとおりです。

- フラグの後にドミナントが長く続いたときの追加のカウント（14ビット目、以後8ビットごと）は実装していません。
- 送信側が、CRCデリミター・ACKデリミター・EOFでレセッシブを出してドミナントを読んだ場合は、フォームの誤りとして報告します（仕様の分類ではビットの誤りにも当たります）。カウンターの増え方は同じです。
- 送信バッファは1本で、成功するまで保持します。送信の取消し、受信フィルター、受信バッファのあふれ、時刻の記録はありません。
- バスオフからの復帰は、条件がそろうと自動で行います。ソフトウェアからの要求は待ちません。

## 検証環境

[`can_tb.sv`](tb/can_tb.sv)は、3つのノードをワイヤードANDのバスにつなぎます。

- **クロック**：3つのノードのクロックは、周期が少しずつ違います。`skew8`は基準・0.8 %遅い・0.8 %速い、`skew5-late`は0.5 %遅い・0.5 %速い・基準です。位相もそろえていません。
- **バスの検査**：テストベンチは、どのノードの読み方にも頼らず、バスのエッジの間隔を公称のビット時間で割って丸め、「ドミナントが何ビット、レセッシブが何ビット」という並び（ラン）に直します。これをモデルの予想と1つずつ比べます。2つのノードの出力が入れ替わるときの、1ビットに満たない切れ目は無視します。32ビット以上のランだけは、長さの1/32までの差を認めます（バスオフからの復帰の約1,400ビットなど。クロックの差0.8 %より大きく取っています）。
- **ノードの報告の検査**：受信したフレーム、誤りの種類、競合に負けた位置、送信の成功数を、ノードごとに順番どおりに比べます。場面の終わりには、聞かれなかった報告が残っていないこと、カウンターと状態がモデルと同じであることを確かめます。
- **乱し方**：3種類です。バスをドミナントにする、1つのノードが読む値だけをドミナントにする、同じくレセッシブにする。場面の最初のドミナントから数えたビット番号で指定し、そのビットの先頭から0.1ビット後に始めて1ビット分（指定があれば複数ビット分）続けます。0.1ビットは、ノードの入力の同期段の遅れに合わせた値です。
- **ノードの切離し**：ノードのリセットを保持して、バスにいない状態を作ります（ACKを返す相手がいない場面）。

乱す位置は公称の時間で決めるので、最後のバスのエッジから12ビットを超える位置は、スクリプトを作るときに拒否します。クロックの差0.8 %で12ビット進むと、ずれは約0.1ビットです。サンプル点までの余裕（0.2ビット以上）に収まります。

テストベンチは、次の3点でノードの内部を読みます。

- カバレッジの条件（スタッフビットを読んだ、サスペンド中である、など）。
- 「フレームの先頭が来うる状態でのエッジは、再同期ではなくハード同期になる」という検査（`CAN_SYNC`）。
- 競合に負けた位置の記録。

## 期待値：ビット単位のモデル

[`model.py`](model.py)は、3つのノードとバスを、1ビットを1ステップとして進めます。各ノードが出す値を決め、バスの値（全員の論理積）を求め、各ノードが自分の読んだ値で状態を進めます。クロック、タイムクォンタム、同期の概念はありません。RTLは、周波数の違う3つのクロックと再同期で、同じビット列に行き着かなければなりません。

モデルが予想するのは、場面ごとのバスのラン、各ノードの報告の列、場面の終わりのカウンターと状態です。乱した場面も、乱したビットをモデルに与えて同じ規則で進めます。

独立といえる点と、いえない点を分けておきます。

- **独立な点**：書き方が違います。モデルはビットの列をリストで持ち、CRCは列全体から計算し直します。RTLは1ビットずつのレジスタです。バスの検査は、ノードの受信結果ではなく、テストベンチが測ったランで行います。CRCは、シフトレジスタの式と、多項式の筆算（割り算）の2通りで計算して一致を確かめています。識別子0・データなしのフレームのビット列は、手で求めた並びと比べています。
- **独立でない点**：モデルとRTLは、同じ人が同じ仕様の読み方で書いています。仕様の読み違いは両方に入ります。外部の実装や、公開のフレーム例、適合試験とは照合していません。

## 場面

固定の場面は2つのケースに分かれ、合わせて35個あります。どの目標も、乱数の場面に頼らず、固定の場面だけで届きます。

`protocol`（27場面、約2,800ビット）：

| 内容 | 場面 |
| --- | --- |
| フレーム | 8バイト、0バイト、リモート、長さコード12、CRC列の後のスタッフ、同じノードから3本続けて |
| 競合 | 3ノード同時（識別子で2ノードが順に負ける）、同じ識別子のデータとリモート、送信中に別のノードへ要求、要求を2本持つノード |
| 誤り（どれも再送まで確かめる） | 送信側が自分のドミナントを読み違える、受信側がスタッフビットを読み落とす、受信側のCRCの誤り、CRCデリミター・ACKデリミター・EOFの3ビット目・EOFの最後（受信側と送信側） |
| 過負荷の条件 | インターミッションの1ビット目と2ビット目。3ビット目のドミナントはフレームの開始として扱う |
| フラグとデリミター | 送信側のフラグを乱す、受信側のフラグを乱す、エラーデリミターの2ビット目と最後のビット |
| カウンターを増やさない場合 | 識別子の中のレセッシブのスタッフビットをドミナントにする |
| そのほか | 送信側がSOFを読めない |

`confinement`（8場面、約4,600ビット）：

| 内容 | 場面 |
| --- | --- |
| バスへの参加 | エラーフラグの終わりで離したノードは、次の送信までにレセッシブを10ビットしか読めない。その送信にはACKを返さず、次のエラーフラグの後の11ビットで参加する |
| ACKなし | 相手のいない送信側は、16回でエラーパッシブになり、128で止まる。サスペンドを挟んで送り続け、相手が戻ると成功して127になる |
| 受信側が1つだけ | その受信側がCRCの誤りを持つと、誰もACKを返さない |
| バスオフ | 送信側の読み違いを32回続けて256にする。レセッシブ11ビット×128回の後に戻り、保持していたフレームを送る |
| 受信側のエラーパッシブ | 受信側のフラグを16ビット乱して128を超えさせる。次の誤りではパッシブのフラグを出し、ほかのノードのフレームを壊さない。正常な受信で127に戻る |

乱数の場面（`random-seed<N>`）は、1〜3ノードが1〜2本ずつ要求し、6割の場面で乱しを1つ入れます。乱す位置と種類は乱数で選び、モデルで先に試して、エラーパッシブやバスオフに入るものは選び直します。smokeは1 seed・10場面、nightlyは3 seed・各20場面です。

握手については、次の2つを固定の場面に入れています。要求のないまま`tx_ready`が出ている状態と、バッファが埋まっている間に次の要求を出し続ける状態です。

## 検査ラベル

| ラベル | 内容 |
| --- | --- |
| `CAN_RUN` | バスのランの値または長さが、モデルと違う |
| `CAN_RX`、`CAN_ERR`、`CAN_LOST`、`CAN_DONE` | 受信フレーム、誤りの種類、競合に負けた位置、送信の成功数が違う、または届かない |
| `CAN_STATE` | 場面の終わりのカウンターまたは状態が違う |
| `CAN_END` | 聞かれなかった報告やランが残っている、要求が残っている、バスがドミナントのまま |
| `CAN_SYNC` | 自分のドミナントの遅れたエッジでビットを伸ばした／フレームの先頭が来うる状態で再同期になった |
| `CAN_RESET`、`CAN_UNKNOWN` | リセット中の出力が規定と違う／出力やバスがX |
| `CAN_TIMEOUT` | 予想したランが、4,000ビット待っても現れない（検査の不一致とは別のラベル） |

## 要求と目標

[`requirements.json`](requirements.json)は8要求・36目標です。2つの構成のどちらでも、通常の実行で36目標すべてに届くことを求めます。

| 要求 | 目標 |
| --- | --- |
| `CAN-FRAME` | 0バイト、8バイト、長さコード9以上、リモート、続けて送る |
| `CAN-STUFF` | ドミナントのスタッフ、レセッシブのスタッフ、CRC列の後のスタッフ |
| `CAN-ARBITRATION` | 識別子で負ける、RTRで負ける、3ノードの競合、負けた後の再送 |
| `CAN-ERROR` | 5種類の誤り、過負荷の条件、フラグの送信中の誤り、識別子の中のスタッフの誤り、誤りの後の再送 |
| `CAN-COUNTERS` | 送信の成功で減る、受信の成功で減る、127へ戻る、フラグの直後のドミナントで8増える、ACKの誤りで増えない |
| `CAN-CONFINEMENT` | エラーパッシブ、パッシブのフラグ、サスペンド、バスオフ、復帰 |
| `CAN-TIMING` | ハード同期、ビットを伸ばす、ビットを縮める |
| `CAN-HOST` | 要求のない状態、バッファが埋まっている間の要求 |

## 意図的な誤実装

`MUTATION`で10種類の誤りを選びます。それぞれを、その誤りが現れる固定のケースで実行し、予定したラベルで不合格になることを、2つの構成で確かめます（20件）。

| 番号 | 誤り | ケース | ラベル |
| --- | --- | --- | --- |
| 1 | 送信側が、同じ値を6ビット送ってからスタッフする | `protocol` | `CAN_RUN` |
| 2 | CRCの多項式が1ビット違う（送信と受信の両方） | `protocol` | `CAN_RUN` |
| 3 | CRCが合わなくてもACKを返す | `confinement` | `CAN_RUN` |
| 4 | 競合に負けても送り続ける | `protocol` | `CAN_RUN` |
| 5 | 送信の誤りで8ではなく1増やす | `protocol` | `CAN_STATE` |
| 6 | エラーパッシブでもアクティブのフラグを出す | `confinement` | `CAN_RUN` |
| 7 | サスペンドしない | `confinement` | `CAN_RUN` |
| 8 | 再同期しない（ハード同期だけ） | `protocol` | `CAN_RUN` |
| 9 | 受信の成功で受信カウンターを減らさない | `protocol` | `CAN_STATE` |
| 10 | レセッシブ11ビットを1回読んだだけでバスオフから戻る | `confinement` | `CAN_RUN` |

2番は、3つのノードが同じ誤った多項式を使うので、ノードどうしの通信は成立します。見つけるのは、モデルが予想したバスのビット列との比較です。3番は、ほかの受信側がACKを返す3ノードの場面では現れません。受信側が1つだけの場面で見つかります。8番は、クロックに差があるこの環境だから見つかります。

## 構成と件数

| 構成 | `TSEG1`／`TSEG2`／`SJW` | サンプル点 | クロックの差 |
| --- | --- | --- | --- |
| `skew8` | 13／6／4 | 70 % | ノード1が0.8 %遅い、ノード2が0.8 %速い |
| `skew5-late` | 14／5／3 | 75 % | ノード0が0.5 %遅い、ノード1が0.5 %速い |

どちらも1ビット20クォンタムです。再同期で吸収できるクロックの差の目安は、よく引用される式`SJW ÷ (2 × 10 × 1ビットのクォンタム数)`で、順に1.0 %と0.75 %です。試験の差はその内側です。この式そのものは、仕様の本文と照合していません。

JUnitは、smokeが28件、nightlyが32件です。1構成あたり、固定2、乱数1（nightlyは3）、変異10、要求と目標の判定1です。

## 実行

Python 3.10以上とIcarus Verilogを使い、リポジトリのルートで実行します。

```sh
python3 examples/local-can/run.py --out artifacts/local-can
python3 examples/local-can/run.py --profile nightly --seed 17 --out artifacts/local-can-nightly
python3 examples/local-can/run.py --configuration skew8 --demo-bug 5 --out artifacts/local-can-bug5
python3 -m unittest discover -s examples/local-can/tests
```

`--demo-bug 1..10`は通常のケースにも誤りを入れ、終了コード1になることを確かめるためのものです。出力先には、`manifest.json`、ケースごとの`vectors.txt`・`simulation.log`・`wave.vcd`・`result.json`、`coverage.json`、`summary.json`、`junit.xml`が残ります。波形には、バス、3つのノードの出力と読む値、乱し、各ノードの報告を入れています。クロックとノードの内部は入れていません。

セルフテストは22件です。モデルの単体（CRCの2通りの計算、手で求めたビット列、スタッフの往復、競合の順、ACKなしで128に止まること、32回でバスオフになり128回の後に戻ること、カウンターの規則）、計画（seedの再現、変異とケースの対応、行と件数の一致、遠すぎる乱しの拒否）、実RTLでの全構成の実行と証跡、期待値を1か所変えたときに決まったラベルで不合格になること、を確かめます。

## 確認範囲と残る制限

- **再同期ジャンプ幅による制限は確かめていません。** 位相のずれを`SJW`で打ち切らず全部詰める誤りを入れても、すべての実行が合格します（下の確認記録）。バスのランは公称のビット時間に丸めて比べるので、1〜2クォンタムの違いは見えません。ビットの途中にエッジを作る乱しは、1ビット単位のモデルと合わなくなるので用意していません。
- ビットタイミングの検査は、2つの構成とクロックの差0.8 %・0.5 %の範囲です。許容できる差の限界、サンプル点の最適さ、ノイズによるエッジは確かめていません。伝搬遅延はありません（3ノードは遅延0でつながり、入力の同期段の2クロックだけです）。
- モデルとRTLは同じ人が書いています。外部の実装、公開のフレーム例、ISO 16845の適合試験とは照合していません。CAN 2.0への適合や相互接続性の確認ではありません。
- 乱しは1ビット単位で、場面あたり1〜2個が中心です。フラグの後にドミナントが続く場合の追加のカウントは実装しておらず、その場面もありません。
- 過負荷フレームは反応として出すだけです。過負荷フレームが2回を超えて続く場合は確かめていません。
- エラーパッシブの受信側が、パッシブのフラグの後に誤りを重ねる場面、バスオフの間のドミナント（11ビットの数え直し）は、固定の場面にありません。
- 単一クロック領域の同期回路で、リセットは非同期です。リセット解除の同期、クロックの停止、低電力のスリープと起床は扱いません。
- 車載の手順書が挙げるLIN、車載Ethernet、CAN FDは扱っていません。
