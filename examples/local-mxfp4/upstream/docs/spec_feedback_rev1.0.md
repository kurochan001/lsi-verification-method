## B1. 5.6 節 — FP32 加算器の丸めビット位置がオフバイワン

### 該当箇所

5.6 節 `mxfp4_fp32_add_core` の骨格コード。

```systemverilog
    ext_s   = {1'b0, sig_s, 3'b000};        // ← 28bit = carry 1 + 仮数 24 + GRS 3
    ...
    // 丸め(RNE)。norm[27:4]が24bit有効, [3]=G, [2]=R, [1:0]->S
    lsb = norm[4]; g = norm[3]; rnd = norm[2]; stk = |norm[1:0];
    round_up = g & (rnd | stk | lsb);

    logic [24:0] rounded;
    rounded = {1'b0, norm[27:4]} + round_up;
```

### 問題

`ext_s` / `sig_l_ext` を `{1'b0, sig(24), 3'b000}` で構成しているので、28bit の内訳は

```
bit27      = carry
bit[26:3]  = 24bit 有効仮数
bit2/1/0   = G / R / S
```

でなければならない。コードは有効仮数を `norm[27:4]`、guard を `norm[3]` としており、
全体が 1 ビット上にずれている。コメント `// norm[27:4]が24bit有効, [3]=G, [2]=R, [1:0]->S`
は 28 = 24 + 1 + 1 + 2 の分割を前提にしているが、`ext_s` の構成 (1 + 24 + 3) と一致しない。

### 具体例: `1.0 + 1.0` が `3.0` になる

| 変数 | 値 |
|---|---|
| `a_exp = b_exp` | 127 |
| `a_sig = b_sig` | `24'h800000` |
| `sig_l_ext = aligned_s` | `28'h4000000` (bit26 = 1) |
| `sum` | `28'h8000000` (bit27 = 1 → 桁上げ) |
| `norm = sum >> 1` | `28'h4000000` (bit26 = 1) |
| `exp_n` | 128 |

- **正しい丸め**: `lsb = norm[3] = 0`, `g = norm[2] = 0` → `round_up = 0`
  `rounded = {1'b0, norm[26:3]} = 25'h0800000` → `r_sig = 24'h800000`
  パック結果 `{0, 8'd128, 23'h000000}` = **`0x40000000` = 2.0** ✓

- **骨格コードの丸め**: `lsb = norm[4] = 0`, `g = norm[3] = 0` → `round_up = 0`
  `rounded = {1'b0, norm[27:4]} = 25'h0400000` → `r_sig = 24'h400000`
  パック結果 `{0, 8'd128, 23'h400000}` = **`0x40400000` = 3.0** ✗

`r_sig` の bit23 (暗黙 1 の位置) が 0 になっている時点で、有効仮数として不正である。

### 修正案

```systemverilog
-   // 丸め(RNE)。norm[27:4]が24bit有効, [3]=G, [2]=R, [1:0]->S
-   lsb = norm[4]; g = norm[3]; rnd = norm[2]; stk = |norm[1:0];
+   // 丸め(RNE)。norm[26:3]が24bit有効, [2]=G, [1]=R, [0]=S
+   lsb = norm[3]; g = norm[2]; rnd = norm[1]; stk = norm[0];
    round_up = g & (rnd | stk | lsb);

    logic [24:0] rounded;
-   rounded = {1'b0, norm[27:4]} + round_up;
+   rounded = {1'b0, norm[26:3]} + round_up;
```

5.4 節の内部信号ビット幅表にある `aligned(GRS 付) | 28 | 桁上げ 1 + 24 + G + R + S` は
正しいので、こちらを正として骨格コードを直せばよい。あわせて 5.4 節の表に
「bit27 = carry / bit[26:3] = 有効仮数 / bit[2:0] = GRS」というビット割当を明記すると
再発を防げる。

### 検証での裏付け

修正版は `tb_mxfp4_bdp` の R2a (ランダム累積 2 万系列) と R2d (指数境界) で
リファレンスモデルとビット一致 100%。骨格コードのビット位置では R2a が全滅する。

## B2. 5.5 節 — EX1/EX2 の段割りがアキュムレータの RAW ハザードを生む

### 該当箇所

5.5 節「パイプライン分割(EX1 / EX2)」

> - EX1(アライン段): i2f 変換(絶対値・LZC・仮数配置・e_conv 合成)+ **アンパック + 指数比較 + アライン右シフト + GRS 生成**。段末レジスタに large 有効仮数、aligned small(GRS 付)、実効演算フラグ、larger_exp、out_sign を格納。
> - EX2(加算・丸め段): 実効加減算 + 正規化 + RNE 丸め + 再正規化 + 範囲判定 + FP32 パック + **アキュムレータ更新**。

### 問題

「アンパック + 指数比較 + アライン」の対象は `acc` である。したがって EX1 (S4) で `acc` を
**読み**、EX2 (S5) で `acc` を**書く**ことになる。

一方 8.4 節は「1 サイクルに 1 ブロックペアを全 16 PE へ同時投入する」と規定している。
3.2 節の段構成 (S1..S6) でブロック `j` を投入サイクル 0 とすると:

| ブロック | EX1 で acc を読む | EX2 で acc を書く |
|---|---|---|
| `j`   | サイクル 3 | サイクル 4 |
| `j+1` | サイクル 4 | サイクル 5 |
| `j+2` | サイクル 5 | サイクル 6 |

`j+1` はサイクル 4 で `acc` を読むが、`j` の書き込みは同じサイクル 4 の末である。
`j+1` が読むのは `j` を反映する前の値、`j+2` は `j` までを反映した値、というように
**累積が偶数番目と奇数番目の 2 本のチェーンに分裂する**。KBLK ≥ 2 の内積列がすべて誤る。

*(第 2 版: 初版では「最大 3 ブロック分の寄与が失われる」と書いたが、正しくは偶奇 2 本への
分裂。仕様書チームの精密化による。)*

### 修正案

5.6 節の骨格コード `mxfp4_fp32_add_core` は**加算器全体が 1 つの組合せモジュール**として
書かれており、こちらに従えば `acc` の読み書きは EX2 の 1 サイクルに閉じる。
5.5 節の記述を 5.6 節に合わせるのが最小の修正である。

```
- EX1(アライン段): i2f 変換 + アンパック + 指数比較 + アライン右シフト + GRS 生成。
+ EX1(変換段): i2f 変換(絶対値・LZC・仮数配置・e_conv 合成)。段末レジスタに
+   項の符号 / 内部指数 / 24bit 有効仮数 / ゼロ・NaN フラグを格納。
+   ※ acc を参照する処理をこの段に置いてはならない。EX1 で acc を読み EX2 で
+     書く構成にすると、8.4 節の 1 ブロック/サイクル連続投入で RAW ハザードになる。
- EX2(加算・丸め段): 実効加減算 + 正規化 + RNE 丸め + 再正規化 + 範囲判定 + FP32 パック + アキュムレータ更新。
+ EX2(加算・丸め段): acc のアンパック + 指数比較 + アライン右シフト + GRS 生成 +
+   実効加減算 + 正規化 + RNE 丸め + 再正規化 + 範囲判定 + FP32 パック + アキュムレータ更新。
```

図4 (BDP データパス) の段境界、3.2 節の段構成表、および 5.6 節コード内の
「`// ---- EX1: ... ----` / `// ---- EX2: ... ----`」コメントも同様に直す必要がある。LAT = 6 と 1 ブロック/サイクルの
スループットはこの配分で両立する (クリティカルパスは EX2 に集中するが、5.1 節の
「学習・検証優先」の方針と整合する)。

### 検証での裏付け

`tb_top` の Driver は内積列を**隙間なく連続投入**する構成にしてあり、このハザードがあれば
即座に破れる。修正版の配分では 5,000 系列の制約付きランダムでリファレンスとビット一致 100%。

## B3. 7.3 節 — 量子化の丸め結果の割り当てが 7.2 節の確定表と矛盾

### 該当箇所

7.3 節 `e2m1_quantize` の骨格コード。

```systemverilog
      up = g & (s | m1);              // binade内 x.0/x.5 の RNE 増分
      unique case (1'b1)
        ...
        (e_rel == -10'sd1):   mag3 = up ? 3'b010 : 3'b001; // 0.5 or 1.0
        (e_rel ==  10'sd0):   mag3 = up ? 3'b011 : 3'b010; // 1.0 or 1.5
        (e_rel ==  10'sd1):   mag3 = up ? 3'b101 : 3'b100; // 2.0 or 3.0
        (e_rel ==  10'sd2):   mag3 = up ? 3'b111 : 3'b110; // 4.0 or 6.0(6超も6)
```

### 問題

`up = g & (s | m1)` という式そのものは正しい (「`m1` を仮数 LSB とみなした RNE の増分」)。
誤っているのは**その使い方**で、`up` を 2 択のセレクタにしている点である。
E2M1 の仮数は 1bit なので、丸め後の値は `m1 + up` で決まり、桁上がりが次の binade へ
繰り上がる。正しくは

```
up    = g & (s | m1)   // RNE の増分
rm1   = m1 ^ up        // 丸め後の仮数ビット
carry = m1 & up        // 次の binade への繰り上がり
```

骨格コードは `m1` を捨てて `up` だけで出力を決めているため、`m1 = 1` の入力が
すべて 1 段下のコードに落ちる。

### 具体例 (いずれも 7.2 節の区間表に反する)

| scaled 値 `v` | FP32 frac | m1/g/s | `up` | 骨格コードの出力 | 7.2 節の正解 |
|---|---|---|---|---|---|
| 1.5 (`e_rel=0`) | `0x400000` | 1/0/0 | 0 | `010` = 1.0 ✗ | `011` = 1.5 |
| 1.75 (`e_rel=0`, タイ) | `0x600000` | 1/1/0 | 1 | `011` = 1.5 ✗ | `100` = 2.0 |
| 3.0 (`e_rel=1`) | `0x400000` | 1/0/0 | 0 | `100` = 2.0 ✗ | `101` = 3.0 |
| 0.75 (`e_rel=-1`, タイ) | `0x400000` | 1/0/0 | 0 | `001` = 0.5 ✗ | `010` = 1.0 |

7.2 節の区間表 `[1.75, 2.5] -> 100` / `(1.25, 1.75) -> 011` / `[0.75, 1.25] -> 010` は
すべて正しく、骨格コードだけがこれを満たさない。

### `e_rel = -1` は別扱いが要る

`v ∈ [0.5, 1)` の binade には E2M1 の代表点が 0.5 しかなく、`x.5` に相当する 0.75 は
**表現できない**。したがってこの区間では `up` / `carry` の枠組みが使えず、丸め先は
0.5 か 1.0 の 2 択、中点 0.75 のタイは偶数仮数側 (1.0, M=0) へ入る。判定は `m1` 単独になる。

7.3 節の表で `-1 | [0.5, 1) | 中点 0.75 判定で 001 or 010` としているのは正しいので、
コードだけがこの表と食い違っている。

### 修正案

```systemverilog
      up    = g & (s | m1);
+     rm1   = m1 ^ up;      // 丸め後の仮数ビット
+     carry = m1 & up;      // 次の binade への繰り上がり
      unique case (1'b1)
        ...
-       (e_rel == -10'sd1):   mag3 = up ? 3'b010 : 3'b001;
+       // [0.5, 1) の代表点は 0.5 のみ。0.75 は表現できないので m1 単独判定。
+       (e_rel == -10'sd1):   mag3 = m1 ? 3'b010 : 3'b001;
-       (e_rel ==  10'sd0):   mag3 = up ? 3'b011 : 3'b010;
+       (e_rel ==  10'sd0):   mag3 = carry ? 3'b100 : {2'b01, rm1};
-       (e_rel ==  10'sd1):   mag3 = up ? 3'b101 : 3'b100;
+       (e_rel ==  10'sd1):   mag3 = carry ? 3'b110 : {2'b10, rm1};
-       (e_rel ==  10'sd2):   mag3 = up ? 3'b111 : 3'b110;
+       // 繰り上がり先 8.0 は表現できないので 6.0 へクランプ
+       (e_rel ==  10'sd2):   mag3 = carry ? 3'b111 : {2'b11, rm1};
```

あわせて 7.3 節の場合分け表も更新を推奨する。現在

| e_rel | 区間 | 出力 |
|---|---|---|
| 0 | [1, 2) | 010 or 011 |

とあるが、`v ≥ 1.75` は繰り上がって `100` になるため 3 通りである。

### 検証での裏付け

`e_rel` × 代表 frac 11 通り (G/S の全組合せを踏む) の全数照合を `tb_quant_encoder` の
D5 に実装した。修正版は 7.2 節の確定表と 100% 一致する。

## B4. 7.3 節 — `unique case` で `is_zero` と `e_rel` 条件が同時成立する

### 該当箇所

```systemverilog
      unique case (1'b1)
        is_zero:              mag3 = 3'b000;
        (e_rel <= -10'sd3):   mag3 = 3'b000;               // < 0.25
```

### 問題

`is_zero` は「入力がゼロまたはデノーマル (DAZ)」を示す。このとき `exp_field(Vi) = 0` なので

```
e_rel = exp_field(Vi) - X_biased = -X_biased
```

となり、`X_biased ≥ 3` (= `amax_exp ≥ 5`、すなわち amax が `2^-122` 程度以上) では
`e_rel ≤ -3` も同時に成立する。実用上ほぼすべてのブロックが該当するため、
**ゼロ要素を 1 つでも含むブロックで unique 違反の実行時警告が出続ける**。

10 章が `unique case` を「重複禁止の実行時検査」として挙げている以上、仕様書の
サンプルコード自体がその検査に引っかかるのは避けたい。

### 修正案

`is_zero` を `case` の外へ出す。

```systemverilog
+   if (is_zero) begin
+     mag3 = 3'b000;
+   end else begin
      unique case (1'b1)
-       is_zero:              mag3 = 3'b000;
        (e_rel <= -10'sd3):   mag3 = 3'b000;
        ...
      endcase
+   end
```

## B5. 9.2 節 — リファレンスコードのスライス位置が 2.3 節と不整合

### 該当箇所

9.2 節のリファレンスモデル。同一コードブロック内で 2 つの前提が混在している。

```systemverilog
  // (1) scale が下位 8bit という前提
  s += dec2_of(a[8 + 4*i +: 4]) * dec2_of(b[8 + 4*i +: 4]);

  // (2) scale が上位 8bit という前提
  if (a_blk[j][135 -: 8] == 8'hFF || b_blk[j][135 -: 8] == 8'hFF)
```

### 問題

2.3 節の `mxfp4_block_t` は packed struct で `scale` が先頭メンバなので、
**scale は `[135:128]`、要素 `i` は `[4*i +: 4]`** が正しい。(2) は正しく (1) が誤り。
9.5 節の SVA も `a_block[135:128]` を使っており、(2) と整合している。

節末に「スライス位置は 2.3 節の定義に合わせて実装すること。上記は方針を示す擬似コード
である」という注記はあるが、同一コードブロック内で 2 つの流儀が混在していると
読み手が「どちらかが正しい」と判断できない。

### 修正案

```systemverilog
-   s += dec2_of(a[8 + 4*i +: 4]) * dec2_of(b[8 + 4*i +: 4]);
+   s += dec2_of(a[4*i +: 4]) * dec2_of(b[4*i +: 4]);
```

2.3 節に「本書のコード例はすべて `{scale[7:0], elems[127:0]}` の 136bit 並びを前提とする」
と一文を足すと、以降の節で迷わなくなる。

## C1. 9.4 節 — `cg_bdp` のサンプルタイミングが段と一致しない

### 該当箇所

```systemverilog
covergroup cg_bdp @(posedge clk iff in_valid);
  cp_a_scale:    coverpoint a_block[135:128] { ... }
  cp_sop_sign:   coverpoint sop4_dbg[13];
  cp_sop_zero:   coverpoint (sop4_dbg == 0);
  cp_first_last: cross first, last;
  cp_exp_region: coverpoint exp_internal_dbg { ... }
endgroup
```

### 問題

`a_block` / `first` / `last` は投入時 (S1) の信号だが、3.2 節の段構成より

- `sop4_dbg` は **S3** の出力 (投入から 3 サイクル後)
- `exp_internal_dbg` は **S5** の信号 (投入から 4 サイクル後)

である。`iff in_valid` でサンプルすると、`sop4_dbg` / `exp_internal_dbg` については
**3〜4 サイクル前に投入された別ブロックの値**を拾う。値の分布だけを見るなら偶然
埋まることもあるが、`cross first, last` との相関は完全に崩れ、「どの入力条件で
どの指数領域を踏んだか」がカバレッジから読めなくなる。

### 修正案

covergroup を段ごとに分割し、それぞれ対応する段の valid でサンプルする。

```systemverilog
covergroup cg_bdp_in @(posedge clk iff in_valid);
  cp_a_scale: coverpoint a_block[135:128] { ... }
  cp_b_scale: coverpoint b_block[135:128] { ... }
  cp_first: coverpoint first;
  cp_last:  coverpoint last;
  cp_first_last: cross cp_first, cp_last;
endgroup

covergroup cg_bdp_sop @(posedge clk iff sop_valid);   // S3 の valid

endgroup

covergroup cg_bdp_exp @(posedge clk iff exp_valid);   // S5 の valid
  cp_exp_region: coverpoint exp_internal_dbg { ... }
endgroup
```

9.4 節末の「デバッグ用に SoP4 / exp_internal / e_rel を観測ポート (`*_dbg`) として
引き出す」に、**対応する段の valid も併せて引き出す**旨を追記すると実装しやすい。

分割版で sukimasim を走らせ、`cg_bdp_in` / `cg_bdp_sop` / `cg_bdp_exp` すべて 100%

## C2. 9.4 節 — `cg_enc` の `bins hi = {[3:10]}` が到達不能

### 該当箇所

```systemverilog
  cp_erel: coverpoint e_rel_dbg {
    bins low = {[-10:-3]}; bins b_m2 = {-2}; bins b_m1 = {-1};
    bins b0 = {0}; bins b1 = {1}; bins b2 = {2}; bins hi = {[3:10]};
  }
```

### 問題

7.4 節より `X_biased = clamp(amax_exp - 2, 0, 254)`、かつ amax の定義から
すべての要素で `exp_field(Vi) ≤ amax_exp`。したがって

- `amax_exp > 2` のとき: `e_rel ≤ amax_exp - (amax_exp - 2) = 2`
- `amax_exp ≤ 2` のとき: `X_biased = 0` なので `e_rel ≤ amax_exp ≤ 2`

いずれの場合も `e_rel ≤ 2` が構造的に成り立ち、**`quant_encoder` の中で `e_rel ≥ 3` は
決して発生しない**。9.4 節末の「カバレッジ 100%(除外bin明記)を回帰の合格条件とする」を
満たすには、この bin を除外として明記する必要がある。

なお `bins low = {[-10:-3]}` も、実際の値域が `-252..2` なので下限が足りない。
`e_rel = -50` のような値がどの bin にも入らず、集計から落ちる。

### 修正案

```systemverilog
  cp_erel: coverpoint e_rel_dbg {
-   bins low = {[-10:-3]};
+   bins low = {[-300:-3]};        // 値域は -252..2
    bins b_m2 = {-2}; bins b_m1 = {-1};
    bins b0 = {0}; bins b1 = {1}; bins b2 = {2};
-   bins hi = {[3:10]};
+   // e_rel = exp_field(Vi) - X_biased、X_biased = max(0, amax_exp - 2)、
+   // exp_field(Vi) <= amax_exp より e_rel >= 3 は構造的に発生しない
+   ignore_bins hi = {[3:10]};
  }
```

`e_rel ≥ 3` の経路 (7.3 節の `default` 分岐 = 6.0 クランプ) 自体は死んでいないので、
`e2m1_quantize` **単体**では `e_rel` を直接与えて検査できる。9.3 節の D5 に
「`e2m1_quantize` を単体でインスタンス化し `e_rel` を直接駆動して `default` 分岐も
検査する」と明記することを推奨する。

## C3. 7.4 節 — X_biased の上限クランプは構造的に発火しない (注記推奨)

7.4 節の `X_biased = clamp(amax[30:23] − 2, 0, 254)` は数式としては正しいが、
`amax_exp` は 7.5 節により `0xFF` が NaN/Inf として bypass されるので実効的な最大は
`0xFE = 254`、したがって `amax_exp - 2` の最大は **252** であり、**上限 254 のクランプは
決して発火しない**。

これを 8bit 幅で素直に実装すると

```systemverilog
  else if (amax_exp >= (8'd254 + 8'd2)) xb = 8'd254;   // 8'd256 が 8'd0 に潰れる
```

のように右辺が桁溢れし、**条件が常に真**になる (Verilator の `UNSIGNED` 警告で検出できる)。
7.4 節に「上限クランプは表現上のものであり、`amax_exp <= 0xFE` である以上 `X_biased` の
最大は 252 なので到達しない。実装は下限クランプのみでよい」と一文を添えると、この
踏み間違いを防げる。

*(第 2 版での訂正: 初版では最大値を 253 と記していたが、`amax_exp = 0xFF` は 7.5 節で
bypass されるため実効最大は 252。仕様書チームの指摘による。結論は変わらない。)*

## C4. 6.5 節 — リファレンスの二重丸め (注記推奨)

6.5 節の方針 2 は「double で累積 → 各ステップで FP32 へ RNE」という手順である。
**両オペランドが binary32 で表現可能な範囲に収まる限り、この二重丸めは無害**である
(中間精度 53bit ≥ 2p+2 = 50bit)。したがって R2a のような範囲内テストで方針 2 が
偽判定を出すことはない。

危険なのは項が binary32 の範囲外に出る R2b / R2c と飽和境界の近傍で、ここでは
double 側の丸めが先に効いて FP32 の GRS 判定と食い違い得る。

実装では acc と項を**共通指数の広幅整数 (128bit) へ展開して厳密に加算し、1 回だけ
RNE で FP32 へ丸める**方式を採った。この方式には副次的な利点がある。RTL の 28bit
GRS パス (アライン量 26 で飽和) とアルゴリズムが独立になるため、**飽和シフトの
正しさ自体が検証対象になる**。

6.5 節には「方針 2 は R2a のような範囲内テストでは厳密。境界系 (R2b / R2c / 飽和近傍)
は方針 3 を基準器とする」と書き分けて追記することを提案する。実装は
[`tb/mxfp4_ref_pkg.sv`](../tb/mxfp4_ref_pkg.sv) の `ref_fp32_add_term()` /
`ref_fp32_add_fp32()` を参照。

*(第 2 版: 適用条件は仕様書チームの補足による。)*

## C5. 8.4 / 8.6 節 — `c_o` が有効になるサイクルが未記載 (注記推奨)

8.4 節は done を cycle `1 + KBLK + LAT` に立てると規定し、8.6 節は結果を
「16 本の出力レジスタへ全並列ラッチする」と規定している。両者を満たすと
`c_latch` と `done` が同じサイクルに立ち、**出力レジスタが更新されるのはその
サイクルの末**になる。したがって

> ホストは done = 1 を見て並列に読み出す (8.6 節)

を字義どおり「done と同じサイクルで読む」と解釈すると、1 つ前の GEMM の結果を読むことになる。

8.6 節に「`c_o` が読めるのは done アサートの**次サイクル以降**。結果は次の `start` まで
保持されるので、ホストは done 検出後の任意のサイクルで読み出してよい」と明記することを推奨する。

## 参考: 検証環境で踏んだ落とし穴

仕様書の誤りではないが、9 章の TB を実装する側が同じ穴に落ちないよう共有する。

- **Verilator で `PROCASSINIT` 警告を抑制してはならない。** TB の駆動信号に
  宣言時初期値を付ける (`logic [135:0] a_block = '0;`) とプロセスからの駆動が反映されず、
  DUT に 0 が入り続ける。この警告を握り潰すと「RTL が常に +0 を返す」という偽の不具合を
  追うことになる (実際に 1 回踏んだ)。TB の駆動信号は初期値を付けず、リセットシーケンスで
  初期化する。

- **`$past` の第 1 引数には式ではなく中間信号を渡す。** `out_valid` の逆向き因果を
  `out_valid |-> $past(in_valid && last, LAT)` と書くと、Verilator では成立するが
  sukimasim 0.9.9.2 では約半数が偽陽性で落ちる。切り分けた結果、**第 1 引数が式のとき
  sukimasim が 1 tick 余分に遅れた値を返す**ためと判明した。IEEE 1800-2023 §16.9.3 は
  `expression1` に任意の式を許し「`k` 番目の strictly prior なティックでのサンプル値」を
  返すと規定しているので、これは sukimasim 側の不具合である (最小再現:
  [`repro/past_expr_minimal.sv`](../repro/past_expr_minimal.sv))。
  `assign` で単一信号にしてから渡せば両シミュレータとも規定どおりに動くので、
  9.5 節に逆向きプロパティを追加する場合はその形を推奨する。
  なお `number_of_ticks` の数え方自体は両者とも LRM 準拠だった。

- **Icarus Verilog は使えない。** 5.6 節の LZC が使う `for` ループ内の `break` を
  Icarus Verilog 12.0 が未サポート (`sorry: break statements not supported`)。
  10 章が `for + break` を検証対象言語機能に挙げている以上これは想定内だが、
  11 章の段階 1〜2 で手軽な参照シミュレータとして使えない点は認識しておくとよい。

## A1. 5.6 節 — 桁上げ右シフト時に押し出しビットを sticky へ OR していない

### 指摘内容 (仕様書チーム)

5.3 節本文 5. は「加算で桁上げ(bit27 = 1)が出たら右シフト 1・指数 +1
(**押し出しビットを sticky へ OR**)」と正しく規定しているが、5.6 節の骨格コードは

```systemverilog
    if (sum[27]) begin           // 桁上げ: 右シフト1
      norm  = sum >> 1;          // ← sum[0] が捨てられている
      exp_n = exp_l + 11'sd1;
    end
```

となっており `sum[0]` を落としている。B1 の修正だけを適用した骨格を float32 真値と
30 万件照合して 126 件不一致、すべて実効加算 + 桁上げ + sticky ≠ 0 の系。
反例 `0x417C7180 + 0x3F00FC52` → 骨格 `0x418240A2` / 真値 `0x418240A3` (1ulp 差)。

### 実装側の確認

**指摘のとおりで、A1 は B1 とセットで Rev.1.1 に入れる必要がある。**
実装 (`rtl/mxfp4_fp32_add_core.sv`) は 5.3 節本文に従って sticky を保存済みだった。

```systemverilog
    end else if (sum[ALIGN_W-1]) begin
      // 桁上げ: 右シフト 1 / 指数 +1。押し出しビットは sticky へ OR。
      norm    = sum >> 1;
      norm[0] = norm[0] | sum[0];
      exp_n   = exp_l + 11'sd1;
    end
```

提示された修正案 `norm = {1'b0, sum[27:2], (sum[1] | sum[0])}` と論理的に同一
(`sum >> 1` は `norm[0] = sum[1]`、そこへ `sum[0]` を OR)。
反例も期待どおり `0x418240A3` を返す。

### 検証側の穴 (実装側からの報告)

**当初の回帰は A1 を検出できなかった。** sticky 保存を削除するミューテーションを
かけても R2a (20,000 系列) が 0 errors で通ってしまった。原因は BDP 経由のテストの
構造的な制約である。

1. **第 2 項の仮数が 13bit しかない。** term は i2f 由来なので有効仮数は
   `mag13` を左詰めしたもので、下位 11bit 以上が必ず 0。アライン量が 14 以下では
   sticky が立たない。
2. **acc の仮数も埋まりにくい。** 内積列が短いと acc の仮数は 13bit のままで、
   桁上げに必要な「`sig_l` の上位がほぼ全 1」という条件が成立しにくい。
3. **R2a は指数差が大きすぎる。** 各ブロックの `scaled_exp` を独立一様
   (−120..+110) に取るため隣接ブロック間の指数差は平均 100 を超え、アライン量 26 で
   飽和する領域しか踏まない。sticky が丸めに効くのは指数差が中程度 (概ね 15〜25) の
   帯だけである。

指数差を 0..30 で掃引する `R2e` を追加してもまだ検出できず、最終的に
**加算器を汎用 FP32 加算器として直接叩く単体テスト** (`tb/tb_fp32_add.sv`) が必要だった。

| テスト | sticky 保存あり (現行) | sticky 保存なし |
|---|---|---|
| R2a (20,000 系列) | 0 errors | 0 errors (検出できず) |
| R2e (指数差 0..30 掃引) | 0 errors | 0 errors (検出できず) |
| **tb_fp32_add (660,001 件)** | **0 errors** | **A1 反例を含め多数 fail** |

`tb_fp32_add` は次の 4 つを回す。

- 提示された反例 `0x417C7180 + 0x3F00FC52`
- 同符号・指数差 1..30 の狙い撃ち (仮数を `0x7FFFFF` 近傍に寄せて桁上げを誘発)
- 一様ランダム
- 指数が近いランダム (相殺・桁上げが起きやすい)

### 仕様書への提案 (新規)

**9.3 節のテストシナリオ表に、加算器を単体で検証する行を追加すべきである。**
現行の 11 章ロードマップは段階 3「`mxfp4_i2f` + `mxfp4_fp32_add_core`(統合パス)」の
完了基準を R2a (BDP 経由) だけに置いているが、上記のとおり BDP 経由では第 2 項が
13bit 仮数に制約され、統合パスの丸め経路を覆いきれない。

| ID | 種別 | 対象 | 内容 | 合否基準 |
|---|---|---|---|---|
| R2f | ランダム | `mxfp4_fp32_add_core` 単体 | 両オペランドに任意の FP32 (正規数) を与える。同符号・指数差 1..30 の狙い撃ちを含む | 厳密リファレンスとビット一致 100% |
