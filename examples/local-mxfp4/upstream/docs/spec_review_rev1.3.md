## D1. 7.7 節「統計的に正方向へ偏る」は符号が逆

### 該当箇所

> OCP 純正 Algorithm 1 をそのまま使うと、scaled 最大値が 6〜8 に達してクランプが起き、
> **統計的に正方向へ偏る**(バイアスが生じる)。

### 問題

クランプは scaled 値を E2M1 の最大値 6.0 で切り詰める操作なので、
量子化後の**大きさは必ず小さくなる**。したがってバイアスは原点方向 (負方向) に生じる。
「正方向へ偏る」は符号が逆である。

### 具体例

X_biased = clamp(amax_exp - 2, 0, 254) より scaled amax は必ず [4, 8) に入る
(7.4 節)。amax の仮数が 1.5 以上のブロックでは scaled amax > 6 となり、
その要素は 6.0 へ丸められる。amax の仮数は一様に近く分布するので、
**約半数のブロックで最大要素がクランプされる**。

実測 (`make sim-q34 N_Q34=20000`、ブロック内指数を 0〜5 の幅で散らした
ランダム FP32 ブロック 645,376 要素):

| 指標 | Algorithm 1 | 3/4 スケーリング (4/3 倍で復元) |
|---|---:|---:|
| scaled 値が 6.0 超だった要素 | 20.36 % | 0 % |
| 大きさの偏り Σ(\|dec\| - \|orig\|) / Σ\|orig\| | **-0.04668** | -0.00289 |
| 符号付きの偏り Σ(dec - orig) / Σ\|orig\| | 0.00001 | 0.00061 |
| 正規化 RMS 誤差 sqrt(Σerr² / Σorig²) | 0.14067 | 0.12206 |

大きさの偏りが **負** (-4.7 %) であり、3/4 スケーリングでこれが -0.29 % まで
縮む (1/16)。符号付きの偏りは正負がキャンセルするためどちらもほぼ 0 で、
クランプの影響はここには現れない。

### 修正案

```diff
-OCP 純正 Algorithm 1 をそのまま使うと、scaled 最大値が 6〜8 に達してクランプが起き、
-統計的に正方向へ偏る(バイアスが生じる)。
+OCP 純正 Algorithm 1 をそのまま使うと、scaled 最大値が 6〜8 に達してクランプが起き、
+量子化値の大きさが系統的に小さくなる(原点方向へのバイアスが生じる)。
```

なお 7.7 節が引く unbiased 性は stochastic rounding を前提とした主張であり、
本実装の roundTiesToEven では厳密な不偏にはならない。上表のとおり
3/4 スケーリングでも偏りは 0 にはならず、-0.29 % 残る。
「クランプが構造的に消える」ことと「不偏になる」ことは別なので、
本文でも区別しておくと実装者が誤解しない。

### 検証での裏付け

`tb/tb_quant_q34.sv` が Algorithm 1 版と 3/4 版の `quant_encoder` を並走させ、
それぞれ独立のリファレンス (`ref_encode_block_ex`、7.2 節の区間表を real 比較で
実装したもの) とビット一致することを確認したうえで上の統計を取っている
(80,686 チェック / 0 errors)。3/4 版で 6.0 超の要素が 0 件であることは
テストの合格条件に含めた。

## E1. 6.3 節: デノーマルを加算器へ渡す前に正規化する必要がある

### 該当箇所

> gradual underflow(デノーマル対応)は発展課題。対応する場合は、指数を 1 に固定して
> 仮数を右シフトし、GRS を維持したまま RNE 丸めする追加パスが要る。

### 補足したい点

出力側の記述は正確で、そのとおり実装すれば足りる (丸めの**前**にシフトすること、
という点も含めて)。しかし gradual underflow を入れると
**アキュムレータがデノーマルを保持するようになる**ため、入力側にも手当てが要る。

5.6 節の加算器は large / small を

```systemverilog
a_ge = (a_exp > b_exp) || ((a_exp == b_exp) && (a_sig >= b_sig));
```

で決めている。これは**仮数が [1, 2) に正規化されている**ことを前提とした比較である。
デノーマル (仮数が [0, 1)) を「指数フィールド 1、暗黙ビット 0」のまま渡すと、
指数だけ大きく絶対値は小さいオペランドが large 扱いになり、実効減算で
桁借りが起きて結果が壊れる。

### 具体例

`make sim-guf` の開発中に実際に踏んだケース (ブロック列 2 本):

```
j=0 : SoP4 = 408,  scaled_exp = -152   ->  acc = 51 x 2^-149   (デノーマル)
j=1 : SoP4 = -69,  scaled_exp = -146   ->  term = -552 x 2^-149
期待 : (51 - 552) x 2^-149 = -501 x 2^-149 = 0x800001F5
```

acc をそのまま (exp = 1, sig = 0x000033) で渡すと、term の内部指数は
i2f 由来で -13 なので `a_exp (1) > b_exp (-13)` により **acc が large** と判定される。
実際は |term| が 10 倍以上大きいので、

```
sum = sig_l_ext - aligned_s = 408 - 4416 < 0
```

と桁借りして結果が壊れる (実測 0x017FFF06、正しくは 0x800001F5)。
内部指数が負まで振れるのは 5.4 節が規定するとおりなので、
「FP32 のデノーマルは指数フィールド 1 が最小だから比較は壊れない」という
FP32 レベルの直感は BDP の内部では成立しない。

### 修正案 (発展課題の記述への追記)

```diff
 gradual underflow(デノーマル対応)は発展課題。対応する場合は、指数を 1 に固定して
 仮数を右シフトし、GRS を維持したまま RNE 丸めする追加パスが要る。
+アキュムレータがデノーマルを保持するようになるので、入力側にも手当てが要る:
+5.6 節の指数比較は仮数が [1, 2) にあることを前提としているため、デノーマルの
+acc は加算器へ渡す前に正規化する (先頭ゼロ数だけ左シフトし、内部指数を
+同じだけ下げる。内部指数は signed なので負になって構わない)。
+また 6.4 節の DAZ は acc に適用してはならない。適用すると自分で作った
+デノーマルを次のブロックでゼロに潰し、累積が壊れる。
```

### 検証での裏付け

`tb/tb_gradual_uf.sv` が FTZ 版と gradual 版の加算器 / BDP を並走させ、
それぞれのリファレンス (`ref_fp32_add_fp32_ex` / `ref_dot_series_ex`、
広幅整数で厳密加算してから 1 回だけ丸める) とビット一致することを確認する
(207,519 チェック / 0 errors、デノーマル出力は加算器単体 14,648 件 / BDP 経由 747 件、
うち 13,782 件は FTZ 版では潰れる)。上の正規化を外すと即座に落ちる。

## E2. 5.7 節: near/far 分割で LZA を使うなら減算専用の式で足りる

### 該当箇所

> near/far 二経路分割、LZA による正規化前倒し、HardFloat 流 recoded 形式は、
> 面積・遅延最適化のための発展課題として言及にとどめる。

### 補足したい点

言及にとどめる方針に異論はない。ただし実装してみると、**near path が実効減算に
限定される**おかげで LZA の pre-encoding が教科書の一般形よりずっと簡単になる。
発展課題に取り組む人向けに 1 行入れておくと迷わない。

near path の前提は「実効減算」かつ「指数差 0/1」なので、LZA へ渡す 2 数は
A >= B が保証される (指数差 0 なら a_ge が仮数比較で決まる、指数差 1 なら
`sig_l_ext >= 2^26 > (ext_s >> 1)`)。この条件下では

```
P_i = A_i ^ B_i,  Z_i = ~A_i & B_i
f_i = P_i & ~Z_{i-1}          (Z_{-1} = 0)
```

の先頭 1 の位置が、真の先頭 1 の位置と高々 1 しかずれない。
加算も扱う一般形 (G / Z / P の 4 通りに場合分けする形) は不要である。

導出: 上位から最初に A_i ≠ B_i となる位置を k とすると A_k = 1, B_k = 0 であり、
D = A - B = 2^k + (A_low - B_low)。k の 1 つ下から Z が r 個連続すると
借りがそこまで伝播して D は 2^(k-r) の帯に落ちるので、D の MSB は k-r か k-r-1。
`f_i = P_i & ~Z_{i-1}` はちょうどこの k-r を選ぶ。

### 検証での裏付け

`tb/tb_nearfar.sv` が統合パス版と near/far 版を FTZ / gradual の両モードで並走させ、
`r_sign / r_exp / r_sig / r_carry_ovf / r_zero` の全出力がビット一致することを
確認する (2,467,699 チェック / 0 errors、near 467,680 回 / far 532,328 回)。
LZA の予測誤差が 0 か 1 に収まっていることも毎回検査しており、
1bit 補正が実際に働いたのは 175,749 回だった。

一般形 (P_{i+1} で場合分けする加算用の式) を最初に実装したところ、
桁落ちの大きいケースで最大 6bit ずれて回帰が落ちた。減算専用の上式に
置き換えて解決している。

## E3. 3.3 節: ready を追加すると 9.5 節の p_latency はそのままでは成立しない

### 該当箇所

> ready を追加する場合は、in_valid かつ in_ready 非成立の間、valid とデータを
> 保持する規約とする(9.5 節の SVA で検証)。

および 9.5 節:

```systemverilog
property p_latency;
  @(posedge clk) disable iff (!rst_n)
    (in_valid && last) |-> ##LAT out_valid;
endproperty
```

### 問題

ready を追加すると、下流のバックプレッシャでパイプラインがストールする間
`##LAT` のサイクル数が伸びるため、`p_latency` (と `p_ovalid_cause`、`p_nan`) は
そのままでは成立しない。3.3 節が「9.5 節の SVA で検証」と書いているのは
`p_hold` を指していると読めるが、**残りのプロパティが壊れる**点は書かれていない。

### 修正案

クロッキングイベントを転送サイクルだけに修飾すれば、ready の有無にかかわらず
同じ記述で成立する。`iff` 修飾つきのイベント制御は IEEE 1800-2023 §9.4.2.3 の
条件付きイベント制御で、§16.14.6 の例 (`always_ff @(posedge clock iff reset == 0)`
から `posedge clock iff reset == 0` が推論クロックになる) のとおり
アサーションのクロックとしても使える。

```diff
 property p_latency;
-  @(posedge clk) disable iff (!rst_n)
+  @(posedge clk iff in_ready) disable iff (!rst_n)
     (in_valid && last) |-> ##LAT out_valid;
 endproperty
```

`in_ready` を常時 1 に固定した構成 (3.3 節の初期実装) では
サンプリングが元と完全に一致するので、既存の回帰には影響しない。

あわせて、デスティネーション側の義務も規定しておくと SVA が書ける:

```
out_valid を立てたら out_ready が立つまで下ろさず、その間 result を保持する。
```

これは AMBA AXI §A3.2.1 の VALID/READY 規約と同じ形である。

### 検証での裏付け

`tb/tb_bdp_flow.sv` が `mxfp4_bdp_fifo` (入力 FIFO + ready 拡張した BDP) に対し、
上流のギャップと下流のバックプレッシャをランダムに入れながら
リファレンスとのビット一致を確認する (4,057 チェック / 0 errors、
ストール 3,922 回 / FIFO 満杯 356 サイクル)。
`iff in_ready` 修飾を外すと `a_latency` が即座に失敗するので、
この修飾が効いていることも確認済み。
4-state シミュレータ (sukimasim) でも同じ TB を SVA 付きで走らせ、既定 N で
**1,257 チェック / 0 errors / 結果 1,250 件**と Verilator に一致することを
確認している (チェック数と結果数が一致。ストール回数など乱数系列に依存する
カウンタは当然ながら両者で異なる)。

なお AXI §A3.2.1 は「インタフェースの入力から出力への組合せパスを持たない」
ことも要求している。BDP 単体では `in_ready = ~(out_valid & ~out_ready)` と
なって組合せパスが残るので、AXI 準拠のソースへ直結するには
入力 FIFO を挟む構成 (`mxfp4_bdp_fifo`) が要る。3.3 節が FIFO に触れるなら
この理由を添えておくと構成の必然性が伝わる。
