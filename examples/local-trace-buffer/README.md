# オンチップのトレースバッファと、実機の不具合を固定回帰へ持ち帰る流れ

実機や試作では、回路の中を波形で見ることができません。この例は、回路の入力を毎クロック記録するオンチップのトレースバッファと、それで取り出した記録をシミュレーションの入力に直して、固定回帰にする流れを小さく示します。

1. 「実機」で、監視する回路（フレームの長さの検査）が、正しい通信に対してエラーを出す。トレースバッファは、そのエラーをトリガーにして前後の入力を記録する。
2. 記録を読み出す。読み出した内容は[`field/issue-0001.trace`](field/issue-0001.trace)です。
3. [`replay.py`](replay.py)が、記録を「既知の状態から始まる入力の列」に直す。
4. その列で、古い版の回路を動かすとエラーが再現し、直した版では出ない。これを毎回の回帰に入れる。

実機・FPGAでは何も実行していません。「実機」は、古い版の回路とトレースバッファをシミュレーションで動かしたものです。試作と実機の評価で、シミュレーションと何が違うかは、[試作と実機評価の手順](../../docs/method/prototyping-and-post-silicon.md)にまとめています。

## 仕様

### トレースバッファ（`rtl/trace_buffer.sv`）

| 入力・状態 | 動作 |
| --- | --- |
| `arm`（1クロックのパルス） | `post`・トリガーの選択・値・マスクを取り込み、次のクロックから捕捉を始める。捕捉中の`arm`は捕捉をやり直す |
| 捕捉中 | 毎クロック、`sample`（9ビット）をリングへ書く。`kept`は書いた数で、`DEPTH`で止まる |
| トリガー | `trig_sel=0`は`(sample & mask) == (value & mask)`、`trig_sel=1`は外部の信号（ここでは監視する回路のエラー）。捕捉中の最初の1回だけで、`post`の間は掛け直さない |
| トリガーの後 | `post`個（0〜`DEPTH-1`）を書いて止まる（`done`）。窓は最後の`min(書いた数, DEPTH)`個で、トリガーが早いと前の部分が短くなる |
| 読出し | `done`の間、`rd_req`ごとに、次のクロックで窓の次のサンプルを返す。古いものから順で、トリガーのサンプルに`rd_trig`、最後に`rd_last`を付ける。最後の後の要求と、`done`の前の要求は無視する |
| リセット | すべてを初期値へ戻す。窓も読めなくなる |

構成は`DEPTH=16`（`d16`）と`DEPTH=8`（`d8`）の2つです。

### 監視する回路（`rtl/frame_monitor.sv`）

フラグ（`0x7e`）の間のバイトの並びをフレームとし、フレームが`MAXLEN`（4）バイトを超えたとき、そのバイトの次のクロックに1クロックだけ`error`を出します。2つ続くフラグも、ちょうど4バイトのフレームも正しい通信です。

`MUTATION=1`は、実機に載っていた古い版です。フラグの直後のフラグをデータとして数えるので、2つ続くフラグの後のちょうど4バイトのフレームを長すぎると誤って報告します。正しい通信の中では、まれにしか起きない並びです。

テストベンチは、監視する回路の入力`{valid, data}`をトレースバッファの`sample`へ、`error`を外部のトリガーへつなぎます。

## 持ち帰りの流れ

`field-old-revision`のケースが「実機」です。古い版の回路に、約200クロックの正しい通信を流します。その中に、2つ続くフラグと4バイトのフレームが1回だけあります。トレースバッファは`post=3`・外部のトリガーで捕捉し、止まった後に読み出します。`d16`の読出しの内容は、保存したダンプと一致します（セルフテストが照合します）。

ダンプは1行に1サンプルで、番号、`valid`、`data`、トリガーの印です。

```text
05 1 7e 0
06 1 7e 0
07 1 10 0
08 0 99 0
09 1 20 0
0a 1 30 0
0b 1 40 0
0c 1 7e 1
```

`replay.py`は、ダンプを次の規則で入力の列に直します。

- **既知の状態から始める。** 窓の先頭の時点で、回路の中の状態（フレームの長さ）は分かりません。データの後のフラグの直後は、どの版でも長さが0なので、窓の中で最初のその点から再生を始めます。再生の前にリセットをかけます。
- **トリガーより前に既知の状態が要る。** トリガーのサンプルに見えるエラーは、それより前のバイトから生まれるので、既知の状態はトリガーより前になければなりません。満たさない窓は、短すぎるとして拒否します。
- **形の崩れたダンプは拒否する。** 番号の順、値の範囲、トリガーの印がちょうど1つであること、深さを超えないことを確かめます。

`d8`の窓では、トリガーの前に4サンプルしか残らず、その中にフラグがありません。`replay.py`はこの窓を拒否します（セルフテスト）。トリガーの前に何サンプル残すか（`DEPTH-1-post`）は、再生できるかどうかを決める設計の判断です。

再生の列は`replay-field-issue-0001`のケースになります。期待値は仕様どおりの回路のモデルなので、直した版は合格し、古い版（`detect-mutation1-by-replay`）は、トリガーと同じ位置で`TR_DUT`になります。

## 独立した期待値

`model.py`は、仕様を書き直したモデルです。

- トレースバッファは、`arm`の後の全サンプルのリストを持ち、止まったときに最後の`min(書いた数, DEPTH)`個を窓にします。リングもポインターも持ちません。セルフテストは、ポインターで書いた3つ目の実装と、ランダムな400通りで窓を照合します。
- 監視する回路は、フラグからのバイト数を数えるだけのモデルです。古い版も同じモデルの切替えで持ちます。

テストベンチは各行の入力を与え、エッジの前の出力をビット一致で比べます。

| 比べるもの | 失敗のラベル |
| --- | --- |
| 出力が未知でないこと | `TR_X` |
| 監視する回路の`error` | `TR_DUT` |
| `busy`・`done` | `TR_STATUS` |
| `kept` | `TR_COUNT` |
| `rd_valid`・`rd_last`・読み出した値 | `TR_READ` |
| `rd_trig` | `TR_MARK` |

## 刺激

- **`capture`**：全目標に届く固定の場面です。何も捕捉していないときの読出し、リングが一周した後の一致のトリガー（`post`の中に同じ値をもう1つ置き、掛け直さないことを確かめる）、最後の後の読出し、マスクつきの早いトリガーと`post=0`、`post=DEPTH-1`、捕捉のやり直し、捕捉中のリセット、監視する回路のエラーを使う外部のトリガー、完了の後の`arm`を通します。
- **`field-fixed-revision`**：「実機」と同じ通信を、直した版で流します。エラーが出ないのでトリガーは掛からず、捕捉は続き、読出しは無視されます。
- **`replay-field-issue-0001`**：保存したダンプから作った再生の列です。
- **`random-seed*`**：seedから、一致のトリガーの捕捉、外部のトリガーの捕捉、リセット、通信だけの区間、`arm`と同時の入力を混ぜます。smokeは6操作、nightlyは20操作×3 seedです。

## 要求と目標

5要求・18目標です（`requirements.json`）。

| 要求 | 目標 |
| --- | --- |
| `TR-CAPTURE` | リングが一周、早いトリガー、`post=0`、`post=DEPTH-1` |
| `TR-TRIGGER` | 一致、マスクつきの一致、外部の信号 |
| `TR-READ` | トリガーの印、最後の印、最後の後の要求、止まる前の要求 |
| `TR-CONTROL` | アイドルからの`arm`、完了の後の`arm`、捕捉のやり直し、捕捉中のリセット |
| `TR-FIELD` | 2つ続くフラグ、ちょうど4バイトのフレーム、長すぎるフレームのエラー |

## 意図的な誤実装

| 変異 | 内容 | 検出するケース | 予定のラベル |
| --- | --- | --- | --- |
| 1 | 監視する回路の古い版（実機の不具合） | `detect-mutation1-by-replay` | `TR_DUT` |
| 2 | `post`より1つ多く書く | `detect-mutation2` | `TR_STATUS` |
| 3 | 窓の先頭を、書いた数に関係なく「1周前」とする | `detect-mutation3` | `TR_READ` |
| 4 | `kept`が`DEPTH`で止まらない | `detect-mutation4` | `TR_COUNT` |
| 5 | `post`の間の一致でトリガーを掛け直す | `detect-mutation5` | `TR_STATUS` |
| 6 | マスクを無視して全ビットで比べる | `detect-mutation6` | `TR_STATUS` |
| 7 | トリガーの印を1つ後ろのサンプルに付ける | `detect-mutation7` | `TR_MARK` |

変異2〜7は`capture`で、変異1は再生の列で、両構成とも予定のラベルで検出します。`field-old-revision`は、古い版を入れて、トレースバッファの捕捉と読出しが期待どおりであることを確かめる診断です。

## 実行

```sh
python3 examples/local-trace-buffer/run.py --out artifacts/local-trace-buffer-smoke
python3 examples/local-trace-buffer/run.py --profile nightly --out artifacts/local-trace-buffer-nightly
python3 examples/local-trace-buffer/replay.py examples/local-trace-buffer/field/issue-0001.trace
python3 -m unittest discover -s examples/local-trace-buffer/tests
```

必要なツールはIcarus Verilogだけです。`replay.py`は、再生の列を1行に1クロック（`valid data`）で出し、拒否したときは理由を出して終了コード1で終わります。`--demo-bug 1`〜`7`は通常のケースにも変異を入れ、終了コード1になることを確かめます。

出力は[共通ランナー](../local-common/README.md)の形式です。JUnitは、2構成でsmoke 26件／nightly 30件です（構成ごとに、固定3＋ランダム1／3＋診断1＋変異の検出7＋目標の判定1）。

セルフテストは11件です。ポインターで書いた3つ目の実装との窓の照合、監視する回路の2つの版、正しい通信で両方の版がエラーを出さないこと、保存したダンプが古い版の読出しと一致すること、再生で古い版のエラーが同じ位置に出て直した版では出ないこと、短すぎる窓の拒否、形の崩れたダンプ6種類の拒否、コマンドの出力と拒否、件数、全構成の実行と証跡と`--demo-bug`、seedの再現を確かめます。Icarusが見つからなければ、skipせずに失敗します。

## 確認範囲と残る制限

- サンプルは監視する回路の入力の9ビットだけで、時刻の印はありません。毎クロック記録するので、窓の中の時間の並びはそのまま再生できます。クロックを止めて記録する方式や、圧縮した記録は扱いません。
- 読出しは、テストベンチから`rd_req`で行う形です。JTAGやUARTなど、実機で外へ取り出す経路は持ちません。
- 再生は、回路の状態が分かる点から始められる場合に限ります。この例の回路は状態が小さく、既知の状態を作る点（データの後のフラグ）がはっきりしています。状態の大きい回路では、スキャンの読出しなどで状態そのものを取り出す必要があります。
- 記録が実機の入力そのものだという前提です。実機では、クロックの乗換えや取込みの時刻で、記録と実際の入力がずれることがあります。
- 窓の`DEPTH`と`post`は2組だけで確かめています。

## 確認記録

2026-11-21に、Python 3.13とIcarus Verilog 14.0開発版で、smoke（seed 17・3・100）とnightly（`--timeout 60`）が合格し、全目標18／18に両構成で届きました。セルフテスト11件も合格しました。RTLはVerilator 5.052の`--lint-only --Wall`で、トレースバッファの変異0・2〜7と`DEPTH=8`、監視する回路の変異0・1で警告0件でした。

計画の外の誤りを、作業用の写しのRTLへ10個入れてsmokeにかけ、8個が不合格になりました。

| 誤り | 最初に落ちた検査 |
| --- | --- |
| 最後の印を1つ前に付ける | `TR_READ` |
| `arm`で`kept`を消さない | `TR_COUNT` |
| トリガーの位置を1つ後ろで覚える | `TR_MARK` |
| `post`の間のサンプルを書かない | `TR_READ` |
| 1つ先のサンプルを読み出す | `TR_READ` |
| `post=0`のとき、読み出す数を1つ少なくする | `TR_READ` |
| 一致の比較で`valid`のビットを見ない | `TR_STATUS` |
| 監視する回路の数え方が7で止まらず一周する | `TR_DUT` |
| `done`でないときの読出しの要求も受け付ける | 合格のまま。`done`の前は、読み出す数がいつも0なので、動作に差が出ない |
| 監視する回路が、フラグでもエラーを出しうる | 合格のまま。直した版では、フラグはいつもエラーの判定を通らない分岐に入るので、動作に差が出ない |
