# 別クロックの描画と表示をつなぐダブルバッファ

RGB画像を2面のRAMへ保存し、書込みクロックで描画しながら、別のピクセルクロックで前の画像を表示します。描画済みの面だけをフレーム先頭で表示へ渡し、フレーム途中で新旧画像が混ざるティアリングを防ぎます。[FIFO型の画像パイプライン](../local-video-async/README.md)から、フレーム単位の蓄積へ進む例です。[4教材の入口](../local-memory-common/README.md)も参照してください。

## 2面の所有権を渡します

最初はBank 0へ入力画素を順に書き込みます。フレーム末尾まで受理したら、そのbankとフレーム番号を固定し、要求toggleを反転します。表示側は要求を2段同期して受け取り、次の`x=0, y=0`で表示面を切り替え、応答toggleを返します。この地点は有効画素のフレーム先頭であり、VSYNCのアサートエッジそのものではありません。

書込み側は応答を2段同期して確認するまで次のフレームを受け付けません。応答後は、表示が終わった古い面へ次の画像を書きます。描画側と表示側が同じ面を所有しないことをTBでも確認します。

次の画像が間に合わないときは、完成済みの前フレームをもう一度表示します。固定表示のカウンターと同期信号は停止しません。起動直後の完成画像がない期間は黒です。遅い入力に対して未完成の画像を読み始めないことが、画素単位FIFO方式との学習上の違いです。

## パケット・RAM・リセット

入力は1転送1画素のRGB888、SOF、EOL、16bitのフレーム番号です。`in_valid && in_ready`の書込み立上りで受理します。待機中は全パケットを保持します。SOFは先頭、EOLは各行末に必要で、フレーム番号はフレーム内で同じ値にします。不一致は`protocol_error`をラッチし、不正フレームを公開せず以降の受付を止め、協調リセットを必要とします。通常回帰は正しいパケットを使い、セルフテストで不正なSOF／EOLも確認します。

RAMは2面×`WIDTH*HEIGHT`画素で、独立クロックの同期書込み・同期読出しです。表示のRGB・DE・HSYNC・VSYNC・有効フレーム情報を同じピクセルエッジで登録し、遅延を揃えます。`frame_id`と`frame_valid`は教材の判定・観測用出力です。物理インターフェースのエンコードは行いません。

リセットは全体へ非同期アサートし、各ドメインで2段同期して解除します。相手側の解除完了も同期してから転送・表示タイミングを開始します。部分描画・未処理の要求・応答・表示面の有効状態を破棄し、新しいSOFから始めます。RAM配列は保持しますが、以前の面を有効化しません。片側リセットでの継続は対象外です。

## 画像サイズ・タイミング・供給条件

標準例は8×4画素です。水平フロントポーチ2、同期幅1、バックポーチ1、垂直フロントポーチ1、同期幅1、バックポーチ1です。HSYNC／VSYNCはアクティブLow、DEはアクティブHighです。有効領域外のRGBは黒です。TBはブランキングも含む全ピクセルクロックを検査します。

標準のピクセル周期20nsでは、1フレームは`(8+2+1+1)*(4+1+1+1)=84`クロック、1.68µsです。有効画素は32個なので、表示に必要な平均供給量は`32/1.68µs ≒ 19.05M画素/秒`です。書込み周期7nsの最大受付能力は約142.86M画素/秒ですが、実際は画像の完成・所有権の返却・入力bubbleで待ちます。RAM容量は`2*8*4*3=192`バイトです。

回帰は8×4・7ns/20ns、7×3・29ns/17ns、1×1・11ns/19nsの3構成で、各ピクセルクロックの初期位相もずらします。2番目のフレーム完了後には、約2表示フレーム分の上限付き入力休止を入れます。平均供給が足りない期間も前フレームを繰り返して表示できることを確認します。新しい画像を毎表示フレーム必ず供給する要求とは区別します。

入力が停止できるvalid/ready方式なので、完成フレームを落とさず順に表示できます。停止できないカメラなどを接続する場合は、別途キュー容量やフレーム破棄方針が必要です。2面だけで任意の供給速度差を無限に蓄積することはできません。

## 独立した判定と保存画像

[model.py](model.py)がPythonの整数演算で4フレームのRGB画像を作ります。TBは実際に受理した入力を`trace.csv.accepted`へ、表示した全クロックを`trace.csv`へ保存します。Pythonは入力受理の個数・順序・パケットと、独立した座標カウンターから求めたDE／HSYNC／VSYNC、全有効画素を比較します。DUTの表示アドレスを正解にしません。

フレーム番号を付け替えるだけでは合格しません。フレーム先頭でだけ切り替わること、番号が欠落・逆転しないこと、画像全体がその番号の参照画像と一致すること、4枚すべてが表示されることを要求します。途中リセット前は別の番号と画像を使い、リセット後の4枚は65～68です。旧画像や未完成画像の混入を検出します。

各ケースに`expected-65.ppm`～`expected-68.ppm`と`actual-65.ppm`～`actual-68.ppm`を保存します。画像の目視は補助で、画素比較が合否です。不一致はseed、サイクル、フレーム、座標、期待／実測RGB、クロック条件、サイズを`comparison.json`へ記録します。

4種類の変異は、フレーム途中の切り替え、行ストライドの誤り、所有権応答前の次フレーム受付、切り替え先頭だけ古い面を読む誤りです。[要求と目標](requirements.json)では通常到達と別に検出します。

```sh
python3 examples/local-video-double-buffer/run.py --out artifacts/double-buffer-smoke
python3 examples/local-video-double-buffer/run.py --profile nightly --seed 42 --out artifacts/double-buffer-nightly
python3 examples/local-video-double-buffer/run.py --waves --out artifacts/double-buffer-wave
python3 -m unittest discover -s examples/local-video-double-buffer/tests -v
```

smokeは3構成×1 seed、nightlyは3構成×3 seedで、各ケースを20表示フレーム分実行します。JUnitは12／18件、セルフテストは5件です。PPMと波形は`fast-writer/seed17/`などにあります。VCDでは`request_toggle`、`ack_toggle`、`write_bank`、`show_bank`、`x/y`、表示出力を追います。描画完了と表示開始には待ち時間があり、固定の入力→出力遅延を仮定しません。

## ファイルと確認範囲

[video_double_buffer.sv](rtl/video_double_buffer.sv)がRAMと所有権・表示制御、[video_double_buffer_tb.sv](tb/video_double_buffer_tb.sv)が別クロックの入力と表示記録、[model.py](model.py)が画像生成・比較、[run.py](run.py)が回帰です。リセット同期は[同期RAM型FIFOの部品](../local-sync-ram-fifo/rtl/memory_reset_sync.sv)を再利用します。

2026-11-20にIcarus Verilog 14.0開発版でsmoke／nightlyを実行しています。[実行記録](../../PROVENANCE.md#memory-integration-four)に正確な版と結果を記載します。bank番号とフレーム番号は、要求から応答まで安定させる複数bitのメールボックスです。実装時はCDC静的解析、同期FFの扱い、安定データの到着・保持制約、RAMの衝突条件・合成結果・STAを別途確認します。RTLのPASSはメタスタビリティ耐性の証明ではありません。DDR、PLL、HDMI、実RAMマクロ、他シミュレータでの実行は未確認です。
