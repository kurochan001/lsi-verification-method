# 鍵からスキャン・デバッグ・エラー情報へ情報が流れないことを、2実行の比較で確かめる

鍵を持つ回路では、暗号の結果だけでなく、スキャンチェーン、デバッグの読出し、エラーの記録も外から見える出口です。この例は、小さな鍵のブロックについて、「どの出力が鍵に依存してよいか」を状態ごとの表にし、その表を2つの方法で確かめます。

- **フォーマル**：鍵だけが違う2つの複製に同じ入力を与え、表が「公開」とする出力がいつも一致することを、k帰納法で非有界に証明します。
- **シミュレーション**：同じ2つの複製に、同じ操作列と違う鍵を流し、表のとおりに一致するかを毎クロック比べます。あわせて、各複製の出力をPythonのモデルと照合します。

2つの実行を並べる方法（自己合成、self-composition）は、[定時間比較の例](../local-constant-time/README.md)と同じです。この例はそれを、ライフサイクル（開発・本番）、テストモード（スキャン）、消去（zeroize）がある回路へ広げます。権限やロックそのものは[セキュリティ・ライフサイクルの例](../local-secure-lifecycle/README.md)、手順全体は[セキュリティの検証手順](../../docs/method/security-verification.md)にあります。

防御側の検証の教材です。ここで扱う「漏れ」は、設計の誤りを検査が見つけるかを確かめるための変異で、攻撃の手順ではありません。

## 対象の回路

[`rtl/secret_block.sv`](rtl/secret_block.sv)は、次のものを持つ小さなブロックです。数値と構成は教材のもので、実際の製品の鍵管理の方式ではありません。

| 部分 | 動作 |
| --- | --- |
| ライフサイクル | `lc_in`（0：開発、1：本番）を、リセット中に取り込みます。次のリセットまで変わりません。リセットは同期式で、Lowで有効です |
| 鍵 | `key_we`で`key_wdata`を書きます。これが秘密です。暗号に使う`key_q`と、開発時の読み戻し用の`key_sh`の2つの写しを持ちます。値が0でも「鍵あり」になります |
| 暗号のダミー | `start`で、鍵があれば`din XOR key`を結果にします。鍵がなければエラー1（鍵なし）を記録します。同じクロックの`key_we`が優先し、そのとき`start`は無視されます。結果の出力`ct`は、結果が有効な間だけ値を持ち、ほかは0です |
| デバッグ読出し | `dbg_req`と`dbg_addr`（0：状態、1：鍵、2：結果、3：エラーの符号）で読み、次のクロックの`dbg_rdata`に1クロックだけ出します。本番で鍵を読むと0を返し、エラー2（拒否）とその番地を記録します |
| エラーの記録 | `err_info`は`{符号, 詳細}`です。符号は1（鍵なし）と2（拒否）で、詳細は拒否された番地です。同じクロックに出来事と`err_clr`が重なると、出来事が優先します |
| スキャン | `scan_en`の間、`{key_q, ct_q}`をシフトし、上の端から`scan_out`へ出します。本番でスキャンに入る最初のクロックは、シフトせずに鍵の2つの写しと結果を消し、そのクロックの読出しも捨てます。開発ではすぐにシフトし、鍵が見えます。スキャン中の`key_we`と`start`は無視します |
| 消去 | `zeroize`は、鍵の2つの写し、結果、読出しデータ、スキャンの出力を消します。そのクロックのほかの操作より優先します。エラーの記録とライフサイクルは消しません |

`status`は`{スキャン中, ライフサイクル, 結果が有効, 鍵あり}`の4ビットです。

## どの出力が鍵に依存してよいか

この表が検査の仕様です。「消去の後」は、リセット・`zeroize`・本番のスキャンの入口の後、次に鍵を書くまでの間です。

| 出力 | 開発 | 本番 | 消去の後 |
| --- | --- | --- | --- |
| `status` | 公開 | 公開 | 公開 |
| `err_info` | 公開 | 公開 | 公開 |
| `ct` | 結果が有効な間だけ依存してよい | 同左 | 公開 |
| `dbg_rdata` | 鍵の読出しと、有効な結果の読出しは依存してよい | 有効な結果の読出しだけ依存してよい | 公開 |
| `scan_out` | 依存してよい | 公開 | 公開 |

「依存してよい」は、その値を外へ出すことを仕様として許す、という意味です（declassification）。結果の`ct`は鍵とデータの排他的論理和なので、データが分かれば鍵が分かります。この例の主題は情報の流れの検査で、暗号の強さではありません。

## フォーマル：2つの複製の比較

[`secret_flow_formal.sv`](secret_flow_formal.sv)は、`secret_block`を2つ置き、`key_wdata`だけを別の入力（`key0`、`key1`）にします。ほかの入力はすべて共有です。仮定は最初のクロックのリセットだけで、以後の入力は任意です。どちらの複製の鍵も、毎クロック自由に選ばれます。

| プロパティ | 内容 |
| --- | --- |
| `ap_status` | 2つの`status`が一致する |
| `ap_scan` | 本番では、2つの`scan_out`が一致する |
| `ap_dbg` | 直前の読出しが表で許されたものでなければ、2つの`dbg_rdata`が一致する |
| `ap_err` | 2つの`err_info`が一致する |
| `ap_ct` | 結果が有効でなければ、2つの`ct`が一致する |
| `ap_erased` | 消去の後は、`ct`・`dbg_rdata`・`scan_out`も一致する（開発でも） |
| `ap_erased_internal` | 消去の後は、鍵の2つの写しと結果の内部レジスタも一致する |
| `ai_copies`、`ai_clean_idle`、`ai_clean_secret`、`ai_prod_scan` | 帰納法に要る補助の不変条件。鍵の2つの写しが等しい、消去の後は鍵も結果も無効、消去の後は内部の値が一致する、本番のスキャン中は消去の後である。どれも仮定ではなく、assertとして証明します |

「許された読出し」と「消去の後」は、ラッパーが公開の信号（複製aの`status`と入力）から求めます。複製bの`status`は`ap_status`で同じことが保証されます。

補助の不変条件を外すと、両構成とも帰納段階が成立せず、結果はUNKNOWNでした（`ap_scan`と`ap_erased`の帰納段階の反例。到達できない状態から始まる反例です）。値の一致だけを書いても、本番のスキャン中に鍵が消えていることは帰納法には分からないからです。

計画は[`formal.py`](formal.py)にあり、[共通フォーマルランナー](../local-formal-common/README.md)で実行します。構成は`kw8`（鍵8ビット）と`kw16`（16ビット）で、1構成あたり9タスクです。

| タスク | 方式 | 結果の意味 |
| --- | --- | --- |
| `flow-proof` | k帰納法（深さ4） | 上の全プロパティの非有界の証明 |
| `scenario-cover` | 到達（深さ12） | 許された違いが実際に起きること（結果、本番の結果の読出し、開発の鍵の読出し、開発のスキャン）、拒否、鍵なし、本番のシフト、消去後の開発の読出し。8個 |
| `detect-mutation1`〜`5` | 有界検査（深さ12） | 各変異が予定のプロパティの反例になる |
| `prod-ports-miss-mutation4` | 有界検査（深さ12） | 診断：本番だけなら、変異4は出力のどこにも現れず合格する |
| `prod-internal-detect-mutation4` | 有界検査（深さ12） | 本番だけでも、内部の検査（`ap_erased_internal`）は変異4を見つける |

変異を見つけるタスクでは補助の不変条件を外しています（`AUX=0`）。反例が、変異の破ったプロパティだけを名指しするようにするためです。

## シミュレーション：同じ操作列と違う鍵

[`tb/secret_flow_tb.sv`](tb/secret_flow_tb.sv)は、2つの複製に1行ずつ同じ公開の入力を与え、鍵だけを`key0`と`key1`に分けます。各クロックの後に、次の順で検査します。

1. **流れの検査（`SF_FLOW_*`）**：上の表と同じ規則で、公開の出力が2つの複製で一致するかを比べます。期待値を使いません。フォーマルのラッパーと同じ規則です。
2. **モデルとの照合（`SF_*`）**：各複製の5つの出力を、[`model.py`](model.py)の値と`!==`で比べます。Xが出れば不一致になります。

モデルは、READMEの仕様から、クロックごとに整数で書いたものです。1つの操作列に対して2回（それぞれの鍵で）動かし、2つの複製の期待値を作ります。表は`model.allowed`と、テストベンチとラッパーの中に、それぞれ書いています。

流れの検査は、2つの鍵が漏れの現れる場所で違うときにしか、漏れを見られません。そのため固定シナリオは、2つの鍵がすべてのビットで違う組（`0xa5…`と`0x5a…`）と、片方が0の組を使います。変異2は、同じ鍵を2つの複製に与えた固定シナリオでも実行し、そのときは流れの検査が何も報告せず、モデルとの照合だけが見つけることを確かめます。

| ケース | 内容 |
| --- | --- |
| `boundaries` | 固定シナリオ（8ビットで74行、16ビットで106行）。本番と開発の両方で、表のすべての行を通る |
| `random-seed*` | 乱数の操作列。リセットのたびにライフサイクルを選び、2つの鍵を独立に選ぶ（10%は同じ鍵）。smokeは300操作×1 seed、nightlyは2000操作×3 seed |
| `detect-mutation1`〜`5` | 固定シナリオで、各変異が予定のラベルで不合格になる |
| `equal-secrets-detect-mutation2` | 同じ鍵の固定シナリオ。流れの検査は合格し、`SF_DBG`（モデルとの照合）で不合格になる |

## 実行

```sh
python3 examples/local-secret-flow/run.py
python3 examples/local-secret-flow/run.py --profile nightly
. artifacts/toolchains/formal-venv/bin/activate
python3 examples/local-secret-flow/formal.py
python3 -m unittest discover -s examples/local-secret-flow/tests -v
```

シミュレーションは[共通シミュレーションランナー](../local-common/README.md)を使い、Icarus Verilogだけで動きます。構成は`kw8`と`kw16`で、JUnitはsmoke 18件、nightly 22件です（1構成あたり、固定1、乱数1または3、変異5、同じ鍵の変異1と、要求・カバレッジの判定1）。`--demo-bug 1..5`は通常のケースにも変異を入れ、終了コード1になります。フォーマルは18件です（2構成×9タスク）。`formal.py --demo-bug 1..4`は証明のタスクに変異を入れ、証明が成立しなくなります。

## 要求と目標

[`requirements.json`](requirements.json)は7要求・28目標です。どの目標も、2構成とも固定シナリオだけで届きます。

| 要求 | 内容 |
| --- | --- |
| SF-LIFECYCLE | 開発と本番の両方を実行する |
| SF-STATUS | 状態は公開の入力だけで決まる。値が0の鍵でも鍵ありになる。書込みが`start`に優先する |
| SF-SCAN | 本番のスキャン出力は鍵に依存しない。入口で消去し、そのクロックの読出しを捨てる。開発のスキャンは鍵を見せてよい |
| SF-DBG | 本番の鍵の読出しは0で、拒否として記録する。開発の鍵の読出しと、有効な結果の読出しは鍵に依存してよい |
| SF-ERR | エラーの記録は、どのライフサイクルでも鍵に依存しない。出来事が消去より優先する |
| SF-CT | 結果は有効な間`din XOR key`で、無効な間は0 |
| SF-ERASE | リセット・消去・本番のスキャンの入口の後は、次に鍵を書くまで、古い鍵がどこにも現れない |

## 変異

| 変異 | 誤り | シミュレーション | フォーマル |
| --- | --- | --- | --- |
| 1 | 本番でスキャンに入るときに消去しない。鍵がシフトアウトできる | `SF_FLOW_SCAN` | `ap_scan` |
| 2 | 本番のデバッグのマスクが鍵の上半分しか覆わない | `SF_FLOW_DBG`（同じ鍵なら`SF_DBG`） | `ap_dbg` |
| 3 | 拒否した読出しで、エラーの詳細にマスク前の値を記録する | `SF_FLOW_ERR` | `ap_err` |
| 4 | 消去が暗号用の写しだけを消し、読み戻し用の写しを残す | `SF_FLOW_ERASED` | `ap_erased`、本番だけなら`ap_erased_internal` |
| 5 | 「鍵あり」を書込みではなく鍵の値（0でない）から決める | `SF_FLOW_STATUS` | `ap_status` |

変異4は、本番では出力のどこにも現れません。本番の読出しは拒否され、スキャンの入口で写しも消えるからです。出力だけの検査は本番では合格し（`prod-ports-miss-mutation4`）、内部のレジスタの検査が見つけます。開発では、消去の後の鍵の読出しが古い鍵を返すので、出力の検査でも見つかります。

変異5は、片方の鍵が0のときにしか見えません。2つの鍵がどちらも0でなければ、「鍵あり」は両方とも1になるからです。

## 計画外の誤り

上の変異とは別に、作業用の写しのRTLへ小さな誤りを11個入れ、両構成の固定シナリオと乱数の操作列（seed 17、300操作）で実行しました。

| 誤り | 固定シナリオ（8・16ビット） | 見え方 |
| --- | --- | --- |
| 本番の鍵の読出しをまったく覆わない | `SF_FLOW_DBG` | 流れ |
| 鍵なしのエラーの詳細に`din`を記録する | `SF_ERR` | モデル（`din`は公開なので流れではない） |
| 状態の読出しのビットの順を誤る | `SF_DBG` | モデル |
| 鍵の書込みが結果を無効にしない | `SF_STATUS` | モデル |
| スキャンを出た後も`scan_out`を保つ | `SF_SCAN` | モデル |
| 開発でも鍵の読出しを拒否と記録する | `SF_ERR` | モデル |
| エラーの消去が出来事より優先する | `SF_ERR` | モデル |
| 開発でもスキャンの入口で消去する | `SF_STATUS` | モデル |
| 消去が結果のレジスタを消さない（無効にはする） | `SF_FLOW_ERASED` | 流れ |
| 本番のスキャンの入口で、読み戻し用の写しを消さない | 合格 | 出力からは見えない |
| 暗号が読み戻し用の写しを使う | 合格 | 動作に差が出ない（2つの写しはいつも等しい） |

「消去が結果のレジスタを消さない」は、最初の固定シナリオでは見つかりませんでした。消去の後の開発のスキャンが2クロックだけで、古い結果がチェーンの出口まで届かなかったためです。そのスキャンをチェーンの長さより1つ長くし、両構成で流れの検査が見つけるようにしました。

「本番のスキャンの入口で、読み戻し用の写しを消さない」は、変異4と同じく出力からは見えません。次のシフトで写しは上書きされ、その間の読出しは本番では拒否されるからです。この誤りを入れた写しで有界検査（深さ12）を実行すると、出力の検査は合格し、内部の検査（`ap_erased_internal`）が反例を出しました。「消去が結果のレジスタを消さない」は、出力の検査（`ap_erased`）でも内部の検査でも反例が出ました。

## 確認範囲と残る制限

- 検査の対象は、ポートのデジタルの値とクロックです。消費電力、電磁放射、遅延の差、故障の注入によって鍵が漏れないことは確かめていません。
- 2値の検査です。Xを伝える経路の解析は扱いません。
- 表で「依存してよい」とした出力（開発の読出しとスキャン、有効な結果）は、何をどれだけ出すかを検査していません。許した範囲の中での漏れの量は、この方法では測れません。
- ライフサイクルはリセットの間だけ変わる、という前提です。動作中に入力が変わる回路は扱いません。開発から本番へ移るときに鍵を引き継ぐ方式も扱いません。
- 内部の検査（`ap_erased_internal`）は、FORMALのときだけある出力`f_secret`で内部のレジスタを見ます。シミュレーションは内部のレジスタを直接は比べません。
- 鍵は外から書く方式だけです。OTPなどからの読込み、鍵の階層、認証は扱いません。
- 消去は1クロックで終わる方式だけです。複数のクロックにまたがる消去の途中の状態は扱いません。
- 情報の流れを検査する標準や規格の文書とは照合していません。この例は認証や適合の主張をしません。
